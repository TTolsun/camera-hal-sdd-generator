# qcam 포함 추가 비용과 원고 이월 결함

이 기록은 [사전 조건](cost-qt-plan.md)에 따른 추가 시험이다. 원래 [부분 비용](cost.json), [24건의 자동 독자 결과](README.md), 사람 평가 상태와 판정 기준을 바꾸지 않는다. 사람 참가자와 사람 검토 시간은 여전히 없다. 기계 비용도 전체 유지 비용 절감으로 해석하지 않는다.

이 기록 이후의 순방향 생성·번역·계약 검토·정상 사이트 단계는 [통제 기계 비용 후속 결과](cost-qt-completed-machine.md)에 별도로 남긴다. 아래 당시의 부분 결과와 실패를 새 성공으로 덮어쓰지 않는다.

## 실제 빌드·추출·영향 분석

생성기는 `d392d7520b74f2c5a462daaba5c1b72a31f46269`, 실제 변경은 `be909e49…→293d751a…`의 qcam AWB uniform 수정이다. 별도 WSL 작업본에서 두 커밋을 각각 빌드·추출했다. qcam=enabled, pipelines=all, IPA 7개, cam·GStreamer=enabled, 빌드 병렬 수 3을 유지했다. 환경 설치, 최초 구축, 증분 비용은 합치지 않는다.

전체 명령·시간 경계·facts 해시·Meson 옵션·의존성·실제 TU와 로그는 [단계 장부](../../../../examples/libcamera/validation/issue253/runs/cost-followup/linux-run-02/execution.json)에 있다. 각 시간은 subprocess 시작부터 종료까지이며 CPU·서버 대기·환경 지연을 분해한 값은 아니다. 사람 활동·대기 분리 값은 null이다. 첫 시도는 캐시의 얕은 Git 이력에 부모 tree가 없어 중단했다. 실패 장부와 로그도 `linux-run-01`에 보존했다. 이후 원본 저장소에서 실제 부모·머리 이력을 가져왔으며 두 facts를 같은 파일로 재명명하지 않았다.

qcam이 빠진 원래 300 TU와 달리 이 시험은 qcam을 포함한다. 이 추가 조건을 원래 운영 프로필의 성과로 바꾸지 않는다. 빌드 성공은 GPU 렌더링·실기기·사내 HAL 검증이 아니다.

## 원고 단계의 실패와 재검증

공개 문서 입력은 `TTolsun/libcamera-sdd@4d656cd…`, build ID `b5da5d8c…`이며 manifest의 328개 산출물과 영어 카탈로그 해시를 확인했다. 모델 호출 전에 [입력 잠금](../../../../examples/libcamera/validation/issue253/runs/cost-followup/generation-input-lock.json)을 만들었다. 기본 예제 설정으로 부모 원고를 구성한 첫 시도는 가상 관찰 문서의 소유 설정 누락과 오래된 커밋 원고 때문에 수명주기 검사에서 중단했다. 역방향 영향 분석 4.114초, 구조 생성 시도 50.575초를 기록했다. 원고 생성·번역 모델 호출은 0회이며 완료 비용이 아니다.

실제 공개판의 추가 sections·products와 과거 집필 프로필을 복원한 뒤 이월 문제를 별도로 대조했다. 발행 기본 집필 규칙은 현재 것으로 유지하고, 보존할 원고에만 명시된 과거 CLI·집필 규칙을 읽기 전용으로 연결했다. 소스·facts·본문·질문·근거 검사와 역사 기록은 그대로 유지했다. 이 설정은 경로를 옮긴 추가 검증 설정이며 원래 공개 설정 그대로라고 주장하지 않는다. 모델 호출은 없다.

| --- | ---: | ---: | --- |
| 수정 전 생성기 | 4 | 25 | 24개 원고는 사이트 검증이 인정하는 명시 집필 프로필을 이월에서 무시했다. |
| 수정 후 생성기 | 28 | 1 | 구성요소 색인은 새 qcam facts와 지문이 달라 계속 차단했다. |

원자료는 [같은 기준 코드의 수정 전](../../../../examples/libcamera/validation/issue253/runs/cost-followup/carry-probe-before-child/result.json)과 [수정 후](../../../../examples/libcamera/validation/issue253/runs/cost-followup/carry-probe-after/result.json)에 있다. 먼저 d392에서도 같은 4/25 결과를 얻었고, 이어 da0ca376의 원래 carryover 함수를 같은 수정 후 런타임에 별도 로드해 4/25를 재현했다. 후자의 result.runtime은 패키지 경로이며 실제 이월 함수는 Git da0ca376에서 로드했다. 차단된 원고의 원본 바이트는 보존했다. 집필 프로필 확인은 과거 CLI를 실행할 권한이 아니며 소스가 바뀐 답변을 재사용하게 하지 않는다. 독립 검토에서 개요 그림의 연결 대상에 개요 프로필이 전파되는 추가 결함도 찾아 대상별 설정을 사용하도록 수정했다.

수정 전후 원고 대조는 서로 다른 생성기 버전이고 순차 실행했으므로 경과 시간 차이를 비용 절감 근거로 사용하지 않는다. 실제 프로필 처리 결함의 수정 여부만 판단한다. 전체 부모·머리 원고 구성, 필요한 번역·독립 검토·사이트 검증, 사람 활동 검토는 아직 미완료다. 원고·질문·근거 수정량과 호출 재사용률·총 유지 비용 절감률도 이 단계에서 확정하지 않는다.

## 실패 과업의 원인 구분

별도 독립 Codex CLI/Terra High 검토는 다음 범위만 확인했다. [검토 원본](../../../../examples/libcamera/validation/issue253/runs/cost-followup/failure-triage/execution.json)의 세 호출은 각각 21.347초, 20.481초, 21.359초다. 사람 검토 시간이 아니다. D2의 첫 초과 길이 payload는 모델 호출 전에 준비 assertion에서 중단했고 소요 시간을 측정하지 않았다.

- T2: 고정 B의 vendor-overview·vendor-integration 본문에서 장치별 핸들러가 스트림 구성에 따라 하드웨어 파이프라인을 구성하는 책임을 직접 설명하지 않았다. source293의 공식 아키텍처 절을 질문 근거에 연결하고 기존 경계 그림을 보완하는 후속 범위를 확정했다.
- D1: 타임아웃과 앱 완료 콜백 설명은 다른 기존 페이지에 있다. 추가 서브에이전트 점검은 `pipeline-requests#요청-준비와-장치-큐`, `request-lifecycle#제출에서-완료까지` 및 정지 절의 콜백 관측 계획을 확인했다. diagnosis의 해당 조사 단계에서 직접 연결하는 개선이 우선이다. 같은 설명을 다시 쓰거나 원래 실패 정답을 변경하지 않는다.
- D2: 고정 B의 정지 조사 계획에 대상 장치의 stopDevice 구현 검토와 요청별 중복 완료 검사가 명시되지 않았다. 기존 콜백 시점 설명·가상 관찰 결과는 반복하지 않고 두 조사 항목을 소스 근거에 묶어 보완한다. 실제 기기 검토·실행을 했다는 문장으로 바꾸지 않는다.

이 세 범위는 제품 질문·근거·탐색·그림의 생성 원본에서 개선한 뒤 기존 루브릭으로 별도 재평가해야 한다. 이번 프로필 수정만으로 설명 결함이나 #253의 완료 조건을 충족했다고 하지 않는다. 자동 검토·원고 이월·기계 실행은 사람 정답률·읽기 부담·사람 승인·사내 효과를 대체하지 않는다. 표와 단계 원자료로 비교 가능한 측정 기록이므로 별도 그림은 생략한다.
