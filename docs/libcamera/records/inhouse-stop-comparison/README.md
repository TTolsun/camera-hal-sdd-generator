# 촬영 정지 중에 돌아온 프레임을 써도 되는가?

사내 원고를 가져오지 않고 공개 코드에서 첫 실행 절차를 시험했다. 대표 과제는 “정지 처리 중 완료 통지를 받았습니다. 프레임을 사용해도 됩니까? 버퍼를 다시 쓰기 전에 무엇을 확인하겠습니까?”였다. 사내 템플릿의 기존 질문 두 개를 적용한 [첫 원고](first-run/vendor-contract.md)와, 같은 주제의 질문과 소스 발췌만 바꾼 [최종 개선 원고](focused/vendor-contract.md)를 실제 CLI로 생성했다. [공개 독자판 원문](https://github.com/TTolsun/libcamera-sdd/blob/663364db7ad97d38e15d217d46ed920010f0c865/docs/request-flow.md)도 같은 과제로 읽혔다.

## 무엇을 고정했는가

- 소스는 공개 독자 페이지 인용 40건이 가리키는 `adfa719f8ed67d18fd8a0739fc088a1f8b9e7252`다. 공개 저장소 커밋은 `663364db7ad97d38e15d217d46ed920010f0c865`, Pages `build_id`는 `cd94f44da4c740fd19dd7b0b186c4e873367edd9c5ccf9e936ae1e75be341dec`다. Pages에서 받은 Markdown의 SHA-256과 manifest의 출력 해시를 대조했다.
- 두 조건은 같은 커밋에서 추출한 구조 facts를 재사용하고, 각각의 발췌는 해당 Git 커밋에서 다시 수집했다. 공개판의 완성 원고·편집 도입문은 생성 입력에서 제외했다. 공개판은 독자 과제의 참고점이고, 입력을 통제한 비교는 첫 원고와 개선 원고 사이에서만 했다.
- 실행기는 Codex CLI `0.171.0-alpha.13.2`, 모델은 `gpt-6.1-terra`, 추론 강도는 `high`다. 두 조건에서 생성기 커밋, 프롬프트, 집필 규칙, 그림 질문 두 개, 30,000자 생성 입력 한도와 재시도 설정이 같다. 그림의 원문 파일은 원고에 포함된 Mermaid 블록에서 추출했다. [입력과 재현 명령](../../../../examples/libcamera/validation/inhouse-stop-comparison/README.md) · [원고 지문과 실행별 CLI 영수증 요약](runs.json)
- 원고마다 이력이 없는 독립 CLI 세션에 독자 역할, 같은 과제, 해당 문서의 본문·그림만 주었다. 생성 front matter, 번역용 그림 주석, 소스 부록은 제외했다. 외부 링크를 열 수 없는 조건이므로 탐색 결과는 한 페이지 안에서의 판단을 뜻한다. 별도의 독립 Terra High CLI에는 생성 원고와 해당 조건의 소스 발췌를 주어 사실 관계를 대조했다. 실제 개발자나 실기기가 참여한 시험은 아니다.

## 입력을 고치면서 드러난 점

첫 원고는 “대기 중인 모든 요청은 취소되어 오류 상태로 동기적으로 완료됩니다”라고 설명했다. 독자는 취소 가능성과 fence 처리 실패 후 재등록 전 회수 조건을 찾았다. 그러나 지금 받은 통지가 정상 영상 사용을 허용하는지는 결정하지 못했다. 요청의 완료 상태를 바꾸는 구현을 읽을 수 있었어도, 첫 입력에는 각 프레임 상태가 영상 데이터의 유효성에 대해 무엇을 뜻하는지 설명하는 발췌가 없었다. [첫 원고 독자 답변](first-run-reader.md) · [첫 원고 근거 검토](first-run-grounding.md)

개선 조건의 첫 실행은 본문을 생성한 뒤 그림 입력이 30,000자를 넘어서 중단됐다. 기본 한도를 유지하고 중복 구간을 줄였다. 다음 원고는 `FrameCancelled`를 찾아냈지만 “프레임 데이터와 상태 필드를 제외한 메타데이터 필드는 유효하지 않습니다”라고 써서 프레임 데이터도 유효하다고 읽힐 여지를 남겼다. 소스는 영상 데이터가 무효이고 메타데이터에서는 상태 필드만 유효하다고 명시한다. 이 경우에는 근거가 이미 있었다. 후속 질문에서 영상 자체의 사용 여부와 읽을 수 있는 메타데이터 필드를 따로 설명하게 했다. 또한 앞선 발췌에서 빠진 정상·시동 상태와 지연 수신자의 포인터 수명 근거를 추가했다. [중간 원고 독자 답변](intermediate-reader.md) · [중간 원고 근거 검토](intermediate-grounding.md)

공개판을 읽은 독자는 `RequestComplete`에도 개별 버퍼에 오류가 있을 수 있다는 설명, 별도 수신자의 마지막 사용 시점, fence 회수 조건을 찾았다. 다만 앞쪽 그림의 “촬영 완료”라는 표현은 뒤쪽 정지 절까지 읽은 뒤에야 정상과 취소 모두에 해당한다는 뜻을 파악했다고 답했다. [공개판 독자 답변](published-reader.md)

## 최종 원고로 할 수 있는 판단

최종 원고는 “`FrameCancelled`는 프레임 완료 전에 촬영이 정지되어 데이터가 유효하지 않은 상태이며, 메타데이터에서는 상태 필드만 유효합니다”라고 설명한다. 독자는 이 문장을 근거로 취소 영상을 쓰지 않겠다고 답했다. 성공·오류·시동 상태도 각각 판별했다. 요청을 다시 제출하기 위한 `reuse()`와 버퍼를 실제로 덮어써도 되는 시점을 구별했고, 후자는 다른 스레드의 소비자가 사용을 끝냈는지 확인해야 한다고 답했다. [최종 원고 독자 답변](focused-reader.md)

독립 근거 검토에서는 정지 경로와 상태 설명에서 뚜렷한 사실 오류를 찾지 못했다. 다만 원고가 장치별 정지 처리나 애플리케이션의 마지막 소비 시점을 특정하지는 못한다. 독자도 실제 상태값을 어디에서 읽어야 하는지는 추가 확인이 필요하다고 답했다. 이 사례에서는 질문과 소스 범위를 바꿔 과제에 필요한 판단을 끌어낼 수 있었다. 어떤 질문이든 같은 결과를 낸다는 결론이나 생성 지시의 단독 효과는 이 시험으로 판단할 수 없다. [최종 원고 근거 검토](focused-grounding.md)

최종 실행에서는 본문 생성 후 그림 하나가 300초 제한에 걸렸다. 같은 출력 디렉터리와 CLI 설정으로 재개해 본문 두 단위의 체크포인트를 검증한 뒤 그림 두 개를 새로 생성했다. 처음 실패한 평가와 재개 장부를 모두 보존했다. [실행 결과](runs.json)

두 원고의 마지막 안내 링크는 공개 후 주소가 바뀔 수 있는 API 문서에서 확인된 소스 커밋으로 교체했다. 생성기에서 다시 출력할 때 추가 CLI 호출은 없었다. 평가에 사용한 본문과 그림이 재출력 전후에 동일한지 대조했다.

## 사내에서 반복하는 방법

1. 연동 담당자가 실제로 결정해야 하는 행동 하나를 질문으로 적는다. 그 행동이 달라지는 두 상황과 호출자가 관찰할 수 있는 값부터 정한다.
2. 같은 커밋에서 요청 상태를 쓰는 쪽, 버퍼별 상태의 의미를 정의하는 쪽, 마지막으로 객체를 사용하는 쪽을 연결한다. 제출 반환, 완료 신호, 지연 수신, 재제출을 구별하는 데 필요한 범위만 발췌한다.
3. 원고 생성 후 처음 읽는 동료에게 원래 질문을 그대로 준다. 판단에 쓴 본문 한 문장과 그림의 해당 분기를 짚게 한다. 답이 없으면 입력을 확인하고, 근거가 있는데도 오독하면 주체·조건·결과가 섞인 문장을 찾아 생성 질문을 고친다.
4. 소스가 보장하는 조건과 제품에서 직접 시험할 조건을 기록한다. 사내 HAL에서 첫 확인 과제는 “정지 중 돌아온 버퍼에서 누가 프레임의 유효성을 판정하며, 비동기 소비자가 사용을 마친 뒤 어느 시점에 버퍼를 생산자에게 돌려줄 수 있는가?”다.
