완료 통지만으로는 프레임을 사용해도 되는지 결정할 수 없습니다. 먼저 **요청 상태와 각 버퍼의 프레임 상태**를 확인하겠습니다.

**문서만으로 결정할 수 있는 경우**

- 버퍼가 `FrameSuccess`이면 해당 프레임을 영상으로 사용할 수 있습니다. 반면 `FrameCancelled`인 버퍼는 사용할 수 없습니다. 요청이 `RequestComplete`여도 버퍼에 `FrameError`가 있을 수 있으므로 요청 상태만으로 판단하지 않겠습니다. **「정지와 연결 해제를 구분하기」**는 “버퍼별 `FrameSuccess`로 영상 사용 여부를 판단”하고 “취소된 버퍼는 `FrameCancelled`”라고 설명합니다.
- 같은 요청을 다시 제출하려면 먼저 `Request::reuse()`를 호출해야 합니다. `ReuseBuffers`는 기존 버퍼를 다시 연결하지만, 펜스를 사용할 때는 이를 피하라는 권고가 있습니다. **「요청 생성과 소유권」**의 “다시 큐에 넣기 전에 `Request::reuse()`를 호출”과 “펜스를 사용할 때는 `ReuseBuffers`를 쓰지 않도록 권고”가 근거입니다. 다시 제출할 때는 버퍼를 최소 한 개 연결하고 카메라가 `Running` 상태인지도 확인하겠습니다. **「요청 제출과 완료」**는 “캡처 버퍼를 최소 한 개 연결”하고 “`Running` 상태일 때만 호출”해야 한다고 명시합니다.
- 신호되지 않은 펜스로 타임아웃이 난 버퍼라면, 다른 요청에 재사용하기 전에 `releaseFence()`로 펜스를 회수해야 합니다. **「타임아웃 뒤 펜스 회수」**는 회수를 “재사용 전 회수 의무”이자 “필요한 선행 조건”으로 설명합니다. 회수만으로 다른 모든 재사용 조건이 충족된다고까지는 말하지 않습니다.

**추가 확인이 필요한 경우**

- 받은 통지가 `bufferCompleted`인지 `requestCompleted`인지, 그리고 실제 요청·버퍼 상태가 무엇인지 질문에 없습니다. **「버퍼 완료와 요청 완료」**에 따르면 “마지막 버퍼가 완료된 뒤에도 `completeRequest()`를 명시적으로 호출”해야 합니다. 따라서 버퍼 완료 통지만 받았다면 요청 완료 여부도 확인하겠습니다.
- 버퍼를 다시 쓰기 전에는 요청 완료 콜백까지 버퍼가 유효하게 유지됐는지와 다른 수신자가 아직 버퍼나 포인터를 사용하는지 확인하겠습니다. **「소유권과 두 완료 경계」**는 “요청 완료 콜백이 호출될 때까지 버퍼가 유효하도록” 요구합니다. 같은 절의 그림은 별도 Queued 수신자가 계속 사용하면 “마지막 사용까지의 수명”을 확인하고, “stop 반환이 모든 수신을 기다린다고 가정하지” 말라고 합니다. 실제 수신자와 동기화 계약은 이 문서만으로 알 수 없습니다.
- 정지가 성공했는지, 연결 해제도 발생했는지 확인하겠습니다. **「정지 API 계약과 연결 해제 TODO」**는 정지에 대해 “모든 대기 요청 취소·즉시 오류 완료”라고 제시하지만, 실행 중 연결 해제의 대기 요청 처리는 “TODO”로 남깁니다. 또한 **「촬영을 멈췄는데 왜 완료 알림이 오는가?」** 그림에는 UVC `STREAMOFF` 실패 시 “장치 버퍼 반환 루프를 건너뛰고 오류 반환”하는 경로가 있어, 성공 경로만으로 모든 버퍼가 반환됐다고 판단할 수 없습니다.

찾을 때는 **「요청 생성과 소유권」 → 「요청 제출과 완료」 → 「소유권과 두 완료 경계」 및 「정상 완료와 다음 요청 준비」 → 「버퍼 완료와 요청 완료」 → 「정지와 연결 해제를 구분하기」 → 「타임아웃 뒤 펜스 회수」** 순서로 흐름을 확인했습니다.

모호했던 표현은 완료 통지가 “촬영 완료”를 알린다는 그림의 문장입니다. 뒤의 정지 절을 함께 읽어야 같은 `requestCompleted`가 정상 완료와 취소 모두에서 올 수 있음을 알 수 있습니다. 또 버퍼를 콜백까지 유효하게 유지하라는 기한은 다른 Queued 수신자의 마지막 사용 시점을 알려주지 않습니다. 그림 자체에도 “의미와 기기 실행은 검증 전”이라고 적혀 있으므로 실제 장치의 실행 결과까지 확정할 수는 없습니다.
