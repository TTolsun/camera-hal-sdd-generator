완료 통지를 받았다는 사실만으로 프레임을 사용할 수는 없습니다. 먼저 **완료된 요청의 상태와 각 버퍼의 프레임 상태**를 확인하겠습니다.

**문서만으로 결정할 수 있는 경우**

- 요청이 정상 완료됐는지 취소됐는지는 완료 통지로 전달된 요청의 상태로 판단합니다. 「제출·완료·정지」는 “요청의 상태에서 확인합니다”라고 설명하며, 상태를 `RequestComplete` 또는 `RequestCancelled`로 설정한다고 적습니다.
- 각 버퍼가 `FrameSuccess`라면 영상 데이터와 모든 메타데이터가 유효합니다. `FrameCancelled`라면 영상 데이터는 유효하지 않고 `status`만 유효합니다. `FrameError`는 영상 데이터가 손상됐거나 없거나 유효하지 않을 수 있으므로 유효한 프레임으로 취급할 수 없습니다. `FrameStartup`은 캡처에는 성공했지만 프레임을 소비하지 않도록 권고됩니다. 근거는 「요청과 버퍼 수명」의 “영상 데이터와 모든 메타데이터 필드가 유효합니다”와 각 상태 설명입니다.
- 요청을 재사용해 다시 큐에 넣으려면 먼저 `Request::reuse()`를 호출합니다. 기존 버퍼를 유지하려면 `ReuseBuffers`를 설정합니다. 버퍼를 다시 추가할 때 fence가 남았는지와 해당 스트림에 버퍼가 이미 설정됐는지도 확인합니다. 특히 fence 처리 실패로 오류 완료됐다면 다시 추가하기 전에 fence를 해제해야 합니다. 「요청과 버퍼 수명」은 “큐에 넣기 전에 `Request::reuse()`를 호출해야 합니다”, “다시 추가하기 전에 … fence를 해제해야 합니다”라고 적습니다. 재큐잉은 카메라가 `Running`일 때만 가능합니다.

**문서만으로는 부족한 경우**

- 통지의 종류와 실제 상태값이 제시되지 않았으므로, 이 사례의 프레임을 사용할 수 있는지는 결정할 수 없습니다. 「요청과 버퍼 수명」에도 “버퍼별 프레임 상태를 읽는 구체적인 접근 방법은 확인 필요입니다”라고 적혀 있습니다.
- 버퍼를 **덮어써도 되는 시점**은 완료 통지만으로 확정할 수 없습니다. 요청 완료 콜백까지 버퍼를 유효하게 유지해야 하고, 다른 스레드의 슬롯은 비동기로 호출될 수 있습니다. 「요청과 버퍼 수명」은 “지연된 콜백과 소비 작업이 버퍼 사용을 끝냈는지 확인하는 구체적인 조건은 확인 필요입니다”라고 명시합니다. 따라서 관련 콜백과 소비자가 사용을 마쳤는지 연동 환경에서 확인해야 합니다.
- 정지 중 장치별 요청 처리 결과도 공통 경로만으로 단정할 수 없습니다. 「제출·완료·정지」의 실행 확인 항목은 “해당 `stopDevice()` 구현을 확인해야 합니다”라고 합니다.

찾을 때는 첫 표에서 「제출·완료·정지」로 이동해 요청 상태와 프레임 상태를 확인한 뒤, 「요청과 버퍼 수명」과 그 안의 「요청과 버퍼를 유지할 기간」 그림에서 콜백, 재사용, fence 조건을 살폈습니다. 특히 “완료 후 제출 순서대로 애플리케이션에 반환됩니다”는 완료 통지와 소비 작업 종료가 같은 시점인지 모호했습니다. 이어지는 본문이 지연된 콜백과 소비 작업의 종료 조건은 확인이 필요하다고 밝혀, 반환만으로 덮어쓰기 안전성을 판단하지 않았습니다.
