# 로컬 9B의 정확한 Vendor 문서 작성 시험

**오류를 거절하는 데서 끝내지 않고, 실제 9B가 질문의 조건을 모두 설명하는 작성 경로를 비교했습니다.** 공개 libcamera 입력을 사용했으며 사내 HAL이나 사내 모델을 시험한 결과가 아닙니다. 이전 [차단 중심 재시험](vendor-9b-retest.md)의 실패 기록도 보존합니다.

## 남은 실패 원인

긴 페이지 집필 지침, 독자 프로필 설명, 예외 지침과 정규식 계약을 한 문단 작성 요청에 함께 넣으면 첫 동작만 설명하는 응답이 반복됐습니다. 같은 질문·근거·JSON 스키마에서 짧은 한국어 지침을 사용한 비교는 `completeBuffer`의 요청 완료 통지, `stopDevice`의 취소·오류 완료, Invalid 조건을 설명했습니다. 기본 집필 지침을 다시 붙인 비교에서는 완료·취소가 다시 빠졌습니다. 질문과 스키마를 유지한 소수 사례 비교이며 통계적 성능 보장은 아닙니다.

JSON 스키마를 없앤 긴 프롬프트에서는 설명이 늘어도 JSON이 깨졌습니다. 따라서 형식 검사를 제거하지 않고 문단 작성 지침과 페이지 구성을 분리했습니다. 짧은 지침에 문장 길이 지시를 더한 전체 시험에서도 누락이 재현됐습니다. 지침을 더 많이 주는 방법을 정확도 개선으로 가정하지 않습니다.

발췌를 함수 하나로 줄이는 것만으로도 충분하지 않았습니다. `generateConfiguration`은 입력 설명만 쓰고 실패 반환·스레드·상태 변경 조건을 빠뜨렸습니다. **같은 근거 뒤에 질문을 배치**하거나 질문을 번호로 구분한 비교에서는 빠진 항목을 모두 작성했습니다. 현재 focused 모드는 근거 → 질문 → JSON 출력 예시 순서입니다.

| 관측한 문제 | 반영한 개선 |
|---|---|
| Camera 등록과 PipelineHandler 하위 클래스 등록 혼동 | 질문에서 등록 대상을 구분하고 근거가 있는 매크로 등록 의무를 묻습니다. |
| 서로 다른 설정 함수나 정지 구현·장치 계약 혼합 | 함수 계약을 각각 발췌합니다. 공통 stop의 바깥 순서·루프·ASSERT는 보존합니다. |
| 완료 통지 의무 누락, 실제 완료를 완료 간주로 표현 | 요청 추적과 completeRequest 의무를 같은 질문에 두고 해당 문단을 직접 제공합니다. |
| 복합 질문의 뒤 조건 누락 | 근거를 먼저 읽고 마지막에 항목별 질문에 답하게 합니다. |
| 정상적인 한국어 번역 거절 | 실제 응답의 “스트림 역할”을 roles의 대안으로 인정합니다. |
| 커널 API와 개발자 추상화 혼동 | 제품 가치 질문에서 내부 작업과 개발자 사용 방식을 구분하고 소개 문단의 불필요한 그림 지시를 제외합니다. |

코드 발췌의 빈 줄 분할도 실패 원인이었습니다. stop의 취소 루프·ASSERT·순번 초기화가 서로 다른 인용 ID로 나뉘었지만 한 답변은 ID 하나만 받을 수 있었습니다. 모델이 여러 ID를 합쳐 잘못된 JSON을 만드는 실제 응답이 남았습니다. 집중 작성에서는 선택한 발췌 전체를 인용 단위로 유지합니다. 반복되는 문구는 새 `sources[].scope`로 해당 함수 안에서만 선택하며 모호하거나 범위를 벗어나면 실패합니다.

독립 질문 시험에서는 등록 대상 클래스, 파이프라인에 필요한 장치와 시스템 전체 장치, 상태에 영향을 주는 함수와 상태를 정의하는 함수의 혼동도 확인했습니다. 역할이 다른 설명을 나누고 불필요한 인자 설명을 발췌에서 제외했습니다. 최종 질문은 40개이며, 입력·반환·호출 문맥을 나누면서도 조건과 필수 완료 의무는 함께 유지합니다.

## 공통 생성기와 사내 적용

`review.design_prompt: focused`를 명시하면 프로젝트의 `focused-design-system.md`를 사용합니다. 표준 모드는 기존 지침을 유지합니다. 제품명, libcamera 함수, 저장소 호스트와 로컬 모델 이름은 공통 작성 프롬프트에 넣지 않았습니다. 사내 템플릿에도 같은 선택을 제공하며 LLM 연결과 질문·근거는 해당 환경에서 바꿉니다.

짧은 프롬프트에서도 원문 인용, 분할 질문 ID, 필수 용어와 알려진 오류, 재시도, 저장 원고·내보내기 검사는 유지합니다. 페이지의 제목·구조·근거 링크는 생성기가 만들고 집필 규칙은 최종 원고 검토에 계속 적용합니다. 스타일 파일 또는 작성 프롬프트가 바뀌면 기존 답변의 재사용 지문이 바뀝니다. 모델의 답을 사람이 다시 쓴 문서로 바꾸어 시험 성공으로 세지 않습니다.

## 시험 입력과 평가 기준

공식 upstream은 `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`로 확인했으며 새 커밋은 없었습니다. Ollama의 `qwen3.5:9b` Q4_K_M, temperature 0.1, think false, num_ctx 16384, 출력 한도 1500, 재시도 1회를 사용했습니다. 각 실행은 새 출력 폴더에 질문 설정, 생성 코드 해시와 실제 HTTP 요청·응답을 보존합니다.

자동 검사와 작성자의 소스 대조를 따로 기록합니다. 소스 대조는 각 답의 주체, 전제, 의무·가능성, 부정, 성공·실패 반환, 호출 순서, 수명과 측정 범위를 확인합니다. 표현이 자연스럽다는 이유로 조건 누락이나 과장을 허용하지 않습니다. 작성 세션의 대조는 독립 평가나 사람 승인이 아닙니다.

최종 시험과 공개 반영 결과는 이 기록에 이어서 남깁니다.
