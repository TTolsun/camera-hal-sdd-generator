# 로컬 9B의 정확한 Vendor 문서 작성 시험

**질문과 근거를 책임 단위로 나누고 실제 Qwen 응답을 소스와 대조했습니다.** 공개 libcamera 입력의 시험이며 사내 HAL이나 사내 모델의 검증 결과가 아닙니다. 이전 [차단 중심 시험](vendor-9b-retest.md)과 [PR #84의 실제 개요 생성·소스 변경 시험](../qwen-overviews.md)을 구분해 보관합니다.

## PR #84에서 유지한 경로

PR #84는 로컬 `qwen3.5:9b`로 Vendor·Developer 개요를 작성하고, 요청 한도 `32 → 16 → 32` 변경에 운영용 `sdd update`를 실행했습니다. 이번 변경은 그 두 개요, 큐 한도 설명과 원응답 증빙을 보존합니다. 남은 Vendor 연동·지원 문서에 같은 표준 프롬프트, 책임별 질문, 한 문장 답변 방식을 적용합니다.

C++ 연산자·템플릿을 허용하는 JSON 스키마, 질문 속 코드 식별자의 서식 처리와 그림을 제외한 원고 대조도 PR #84의 구현을 유지합니다. 그림은 질문별 설명 가까이에 두고, 바뀐 발췌에 연결된 요소만 원문을 다시 대조해 연결했습니다.

## 남은 실패 원인과 수정

| 실제 응답에서 확인한 문제 | 질문·근거·작성 경로의 수정 |
|---|---|
| 호출자의 의무만 쓰고 반환 구성의 스트림·기본 파라미터를 생략 | 의무와 반환 정보는 서로 다른 질문과 근거 유형으로 작성합니다. 한 답변 전체에 의무형을 강제하지 않습니다. |
| 스레드 안전성 또는 카메라 상태 변경 금지를 생략 | 호출 스레드·안전성 질문과 상태 변경 질문을 나누고 각각 답변을 요구합니다. |
| configure의 추가 검증 금지만 쓰고 사용자 정의 필드 활용을 생략 | 검증 의무와 허용된 필드 활용을 분리합니다. |
| completeBuffer 호출 의무만 쓰고 내부 추적 갱신을 생략 | 호출자의 책임과 공통 함수가 수행하는 동작을 나눕니다. 마지막 버퍼 완료와 명시적인 요청 완료 의무도 모두 같은 주제에 남깁니다. |
| match 실패 처리를 acquire 함수의 책임으로 오인 | 담당 함수의 범위를 함께 제공하고 아직 확보하지 않은 장치·이미 확보한 장치·실패 반환을 묻습니다. |
| Adjusted의 변경 가능성을 단정하거나 호출자 확인을 생략 | 상태·변경 범위와 호출자 확인 의무를 나누며 any/may의 범위를 대조합니다. |
| 하나의 stop 제어 흐름을 여러 인용 ID로 합쳐 잘못된 JSON 생성 | 범위를 지정한 발췌는 빈 줄로 자르지 않고 하나의 인용 ID로 제공합니다. 루프·ASSERT·초기화는 원문 그대로 남깁니다. |
| stopDevice 답변에 근거 없는 버퍼 수명 의무가 삽입 | 공통 프롬프트의 버퍼 수명 예시가 그대로 복사된 것을 확인하고 그 사실 예시를 제거했습니다. |
| 프록시 종류를 잘못된 C++ 포인터 반환형으로 재작성 | 프록시를 생성하는 람다를 별도로 발췌하고 객체 종류와 최종 반환 단계를 구분해 묻습니다. |
| 동일한 반환·스레드 문구 때문에 다른 함수를 선택하거나 근거 수집 실패 | `sources[].scope`로 해당 함수 안에서만 유일한 시작·끝 문자열을 찾습니다. |
| 마지막 버퍼 완료와 명시적 요청 완료를 한 발췌에서 읽고 이유를 반대로 설명 | 질문별로 직접 답하는 절을 선택하되 함수 범위와 원문 위치를 함께 검증합니다. |
| 대기 요청 분리와 장치 정지 후 취소를 섞어 순서를 바꿈 | 호출 순서, 분리 이유, 정지 후 취소 경로, 마지막 ASSERT를 별도 질문으로 나눕니다. |
| 정확한 접근 금지 계약을 `limitation`으로 분류해 필수 답변 검사에서 실패 | 필수 답변 한 개를 받는 스키마는 검증기가 허용하는 `behavior`만 제시합니다. 금지 계약 자체를 불확실한 내용으로 취급하지 않습니다. |

짧은 프롬프트 비교도 수행했습니다. 같은 질문·근거·스키마의 세 사례에서는 짧은 지침이 완료 통지·취소·Invalid 조건을 더 잘 설명했지만, 전체 문서에서는 누락과 주체 혼동이 계속됐습니다. 질문을 근거 뒤에 놓은 비교도 일부 사례를 개선했으나 전체 성공을 보장하지 않았습니다. 따라서 `focused`는 비교용 선택지이며 공개 예제와 사내 템플릿의 기본값은 `standard`입니다.

## 실제 비교 기록

각 실행은 새 폴더에서 질문 사본, 코드 해시, 원요청·원응답과 HTTP 영수증을 보존합니다. 다음 표의 자동 통과는 인용·구조·용어 검사 결과이며 의미 정확도 점수가 아닙니다. 실행마다 질문이나 근거가 달라 서로 같은 모집단의 성공률로 합산하지 않습니다.

| 실행 | 자동 통과 | 관측 결과 |
|---|---:|---|
| focused1 / focused2 / focused3 / focused4 | 문서 1/3, 0/3, 1/3, 1/3 | 짧은 지침, 문장 길이 지시, 근거 축소, 질문 순서를 비교했으나 전체 작성은 실패했습니다. |
| diagnostic1 | 독립 질문 21/30 | 주체·적용 범위 혼동과 복합 질문 누락을 확인했습니다. 실패 두 건은 모호한 근거 선택이어서 모델 호출 전에 중단됐습니다. |
| focused-final1 / focused-final2 | 문서 각각 1/3 | 함수 문맥과 전체 발췌를 제공해도 조건 누락이 남았습니다. 폴더 이름의 final은 당시 실행 이름이며 최종 채택을 뜻하지 않습니다. |
| focused-thinking | 개별 질문 3개 비교 | 추론을 켜도 match의 주체 혼동이 남았습니다. 전체 문서 성공 시험이 아닙니다. |
| pr84-standard1 | 문서 1/2 | 지원 문서가 자동 통과했으나 Adjusted의 any 범위를 all로 확대하는 표현이 남았습니다. |
| cpu-comparison | 같은 요청 3개 비교 | 연동 순서는 완전해졌지만 다른 조건은 여전히 빠졌습니다. 실행 장치만 바꾸면 해결된다고 결론 내리지 않습니다. |
| pr84-cpu1 | 문서 1/2 | 반환 순서 누락과 허용을 의무로 바꾸는 표현을 확인했습니다. 출력 한도 증대만으로 해결되지 않았습니다. |
| pr84-cpu2 | 문서 1/2 | 모듈 조회 인자와 실패 반환을 함께 물었을 때 `nullptr`가 누락됐습니다. 질문을 분리했습니다. |
| pr84-repaired2 | 문서 1/2 | 실제 HTTP 응답 31회를 재사용하고 13회를 새로 호출했습니다. 정지 순서와 이유를 더 좁혀 물어야 했습니다. 전체 신규 생성 성공으로 세지 않습니다. |
| pr84-repaired3 | 문서 1/2 | 요청 접근 금지 계약의 내용은 맞았으나 `limitation` 분류가 반복됐습니다. 스키마와 검증 규칙의 모순을 제거하고 전체 신규 시험을 시작했습니다. |

PR #84와 같은 CPU 전용 loopback 서버도 시험했습니다. 기존 서버를 바꾸지 않고 동일한 로컬 모델 digest를 사용했습니다. CPU/GPU 비교는 세 요청의 관측이며, 낮지만 0이 아닌 temperature를 사용했으므로 차이를 장치의 인과 효과로 단정하지 않습니다. 모델 digest는 `6488c96fa5faab64bb65cbd30d4289e20e6130ef535a93ef9a49f42eda893ea7`입니다.

## 공통 생성기와 사내 적용

`sources[].scope`는 프로젝트별 함수·클래스 이름을 공통 코드에 넣지 않는 범위 선택 기능입니다. 선택 범위가 없거나 모호하면 실패하고 다른 함수로 대체하지 않습니다. 선택한 원문과 줄 번호·해시를 검증하며, `scope`가 있는 근거는 표준·집중 프롬프트 모두 한 인용 단위로 제공합니다. 괄호나 제어 흐름을 자동 해석하는 기능은 아니므로 바깥 조건과 실패 분기를 직접 확인해야 합니다.

`review.design_prompt: focused`를 비교할 때는 프로젝트의 `focused-design-system.md`를 사용합니다. 최종 집필 규칙과 원문 인용·분할 질문·답변 계약·저장 원고 검사는 유지하며, 스타일 또는 작성 프롬프트 변경은 기존 집중 작성 답변의 재사용을 무효화합니다. 제품명·소스 경로·모델 연결은 프로젝트 설정에 둡니다.

사내 적용 때는 [질문 작성과 모델 시험 절차](../../inhouse/contract-authoring.md#사내-llm-생성-시험)에 따라 실제 HAL 근거와 모델로 다시 시험해야 합니다. 작성 세션의 소스 대조는 독립 평가나 사람 승인이 아닙니다. 모델 답변을 사람이 고쳐 쓴 결과를 9B 생성 성공으로 세지 않으며, 코드 계약을 실기기 성능·지원 보장으로 확대하지 않습니다.

`sdd.repair_reader`는 같은 소스 커밋의 시험을 보완하는 명시적인 경로입니다. 원요청·원응답 해시, 모델과 설정이 일치하는 HTTP 기록만 재사용하고 질문·근거·프롬프트·응답 스키마가 바뀐 요청은 실제 모델에 다시 보냅니다. 재사용 전송과 HTTP 원본을 따로 기록하며, 서로 다른 응답이 같은 요청 해시로 저장돼 있으면 임의로 선택하지 않고 실패합니다. 전체 모델 재시험은 `sdd.evaluate_reader`로 별도 수행합니다.

## 최종 원고의 출처 확인

실제 응답과 배포 원고를 대조하는 `examples/libcamera/verify_vendor_trial.py`는 요청·응답·질문 설정·원고 해시와 인용을 확인합니다. 허용하는 본문 차이는 코드 식별자의 백틱 서식뿐입니다. 문장을 수동 수정하고 원고 해시만 다시 계산해도 원응답 대조에서 실패합니다. 이 검증기 역시 자연어 의미의 정확성이나 사람 승인을 판정하지 않습니다.
