# Vendor의 채택·연동 판단을 위한 개요 검토

**Vendor 개요에서 기능·강점·연동 순서·제약을 먼저 확인하고, 구현 계약으로 이동합니다.** 공개 libcamera 소스 `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`를 대상으로 검토했습니다. 사내 HAL이나 실제 장치 시험 결과가 아닙니다.

## 발견한 누락과 반영

기존 개요는 하드웨어 매칭·설정·요청·IPA·정지·검증의 여섯 질문에 답했습니다. 상세 문서에는 소유권과 실패 조건이 있었지만, 제공 기능과 강점, 전체 연동 순서, 지원 판단 기준을 먼저 설명하는 필수 질문이 없었습니다. 사이트 첫 화면도 처음 읽는 개발자의 코드 탐색을 우선했습니다.

| Vendor가 판단할 내용 | 추가한 설명과 근거 |
|---|---|
| 제공 기능 | `Camera`의 스트림 설정·제어·캡처와 장치별 `PipelineHandler` 구현·등록 의존성을 설명합니다. |
| 강점 | 공통 준비 대기·제출 순서·장치 요청 한도·실패 취소·정지 추적을 설명하고, 장치 구현자의 완료 통지 책임을 유지합니다. |
| 연동 방법 | 카메라 확보부터 해제까지의 사용 순서와 장치 매칭·등록 구현 책임을 구분합니다. 상태 변경 동기화는 호출자 책임입니다. |
| 제약 | 구성 검증의 `Valid`·`Adjusted`·`Invalid`, 스트림 변경·삭제 가능성, 요청 용도를 만족하지 못할 때의 null 반환을 설명합니다. |

기능 존재를 성능 우위나 모든 장치 지원으로 바꾸지 않습니다. 실측 성능·지원 기종·제품 완성도는 이 근거로 보장할 수 없습니다. 미확인 항목을 미지원으로 단정하지도 않습니다.

## 공통 기능과 사내 적용

`vendor-overview`는 네 관점과 기존 다섯 구현 관점을 검사합니다. 기존 `vendor`는 상세 계약용으로 보존합니다. 개요의 LLM 프롬프트에도 강점의 구현 근거와 조건, 제공 측과 Vendor의 책임 구분을 요구합니다. CLI와 impact schema 1은 유지합니다.

사내 템플릿과 공개 mini HAL은 같은 프로필을 사용합니다. 템플릿의 근거·답변은 비워 두어 실제 소스를 연결하기 전에는 생성이 실패합니다. mini HAL에서는 요청 관리 구조의 이점과 미완성 오류·종료 처리를 함께 설명합니다. 빌드 시스템·코드 호스트·모델·정적 자산·게시 대상은 기존 프로젝트 설정으로 교체합니다. 사내 기능과 지원 범위는 실제 소스·제품 구성·시험 결과를 제공받아 채워야 합니다.

## 분량과 검토 한계

기존 여섯 구현 질문을 삭제하지 않고 네 채택 질문을 앞에 추가하면서 개요의 산문이 4,922자에서 7,889자로 늘었습니다. 증가율 검사에서 검토 대상으로 중단된 뒤, 추가 내용과 상세 문서 연결을 검토했습니다. 개요에만 증가율 1.7과 절대 산문 한도 8,500자를 함께 설정했습니다. 다른 페이지의 한도·중복 검사·근거 검사는 유지합니다. 이 수치는 독자의 이해도를 측정한 결과가 아닙니다.

원고는 현재 Codex 세션이 실제 발췌를 읽고 작성한 LLM 응답을 입력 해시와 묶어 생성합니다. 소스 해시·인용·질문 연결·문서 형식 검사는 설명의 의미를 승인하지 않습니다. 작성자의 소스 대조와 실제 Vendor의 읽기 시험, 사람 승인, 실기기 검증은 별개이며 후자의 검증은 수행하지 않았습니다.
