# #163 진행자용 채점 기준

참여자에게 과업 전에 이 문서를 보여 주지 마세요. 측정할 공개 build_id와 URL이 확정된 뒤 시작하며, 아래 내용이 그 빌드에도 그대로 근거와 함께 있는지 먼저 확인합니다. 실제 수행 없이 성공·시간·부담 점수를 채우지 않습니다.

| 과업 | 무설명 완료로 인정할 내용 | 인정하지 않을 답변 |
| --- | --- | --- |
| index | ‘처음 읽는 개발자의 순서’에서 처음 열 문서를 찾고, 이어서 요청 제출·완료를 따라갈 문서 또는 절로 이동합니다. 선택 이유와 실제 방문 URL을 기록합니다. 시스템 개요·CameraManager 진입점은 기준 페이지의 예이며, 참여자 과업에 없는 추가 API 이름을 말하지 않았다는 이유로 감점하지 않습니다. | 제목만 짐작해 말하거나, 작성자의 설명을 듣고 이동한 경우입니다. |
| overview | createRequest가 반환하는 요청의 소유자·삭제 책임이 호출자에게 있음을 찾습니다. 같은 요청을 다시 큐에 넣기 전에 Request::reuse를 호출해 상태를 초기화한다는 계약과 근거를 찾습니다. | 요청 제출 직후 자동 삭제되거나, 완료 전 재사용해도 된다고 답하는 경우입니다. |
| vendor-overview | 공통 libcamera 프레임워크가 맡는 카메라 제어/API와, 장치별 파이프라인 핸들러 구현의 하드웨어 연동 책임을 구분합니다. 실제 장치 지원이 해당 구현·필요 장치 확보에 달려 있음을 찾습니다. | 모든 기기의 지원·성능이 공통 API만으로 보장된다고 확대하는 경우입니다. |
| vendor-assurance | 내장 벤치마크가 통계 수집과 디베이어 처리 시간을 측정하며 프레임 캡처·출력 시간은 포함하지 않음을 찾습니다. | 수치를 만들어 내거나 전체 촬영 지연·기기 성능 실측으로 해석하는 경우입니다. |
| vendor-integration | 마지막 버퍼 완료가 요청의 자동 완료가 아님을 찾습니다. 파이프라인 핸들러가 completeRequest를 명시적으로 호출해야 하며 해당 호출의 CameraManager 스레드 계약을 찾습니다. 문서 또는 소스 발췌를 근거로 제시합니다. | completeBuffer만으로 요청이 끝난다고 하거나, 호출 문맥을 스레드 안전성 보장으로 확대하는 경우입니다. |
| queue_request | 주요 확인 지점에서 Camera가 요청을 넘기는 PipelineHandler::queueRequest를 찾고 예약된 호출 표기를 설명합니다. 이 정적 목록만으로 시간 순서·모든 실행 경로·실제 실행 스레드를 확정할 수 없음을 찾습니다. | 장치별 queueRequestDevice 구현이 이 화면에서 실제 실행됐다고 단정하거나, 화살표를 시간 순서의 증거로 사용하는 경우입니다. |

답은 위 문장과 바이트 단위로 같을 필요가 없습니다. 조건·주체·시점의 의미와 유효한 근거가 맞아야 합니다. 참여자 답변을 실제로 읽고 `correct`를 판정하며, 도움을 받았으면 정확해도 `completed_without_help=false`로 기록합니다. 막힌 이유와 주관적 읽기 경험은 원문 그대로 남깁니다. 사람 검토 전 표시나 별도 #150 승인 상태는 이 과업 채점으로 바꾸지 않습니다.

동일 참여자에게는 정해진 2과업을 모두 시행합니다. 누락·중단·도움 과업도 분모에서 빼지 않습니다. 최종 통계는 실제 제출된 최소 6과업에서 무설명 성공 5개 이상, 읽기 부담(5=낮은 부담) 중앙값 4 이상인지 계산합니다. 이 채점 기준을 준비했다는 사실은 실제 사람이 수행했다는 증거가 아닙니다.
