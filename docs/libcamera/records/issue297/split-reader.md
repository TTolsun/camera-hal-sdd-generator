## 최종 판정 근거

### Q1

- ① Running 상태와 제출 검사, 0 반환의 의미, requestCompleted를 통한 요청 완료 및 선행 Pending 요청에 따른 반환 지연을 설명했다.
- ② 버퍼 완료와 요청 완료를 구분하고, 정상 경로의 통지·pending 갱신·역참조 해제 순서와 명시적 completeRequest 호출을 설명했다. 요청 상태와 프레임 상태를 구분하고 실패·취소된 데이터의 유효성도 제시했다.
- ③ 앱의 요청 소유와 버퍼 참조, raw 포인터의 수명 한계, 직접·지연 수신자와 외부 소비자의 마지막 사용, stop 반환의 한계를 설명했다.
- ④ 기본 reuse와 ReuseBuffers의 맵 처리 및 RequestPending 설정을 실제 코드 행에 연결했다. 타임아웃 후 남은 펜스의 회수와 addBuffer의 -EEXIST 분기도 설명했다.
- ⑤ 소스 계약과 구현에 따른 수신 순서, 검증 계획과 실제 관측을 구분하고 플랫폼별 DMA 동기화의 미확인 범위를 밝혔다.
- ⑥ 제공된 소스 창의 파일과 행을 주요 판단에 연결했고, 완료·반환과 재사용 그림의 주요 분기를 사용했다. 지정된 일곱 tail 값도 모두 제시했다.

### Q2

- ① 같은 제출 회차를 식별해 API 시작·반환·게시·파이프라인 진입을 연결하고, 0의 의미와 진입 여부에 따른 다음 조사를 제시했다.
- ② 준비 성공과 timeout 취소, 장치 제출 실패, DQBUF 실패와 예상 밖 인덱스, 프레임 오류 및 정지와 겹치는 경우를 구분했다.
- ③ 요청과 버퍼의 수명, 제출 및 FIFO 반환 순서, 재귀 호출, 동시 게시와 신호 수신의 관계를 설명했다.
- ④ 준비 큐와 장치 한도, fence·timer, UVC 제어와 QBUF·DQBUF, 명시적 요청 완료 및 앱 수신까지 함수와 관측값, 다음 행동을 연결했다.
- ⑤ API 반환 계약과 구현, 공통 경로와 UVC 사례, 검증 계획과 실제 관측을 구분했으며 300ms를 준비 호출의 인자로 제시했다.
- ⑥ 제공된 검증 소스 창의 파일과 행을 근거로 사용했고, 판단에 사용한 그림의 분기를 본문과 일치하게 설명했다. 열 페이지의 끝값도 모두 제시했다.

### Q3

- ① 미완료 요청, 버퍼 수명과 콜백 순서의 위험에 직접 답했습니다. 공개 정지 계약과 호출자의 상태 변경 동기화 의무를 제시했습니다.
- ② 비실행·접근 실패·정상 정지 경로, 대기 요청 취소, UVC STREAMOFF 성공과 실패, 연결 해제 예외를 구분했습니다. UVC 실패 후 정리되지 않은 요청과 후속 접근 위험도 조건부로 설명했습니다.
- ③ 대기 큐 분리와 장치 요청 처리 순서, 요청의 내부 완료와 제출 순서에 따른 앱 반환, Direct와 Queued 수신, 포인터의 마지막 사용과 재사용 경계를 구분했습니다. 직접 콜백의 버퍼 재연결 위험은 request.cpp:492–499와 기존 요청의 역참조 해제 행에 연결했습니다.
- ④ 실제 큐 등록·완료·신호 발생 행을 근거로 회차별 버퍼와 요청의 신호 및 콜백 횟수를 집계하고 순서를 비교하는 계획을 제시했습니다. 대기·장치 요청 혼합, UVC 오류 주입, 직접·지연 수신과 수명 검증에도 조건과 관측값, 판정 방법이 포함됩니다.
- ⑤ 공개 API 계약, 구현의 상태 및 오류 분기, 조건부 캐시 접근 위험, 앞으로 수행할 시험을 구분했습니다. 장치 오류가 정상 정리나 안전한 재시작을 뜻한다고 단정하지 않았습니다.
- ⑥ 필수 코드 판단에 독해 제공 창에서 실제 확인된 파일과 행을 연결했습니다. Blocking 분기, UVC의 버퍼 알림에서 요청 완료까지의 경로, DQBUF 실패·큐 조회·캐시 접근, 메시지 dispatch 행이 포함됩니다. 제시된 그림의 대기·장치 정지 순서와 지연 수신 경계도 본문과 일치하며, 지정된 모든 페이지의 TAILS가 답변에 있습니다.
