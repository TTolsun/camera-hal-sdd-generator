# 공개 libcamera SDD 실무 질문의 깊이와 평가 비용

세 질문 모두 별도 Codex CLI 읽기와 소스 근거 검토를 받았습니다. 읽기 답변 세 건은 각각 필수 조건을 빠뜨렸습니다. 공개 문서에서 확인한 보완 범위는 Q1의 펜스 그림과 Q2의 제출 회차 연결입니다. Q3는 검토한 공통 및 UVC 범위에서 기술 보완을 요구하는 오류를 확인하지 못했습니다. [이슈 #297](https://github.com/TTolsun/camera-hal-sdd-generator/issues/297) · [관련 기술 보완 #252](https://github.com/TTolsun/camera-hal-sdd-generator/issues/252)

## 질문별 판정

| 질문 | 실제 읽기 답변 | 공개 문서와 남은 범위 |
| --- | --- | --- |
| Q1. 제출 뒤 완료를 어떻게 판단하고 언제 버퍼를 재사용할 수 있나요? | 접수와 `requestCompleted`, 마지막 버퍼와 요청 완료, 지연 수신자와 펜스 회수를 구분했습니다. 버퍼별 상태에 따른 데이터 유효성, 기본 `reuse()` 뒤 재연결, 남은 펜스의 `-EEXIST`를 빠뜨렸습니다. | 프레임 상태 설명은 실제 사이트의 UVC 절에 있습니다. 그 절은 초기 읽기 입력에서 빠졌습니다. `camera-requests`의 그림은 펜스 회수 뒤 바로 재사용할 수 있는 것처럼 표현합니다. `request-lifecycle`의 대응 그림처럼 회수가 선행 조건임을 명시할 필요가 있습니다. |
| Q2. 제출 성공 뒤 완료가 오지 않으면 어디부터 어떤 값으로 조사하나요? | 파이프라인 진입, 준비와 큐 한도, 장치 제출, FIFO와 콜백 전달을 추적했습니다. 요청 객체를 재사용했을 때 각 관측을 같은 제출 회차에 연결하는 방법을 찾지 못했습니다. | 기존 문서는 논리적 회차로 완료 함수 진입과 앱 통지를 비교합니다. 동시 제출 조사도 API 호출, 게시, 파이프라인 진입 및 등록을 관찰하도록 안내합니다. 이 둘을 연결해 API 시작·반환과 파이프라인 진입을 동일 회차로 기록하는 방법이 필요합니다. 보충 검토에서 fence timeout과 UVC QBUF의 실패·등록 경계를 소스로 확인했습니다. |
| Q3. 정지·취소를 바꿀 때 어떤 위험과 회귀 조건을 검증하나요? | 두 큐, 재진입, 중복·누락, 지연 수신자의 마지막 사용을 설명했습니다. `Camera::stop()`의 세 분기, UVC 정상·실패 반환 경로, 동시 제출 조건을 모두 연결하지 못했습니다. | 문서가 세 분기와 공통/UVC 정지 조건을 설명합니다. 보충 검토에서 STREAMOFF가 실패하면 버퍼 반환 루프에 도달하지 않는 점과 `stopDevice()`가 반환해야 공통 대기 요청의 취소가 이어지는 점을 확인했습니다. 연결 해제 TODO의 세부 근거와 타 파이프라인은 이번 판정 범위 밖입니다. |

- Q1에서 검토한 그림은 접수와 완료, 버퍼와 요청 완료, 지연 수신의 수명, 펜스 회수입니다. 프레임 상태 설명과 펜스 그림의 차이는 실제 페이지에서 확인할 수 있습니다. [프레임 상태](https://ttolsun.github.io/libcamera-sdd/request-lifecycle.html#qbuf-호출-전-실패와-cache-반환) · [카메라 요청의 펜스 그림](https://ttolsun.github.io/libcamera-sdd/camera-requests.html#타임아웃-뒤-펜스-회수) · [수명 문서의 펜스 그림](https://ttolsun.github.io/libcamera-sdd/request-lifecycle.html#타임아웃-뒤-펜스-회수)
- Q2에서 준비 여부와 큐 한도, 장치 제출, FIFO 반환 그림의 주요 분기를 대조했습니다. 초기 검토는 완료 절에 있는 회차 계획을 읽지 못했습니다. 보충 검토에서 계획이 이미 있다는 사실과 진입까지 연결할 지침이 빠졌다는 사실을 확인했습니다. [동시 제출의 관찰 경계](https://ttolsun.github.io/libcamera-sdd/request-lifecycle.html#동시-제출의-순서를-관찰할-경계) · [제출 회차별 완료 기록](https://ttolsun.github.io/libcamera-sdd/request-lifecycle.html#제출-회차별-완료-기록의-비교-계획)
- Q3에서 대기 요청 분리, 버퍼별 취소, UVC 정지, 지연 수신 그림을 비교했습니다. 평가 자료에 Mermaid 원문을 포함한 그림만 판정했습니다. [공통 정지의 호출 순서](https://ttolsun.github.io/libcamera-sdd/scenarios/camera_stop.html#장치-종료-뒤-대기-요청을-취소하는-순서) · [UVC 성공과 실패](https://ttolsun.github.io/libcamera-sdd/request-lifecycle.html#uvc-정지의-정상-경로와-실패-경계)

독립 읽기는 문서와 문서가 제공하는 근거에 한정했습니다. Q1의 첫 실행에서는 Windows Codex CLI 하위 셸이 열리지 않았습니다. 재시도에서는 HTML 본문과 일부 그림을 텍스트로 전달했습니다. Q2와 Q3에는 문서가 직접 연결한 코드의 일부도 넣었습니다. 직접 클릭해 소스를 여는 동작까지 수행한 읽기 실행은 없었고, 짧은 발췌 일부는 핵심 분기 앞에서 잘렸습니다. 별도 검토에 더 넓은 공식 소스 창을 제공하고 공개 코드 파일 10개의 바이트를 공식 upstream과 비교했습니다. 이 검증은 읽기 실행 당시의 탐색 성공을 대신할 수 없으므로 독립 읽기 통과는 0건으로 기록합니다.

## 시간과 토큰

시간은 CLI 프로세스의 경과 시간과 질문 착수부터 마지막 판정까지의 벽시계를 기록했습니다. Q2와 Q3는 일부 호출이 겹쳤습니다.

| 질문 | 실패 | 유효 읽기 | 초기 근거 검토 | 보충 근거 검토 | CLI 합계 | 질문 벽시계 | 입력 | 출력 | 입력+출력 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Q1 | 16.656초 | 26.031초 | 52.485초 | 0초 | 95.172초 | 5분 40초 | 176,927 | 4,365 | 181,292 |
| Q2 | 0초 | 35.219초 | 45.625초 | 18.563초 | 99.407초 | 3분 56초 | 156,340 | 4,866 | 161,206 |
| Q3 | 0초 | 44.172초 | 47.985초 | 18.359초 | 110.516초 | 3분 56초 | 143,574 | 5,429 | 149,003 |
| 합계 | 16.656초 | 105.422초 | 146.095초 | 36.922초 | 305.095초 | — | 476,841 | 14,660 | 491,501 |

- 공통 준비는 4분 59.7초였습니다. 준비 시작부터 마지막 독립 판정까지는 15분 33.1초였습니다. 여기에는 질문별 입력 정리와 검토 창 보충도 포함됩니다. 사람의 직접 작업 시간, 금액, 기기 실행 시간은 계측하지 않았습니다.
- Q1에서 독립 읽기 재시도와 근거 검토는 78.516초, 84,422토큰을 사용했습니다. 첫 호출의 프로세스는 정상 종료됐지만 문서를 읽지 못해 평가 실패로 기록했습니다. 이 호출에서 96,870토큰을 사용해 Q1 점검선인 180,000토큰을 1,292토큰 넘겼습니다.
- 총 9회는 모두 새 CLI 호출입니다. 이전 #252의 검토와 동일 공개 빌드 사용은 신규 추출·원고 생성으로 집계하지 않았습니다. 새 원고·수정·번역·사이트 빌드·배포에 따른 호출은 0회입니다. Q1 점검선에 도달했고 Q2에 남은 18,794토큰으로는 관측한 호출 규모의 생성과 독립 재평가를 함께 계획하기 어려워 원고 수정은 보류했습니다.
- 합계는 단일 `turn.completed`의 `input_tokens + output_tokens`입니다. 캐시 입력 187,264토큰은 입력에, 추론 출력 723토큰은 출력에 포함됩니다. `cache_write_input_tokens`는 9개 원본 이벤트에서 모두 0입니다. 실패 호출에도 같은 원본 계측을 적용했습니다. 통과당 비용은 통과가 0건이므로 계산하지 않았습니다.

## 고정 입력과 재현 방법

- 공식 libcamera HEAD와 공개 문서가 연결한 소스는 `c19d05128f3ae1f0ebe63acb4deaca9fbb1dde78`입니다. 시험 도구의 생성기 기준은 `0a05a886d7951d09002087c425a26ff0b3ec9074`입니다. [공식 소스 커밋](https://gitlab.freedesktop.org/camera/libcamera/-/commit/c19d05128f3ae1f0ebe63acb4deaca9fbb1dde78)
- 실제 Pages 배포 커밋은 `efad8548dbf2bdd8427e0e7ac935f2a5878b71fe`이며 build ID는 `c92c121a77e3756c9a10d7813fe71bb517d70c1d020b501f8c56fc54222a63ea`입니다. 사용한 15개 공개 HTML을 manifest와 바이트 단위로 대조했습니다. facts·설정·집필 규칙·원고 지문과 15개 출력 해시를 기록했습니다. [배포 실행](https://github.com/TTolsun/libcamera-sdd/actions/runs/43123178634) · [고정 manifest](https://github.com/TTolsun/libcamera-sdd/blob/efad8548dbf2bdd8427e0e7ac935f2a5878b71fe/docs/site-manifest.json) · [공개 manifest](https://ttolsun.github.io/libcamera-sdd/site-manifest.json)
- [실행 증거](evidence.zip)의 `frozen-plan.md`에는 고정 질문과 상한이 있습니다. `run.json`과 `index.json`에는 시간·입력·출력 지문이 있습니다. 질문별 소스 정답 기준, 검토 창, 실제 읽기·근거 검토의 6개 항목별 판정과 원본 토큰 이벤트를 함께 보존했습니다. CLI 버전은 `0.167.0-alpha.4.1`, 모델은 `gpt-6.1-terra`, reasoning effort는 `high`입니다. 각 호출은 독립 프로세스이며 작성자 대화는 전달하지 않았습니다. 독립 읽기와 근거 검토는 같은 모델 계열을 사용했습니다.
- 유효한 호출을 다시 시험하려면 새 작업 폴더에 아카이브의 `call.py`와 `prompts/`만 복사한 후 `python call.py Q2-baseline-bundle-reader`처럼 실행 이름을 지정합니다. 각 입력에는 당시 제공한 자료가 들어 있습니다. 첫 하위 셸 실패를 재현하려면 고정 문서의 15개 HTML을 내려받아 manifest로 확인한 뒤 `render.py`의 텍스트를 읽기 전용 작업 폴더에 놓고, 해당 호출의 영수증에 기록된 CLI 인자를 사용합니다. 실행 기록의 계정별 절대 경로는 파일 배포를 위해 일반화했습니다. 현재 조건의 실행 시간과 응답에는 변동이 있을 수 있습니다.

## 후속 범위

#252의 후속 범위에 펜스 회수 그림과 동일 회차의 제출·파이프라인 진입 관측을 남깁니다. 먼저 문서 안에서 관련 절을 찾고 실제 근거의 분기까지 읽을 수 있는 시험 입력을 고정해야 세 질문을 같은 조건으로 비교할 수 있습니다. 자동 평가만 수행했으므로 실제 개발자 효과와 사내 HAL의 깊이·비용은 미측정입니다. 이 기록은 공개 원고·생성기 런타임 입력을 수정하지 않으므로 Pages 배포를 수반하지 않습니다.
