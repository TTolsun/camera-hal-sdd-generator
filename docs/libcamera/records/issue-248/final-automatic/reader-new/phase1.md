## 원본 답변

### B1

처음에는 For Developer의 시스템 개요를 선택한다. CameraManager 진입점에서 전체 구조를 본 뒤 한 요청을 따라가라는 안내가 내 과업과 맞기 때문이다. 다음에는 overview의 요청 제출과 완료 절을 고른다. 이 절은 최소 한 개 버퍼를 붙여 queueRequest로 제출하고 requestCompleted로 끝을 확인하는 경로를 보여 준다.

### B2

createRequest로 받은 Request의 소유자와 삭제 책임자는 호출자다. 같은 요청을 다시 제출하기 전에 Request::reuse()로 상태와 연결된 컨트롤을 초기화해야 한다. 기존 버퍼를 계속 쓰려면 ReuseBuffers를 지정하고, 지정하지 않으면 버퍼 맵을 비우므로 버퍼를 다시 연결해야 한다.

### S_pre_reopen

queueRequest가 성공했다는 것은 요청을 접수했다는 뜻이다. 요청이 끝나 애플리케이션에 돌아왔다는 뜻까지 포함하지 않는다. 완료는 나중의 requestCompleted 신호로 따로 확인해야 한다. 그러므로 성공 반환만 있고 신호가 없다는 관측으로 촬영 완료를 단정할 수 없고, 접수 이후 완료 통지까지의 경로를 조사해야 한다.

### S_post_reopen

재열람한 근거가 재열람 전 설명과 일치한다. 0 반환과 requestCompleted는 별개의 관측이다.

### R_phase1_memo

과업이 준 관측은 제출 함수의 성공 반환과 완료 알림 미관측뿐이다. 실제 실행 기록은 없다. 문서에서 0 반환은 queued 호출 예약 성공이고 요청 완료는 아니라는 점을 확인했다. 제출·대기/준비·장치 전달·버퍼 완료·명시적 요청 완료·제출 순서 반환이라는 조사 후보 경로를 읽었다. 어느 단계까지 갔는지는 아직 모른다. 다음에는 request-lifecycle에서 보이는 구성과 요청 오류 조사 링크 중 실패 위치별 확인 순서로 이동해, 완료 누락을 조사할 관측 항목과 분기를 찾겠다. 뒤 요청이 먼저 완료되더라도 앞 요청 때문에 반환이 기다릴 수 있다는 제출 순서 조건도 별도 후보로 남긴다.
