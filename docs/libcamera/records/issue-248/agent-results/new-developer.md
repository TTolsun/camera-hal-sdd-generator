## S — 보지 않고 쓴 설명(근거 재조회 전)

현재 도구로 문서를 다시 읽지 않고 직전 독해를 바탕으로 작성한다. `queueRequest()`의 성공은 요청을 제출하는 작업이 받아들여졌다는 결과다. 촬영 처리가 끝나 애플리케이션으로 요청이 돌아왔다는 뜻은 아니다. 종료 여부는 별도의 `requestCompleted` 통지로 확인해야 한다. 버퍼 하나의 완료와 요청 전체의 완료도 구분한다. 모든 버퍼가 끝났더라도 파이프라인은 요청 완료 함수를 명시적으로 호출해야 한다. 그러므로 0 반환만 있고 통지가 없다면 완료 원인을 확정하지 말고 후속 단계의 도달 여부를 조사해야 한다.

이 '보지 않고'는 도구 재조회 중단을 뜻한다. 대화 문맥과 직전 도구 결과가 유지되는 자동 에이전트이므로 사람의 기억 회상을 측정한 것이 아니다.

## R — 완료 누락 조사 자유 메모(조회 중단 전)

메모 시점 18:43:22 UTC. 지금 가진 실제 관측은 과업이 준 '제출 성공 반환, 완료 알림 없음'뿐이다. 실제 실행 로그나 장치 상태는 제공되지 않았다. 문서에서 확인한 단계는 입력 검사 → queued 호출 예약 → waitingRequests_에 등록/prepare → 준비 여부·소프트웨어 큐 한도 검사 → doQueueRequest의 취소 분기 또는 queueRequestDevice → 각 버퍼 완료 → 핸들러 completeRequest → 제출 큐 선두가 Pending인지 확인 → 애플리케이션 반환이다.

확인된 값은 입력 사례의 성공 반환뿐이다. 숫자 0인지 원시 반환값을 먼저 보존하겠다. `prepared_`, 큐 크기/한도, fence 신호, cancelled_, 장치 제출 반환, 각 버퍼 완료, completeRequest 진입, 선두 요청 상태는 모두 미확인이다. 실제로 이 값들을 관찰했다고 쓰면 안 된다.

다음 행동: 동일 요청의 식별자와 순번으로 단계 도달을 기록한다. 먼저 waitingRequests_ 선두의 준비 상태와 queuedRequests_ 크기를 확인한다. 미준비면 fence 등 준비 경로를 조사하고, 한도와 같으면 기존 요청 진행을 조사한다. 전달됐다면 취소 여부와 장치 함수 ret을 구분한다. 장치 처리로 갔다면 버퍼별 완료 개수와 명시적 completeRequest 호출을 확인한다. 이 호출이 있어도 통지가 없다면 제출 큐의 앞 요청 status()가 RequestPending인지 본다. 참이면 뒤 요청의 반환이 멈출 수 있다. 소프트웨어 큐 크기를 하드웨어 처리 중 요청 수로 단정하지 않는다.
