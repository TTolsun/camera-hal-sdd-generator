# 로컬 9B 자동 보완 루프 시험

**실패 원인에 따라 근거를 확장하고 질문을 분리하는 경로를 실제 Qwen으로 시험했습니다.** 공개 libcamera만 사용했으며 사내 HAL·사내 모델·실기기 검증은 수행하지 않았습니다. 실행 방법과 종료 조건은 [사내 적용 안내](../../inhouse/reader-loop.md)에 있습니다.

## 시험 범위

공식 upstream `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`는 2026-10-26 확인 시 변경되지 않았습니다. 기존 Vendor 연동 가이드에 빠져 있던 `IPAModule::match`의 이름·버전 호환 조건을 추가하는 사례를 선택했습니다. 최초 근거를 버전 비교 중간에서 끊고, 같은 함수 전체를 허용된 확장 범위로 지정했습니다. 이는 자동 보완 능력을 관측하기 위한 통제된 부족 입력입니다.

정답을 프롬프트에 써 넣거나 최종 본문을 수동으로 교체하지 않습니다. `minVersion` 이상, `maxVersion` 이하, 이름 일치가 함께 필요하다는 원래 질문과 답변 계약을 유지합니다. 기존 37개 질문은 정확히 같은 요청·응답 해시인 경우 재사용하고 의미 진단 대상에서는 제외합니다. 전체 문서의 생산용 구조·인용·답변 계약 검사는 계속 실행합니다. 이전 [PR84 개요 시험](../qwen-overviews.md)과 [Vendor 작성 시험](vendor-9b-focused.md)도 보존합니다.

모델은 `qwen3.5:9b`이며 Ollama 0.40.11, 9.7B Q4_K_M, CPU 실행(`size_vram: 0`), `think: false`, temperature 0.1, 문맥 16,384, 최대 출력 6,000으로 시험했습니다. 모델 digest는 `6488c96fa5faab64bb65cbd30d4289e20e6130ef535a93ef9a49f42eda893ea7`입니다.

## 실패에서 확인한 수정 필요 사항

| 개발 시험 | 실제 HTTP 시도 | 결과와 수정 |
|---|---:|---|
| trial-1 | 0 | 재사용 원응답의 첫 실패 뒤 재시도를 허용하지 않아 목표 질문에 도달하지 못했습니다. 이전 실행과 같은 재시도 설정을 유지했습니다. |
| trial-2 | 3 | 완료로 판정했으나 현재 인용에 없는 이름 조건을 넓은 후보 근거로 정당화한 오판이었습니다. 결과를 폐기하고 현재 근거 진단과 확장 계획을 분리했습니다. |
| trial-3 | 11 | 모델이 다시 쓴 코드 구절이 원문과 달라 중단됐습니다. 모델은 후보 ID만 선택하고 생성기가 원문을 연결하도록 바꿨습니다. |
| trial-4 | 1 | 근거 부족 판정에 수정 필드가 섞였습니다. 진단 스키마를 판정·검사·발견 사항 세 필드로 분리했습니다. |
| trial-5 | 10 | 함수 전체로 근거를 넓히고 추가 질문을 반복해도 버전 조건이 계속 빠져 3회차 한도에 도달했습니다. 세부 질문 자동 분리와 전체 답변 계약 검사를 추가했습니다. |
| trial-6 | 5 | 조건 누락을 지적하면서 해당 검사 항목을 통과로 표시했습니다. 진단에도 검증 오류를 알려 주는 제한된 재질문을 추가했습니다. |

이 실행들은 서로 다른 코드·프롬프트를 사용한 개발 시험입니다. 동일한 모집단의 성공률로 합산하지 않으며, 실패 실행의 일부 정확한 답변도 루프 전체 성공으로 세지 않습니다. 모델 진단의 항목 분류와 지적 내용 자체에도 오류가 있었으므로, 모델 검토를 독립 검토나 정확성 보장으로 취급하지 않습니다.

## 최종 실제 실행

trial-7은 최대 3회차·20회 호출·1,800초·같은 실패 2회 한도로 실행했고, **3회차·새 HTTP 10회·488.42초에 `model_review_complete`로 종료**했습니다. 첫 회차에서 함수 전체를 근거로 선택했고, 두 번째 회차에서 버전 조건 누락을 진단해 이름·최소 버전·최대 버전의 세 질문을 자동으로 만들었습니다. 세 번째 회차의 실제 답변은 두 경계의 포함과 이름 일치를 모두 설명했습니다. 본문을 수동으로 고치지 않았습니다.

최종 원고는 기존 답변 37개와 새 세부 답변 3개로 구성됩니다. 마지막 작성 회차는 응답 45회를 재사용하고 3회를 새로 호출했으며, 마지막 재생 과정의 고유 요청은 48개입니다. 누적 원응답 보관함의 84개 HTTP 기록에는 앞선 실패·개발 호출이 포함되므로 이번 실행의 신규 호출 수로 세지 않습니다. 의미 진단 대상은 복합 질문 1개이고 나머지 37개는 제외했습니다.

별도 실제 실행에서는 HTTP 한도를 1회로 두었고, 추가 호출 없이 64.37초에 `call_limit`으로 종료했습니다. 후보 원고를 완료 결과로 노출하지 않았고 승인 상태도 바꾸지 않았습니다. 새 영어 표시 문구 7개 역시 실제 Qwen HTTP 응답과 대조했습니다.

작성 세션에서 `src/libcamera/ipa_module.cpp:470–476`의 `>=`, `<=`, `&&`, `!strcmp`와 최종 문장을 대조했습니다. 세 문단 중 버전 설명은 일부 중복됩니다. 자동 분리가 조건 누락을 보완한 한 사례이지 문장 품질이나 다른 질문의 성공을 보장하는 결과는 아닙니다. 사내 적용 시에는 해당 HAL의 대표 실패 사례와 별도 정답·검토 기준으로 다시 평가해야 합니다.

## 공통 생성기에 반영한 동작

진단 모델에는 현재 인용만 보냅니다. 보완 모델은 진단과 허용된 확장 후보를 확인하고 추가 질문, 근거 후보 ID, 필요하면 세부 질문 2~4개를 제안합니다. 경로·앵커·원고·검사 기준을 직접 수정할 수 없습니다. `&&` 또는 `||`로 끝난 발췌에는 현재 발췌 전체를 포함하는 최소 허용 범위를 요구합니다.

진단·계획의 JSON 모순이나 잘못된 선택은 구체적인 검증 오류와 함께 `review.max_retries` 안에서 다시 요청합니다. 새 요청과 실패 요청은 전체 HTTP 한도에 포함합니다. 복합 질문을 나눈 경우 세부 답변을 조립한 뒤 원래 계약 전체와 원래 질문을 다시 검사합니다. 세부 답변의 요청·응답 해시는 `assembly_origins`로 연결합니다.

회차·호출·시간·정체 한도와 근거 부족·입력 변경 등의 종료 조건이 있습니다. 완료 판정도 `publishable: false`, `human_approval: pending`을 유지합니다. 운영 설정을 반영하는 단계와 공개 배포는 루프 밖의 기존 검토·배포 절차입니다.

## 증빙 읽기

공개 시험은 [libcamera-sdd의 루프 기록](https://github.com/TTolsun/libcamera-sdd/tree/main/qwen-reader-loop)에 보관합니다. `final/loop.json`에서 최종 회차와 호출 수, `history.json`에서 폐기한 개발 시험, `call-limit/loop.json`에서 실제 호출 한도 종료를 구분합니다. `verification.json`은 HTTP 출처와 파일 연결 검사이며 의미 정확도 점수가 아닙니다. `author-review.json`은 작성 세션에서 원문과 대조한 기록이며 사람 승인이나 독립 검토가 아닙니다.
