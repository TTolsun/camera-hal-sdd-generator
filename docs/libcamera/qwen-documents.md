# 나머지 문서의 로컬 Qwen 갱신 검증

공개 libcamera 입력으로 8개 설명 문서의 **기준 생성 → 소스 변경 → 복원 → 공식 커밋 이월**을 실제 로컬 `qwen3.5:9b`로 검증했습니다. 최종 원고와 연결된 HTTP 응답 247개를 요청·응답 해시, 인용 발췌와 함께 대조했습니다. 같은 복원 커밋을 다시 처리하면 추가 모델 호출이 없었습니다. [독립 검증기](../../examples/libcamera/verify_document_replay.py)는 게시 원고와 각 단계의 원응답을 비교합니다. 공개 증빙은 문서 저장소의 `qwen-documents/`에서 관리합니다.

시험은 공식 소스 `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`를 바탕으로 했습니다. 변경·복원 커밋에서 실제 WSL 빌드와 300개 번역 단위 추출을 수행했으며 파싱 오류는 0개였습니다. 생성 실패 뒤 같은 커밋을 재시도할 때는 소스 커밋·추출 입력·facts 해시가 일치하는 이전 실제 추출 결과를 명시적으로 재사용했습니다. 시험용 변경 커밋은 배포하지 않습니다.

초기 실행에서는 비교 연산자 변경, 구현 의무 누락, 잘못된 JSON 등이 발생했습니다. [실패 응답 기록](../../examples/libcamera/fixtures/qwen-document-failures.json)과 [첫 갱신 시도](../../examples/libcamera/fixtures/qwen-document-replay-attempt.json)는 당시 실패를 그대로 보존합니다. 이후 근거 범위를 함수·분기별로 나누고 질문을 보완해 다시 호출했습니다. IPA 검색 경로와 LSC 함수 본문·파일 범위 등록도 분리했습니다. 실패 문장을 사람이 고쳐 채택하지 않았습니다.

소스 변경을 처리할 때는 `sdd update --to <커밋>`을 실행하세요. 이 명령은 대상 커밋의 facts를 추출하고, 변경된 근거를 사용하는 문서를 찾아 해당 주제의 설명을 다시 생성합니다. 근거가 같은 주제는 원래 작성자를 보존한 채 이월합니다.

설명 주제의 재사용 여부는 질문·근거 발췌·작성 지침으로 판단합니다. 클래스 구조표나 발췌의 줄 번호만 바뀐 경우에는 같은 설명을 새 facts로 다시 검증하고 인용 위치를 갱신합니다. 페이지 전체의 구조 지문 검사는 유지하므로, 설명을 재사용하더라도 오래된 구조표를 그대로 이월하지 않습니다.

## 검증 대상

두 개요의 시험은 [개요 갱신 기록](qwen-overviews.md)에 있습니다. 추가 시험은 다음 설명 문서 전체를 대상으로 합니다.

| 문서 | 시험에서 바꾸는 근거 |
| --- | --- |
| 지원 범위와 검증 | Software ISP 벤치마크의 측정 프레임 수 |
| 연동 가이드 | `createIPA()`의 프록시 선택 조건 |
| Pipeline Handler | 요청 준비에 전달하는 대기 시간 |
| IPA | 프록시 선택 조건과 실제 오류 경로 |
| IPU3 LSC의 설정과 프레임 처리 | 수평 그리드의 최대 셀 수 |
| RKISP1 카메라별 왜곡 보정 | 계수 목록의 허용 개수 |
| 카메라와 요청 모델 | 접근 상태 검사에서 반환하는 오류 코드 |
| 요청 처리와 문제 진단 | 접근 상태 오류와 요청 준비 경로 |

클래스 색인, LSC 구조표와 호출 시나리오는 추출 사실에서 생성합니다. 이 문서에는 LLM 작성자를 붙이지 않습니다. 별도 시험 필드와 호출을 추가해 facts와 해당 출력에 반영되는지 확인합니다. 사이트 메뉴, 검색 색인과 용어집은 사이트 구성에서 조립되는 공통 자료이며, 설명 문서의 모델 응답 기록과 구분합니다.

## 소스 변경 시험

공식 libcamera 커밋의 별도 복제본에서 변경 커밋과 복원 커밋을 만듭니다. 실제 제품의 요구사항이나 upstream 변경으로 취급하지 않습니다. 복원 커밋의 전체 트리가 공식 소스와 같은지도 검사합니다.

1. 공식 소스의 모든 대상 설명을 로컬 Qwen으로 생성합니다. 호출 요청, HTTP 응답과 해시를 보관합니다.
2. 변경 커밋에 운영용 `sdd update`를 실행합니다. 실제 빌드·추출 결과와 변경 영향 목록을 보관합니다.
3. 바뀐 값이나 분기가 설명에 반영됐는지 확인합니다. 변경되지 않은 주제의 설명과 작성자도 비교합니다.
4. 복원 커밋에 같은 갱신 명령을 실행하고 원래 소스 동작을 설명하는지 확인합니다. 같은 커밋으로 다시 실행했을 때 추가 모델 호출이 없는지도 확인합니다.
5. 복원 원고를 공식 커밋의 근거와 다시 검증합니다. 전체 문서 설정으로 렌더링하고 사이트·번역·공개 파일 해시를 검사한 뒤 게시합니다.

시험 중 생성이나 검사가 실패하면 기존 원고를 유지합니다. 실패 응답을 수작업으로 고쳐 채택하거나 사람 승인 장부를 작성하지 않습니다. 질문을 나누거나 빠진 소스 근거를 추가한 뒤 모델을 다시 호출합니다.

긴 실행을 재시도할 때는 `review.answer_cache: true`를 선택할 수 있습니다. 같은 커밋에서 검사에 통과한 실제 응답만 체크포인트로 보관하며, 입력이나 모델 digest가 바뀌면 새로 호출합니다. 변경 커밋과 복원 커밋은 서로 다른 커밋이므로 각각 새 호출이 필요합니다. 체크포인트는 승인 기록이 아니며 원본 HTTP 요청·응답 기록도 계속 보관해야 합니다.

## 짧은 문단 작성 지침

실제 Qwen 비교에서 긴 공통 지침은 LSC 셀 크기의 정수 보정 `- 1`을 빠뜨렸고, 동일 근거·모델·JSON 스키마에 짧은 지침을 사용한 응답은 두 계산식을 보존했습니다. 공개 예제는 문서별 `design_prompt`로 짧은 지침과 기존 지침을 선택합니다. 짧은 지침이 긴 복합 질문의 JSON 작성에서도 항상 유리하지는 않았습니다. 근거와 질문을 먼저 제공하고 한 문단 안에 필요한 여러 문장을 작성하도록 요청합니다. 이 비교 결과는 임의의 코드에 대한 정확성 보장이 아니며, 각 변경 시험과 출력 대조는 계속 필요합니다.

## 입력과 출력의 검증 경계

질문별 그림은 작성된 정의를 근거 해시에 고정합니다. 공개 예제의 `visuals.on_stale: omit`는 근거가 바뀐 그림을 제외하고 재검토 안내를 표시하므로, 오래된 그림을 게시하지 않으면서 본문 갱신을 계속합니다. 이것은 LLM의 그림 재생성이나 사람 승인이 아닙니다. 기본값 `error`는 생성을 중단하며, 어느 설정에서도 커밋 불일치나 노드 한도 초과를 허용하지 않습니다.

질문에 현재 기본값을 정답처럼 넣으면 소스 변경 후에도 이전 값의 설명을 유도할 수 있습니다. 예를 들어 `prepare(300ms)`를 설명하라는 질문 대신 `prepare()`에 전달하는 현재 대기 시간 값을 읽도록 질문합니다. 반환 오류도 실제 구현에서 읽도록 하며, API 주석과 구현이 다르면 그 차이를 구분합니다.

벤치마크의 프레임 수는 `Benchmark`의 초기값과 설정 덮어쓰기 경로를 함께 읽습니다. 보정 계수의 허용 개수는 오류 로그만 읽지 않고 `setCoefficients()`의 실제 검사도 읽습니다. 각 근거 파일은 `design_topics.sources`를 통해 변경 영향 분석에 연결됩니다.

공개 증빙 검증기는 원고의 각 문장과 실제 모델 응답, 인용한 발췌, 단계별 커밋, 원고 해시와 이월 결과를 대조합니다. 숫자·분기 확인은 이 시험에 대한 검사이며 임의의 소스 변경에 대한 모델의 의미 정확성을 보장하지 않습니다. 자동 검사와 사람의 내용 검토, 사내 HAL·실기기 검증은 별도입니다.

다음 단계: [공개 libcamera 문서](https://ttolsun.github.io/libcamera-sdd/)에서 원고와 코드 근거를 함께 확인하세요.
