# Feature가 늘어날 때 문서 관리하기

**새 Feature에 필요한 설명은 추가하고, 기존 페이지의 과도한 증가·중복·방치된 원고는 게시 전에 검사합니다.** `sdd audit-docs`로 현재 상태를 먼저 확인하세요.

## 자동으로 하는 일

`documentation.enabled: true`이면 생성·증분 갱신·누락 보완의 사이트 검증·정적 사이트 게시 전에 같은 검사를 실행합니다. 새 커밋이 없는 `update`도 현재 원고를 검사합니다. 문제가 있으면 `build/document-health.json`과 `build/document-health.md`에 원인과 처리 방향을 남기고 실패합니다. `impact.json` schema 1과 기존 명령은 유지합니다.

| 검사 | 실패할 때 할 일 |
|---|---|
| 페이지 본문 길이와 이전 성공 결과 대비 증가율 | 독립적인 주제를 별도 섹션으로 나누거나 필요한 증가인지 검토합니다. |
| 표·코드를 포함한 Markdown 전체 길이 | 자료를 상세 문서로 나누고 기존 문서에서 연결합니다. |
| 같은 페이지 또는 여러 페이지의 동일한 긴 문단 | 한 문서를 기준으로 정하고 다른 위치에는 링크를 둡니다. |
| 원고 누락, 설정에서 빠진 원고, facts와 다른 커밋 | 재생성하거나 폐기 계획을 명시합니다. |
| Feature의 기준 문서·관련 섹션·시나리오·심볼 누락 | 범위를 보완하거나 삭제된 Feature의 문서 계약을 정리합니다. |

커밋 수와 전체 페이지 수에는 고정 상한을 두지 않습니다. 새 Feature에 필요한 페이지 추가는 허용합니다. 페이지별 읽기 부담을 관리하므로 상세 문서를 추가해도 개요가 계속 길어질 필요가 없습니다.

## 프로젝트 설정

```yaml
documentation:
  enabled: true
  limits:
    max_chars: 18000
    max_markdown_chars: 120000
    max_growth_ratio: 1.5
    min_growth_chars: 1000
    duplicate_min_chars: 180
  pages:
    overview.md:
      max_chars: 6000
  features:
    - id: capture
      primary: capture.md
      sections: [camera-model, pipeline-handler]
      scenarios: [queue_request, complete_request]
      symbols: [CameraDevice]
```

위 값은 시작용 기본값이며 사내 HAL 검증으로 정한 값은 아닙니다. `pages`에는 특정 페이지의 한도만 덮어씁니다. Feature의 심볼·섹션·시나리오 이름은 실제 설정과 facts에 맞춥니다. 하나의 Feature에는 기준 문서 하나를 지정하며, 설명이 충분한지는 별도로 검토합니다.

본문 길이는 제목·표·코드 펜스·인용 블록·생성된 근거 안내를 제외한 문단의 공백을 정규화한 문자 수입니다. 동일 문단 검사에서는 인라인 식별자를 유지합니다. 전체 Markdown 한도는 표와 코드가 과도하게 커지는 경우를 별도로 잡습니다.

증가율과 최소 증가량을 모두 넘으면 실패합니다. 기준이 2,000자이고 새 본문이 3,200자이면 기본값에서 검토 대상입니다. 새 페이지에는 이전 길이가 없으므로 절대 길이와 중복·범위 검사를 적용합니다.

## 분리·통합·폐기를 반영하는 순서

1. 검사 보고서에서 `split`, `merge-or-link`, `retire-or-map` 등 처리 방향과 대상 페이지를 확인합니다.
2. `sections.yaml`의 주제·필수 질문·소스 근거를 옮기고 `routes`·`next`와 Feature 계약을 갱신합니다. 고유한 조건·예외·진단 정보는 보존합니다.
3. 전체 `generate`로 원고를 다시 만듭니다. 근거 지문·커밋·문서 수명주기·사이트 링크 검사가 변경된 구조를 확인합니다. 번역판이 있으면 번역 카탈로그도 다시 검토합니다.
4. 원고 검토와 게시 절차를 수행합니다. 자동 검사 통과를 사람 승인으로 기록하지 않습니다.

설정을 지웠다는 이유만으로 기존 원고를 조용히 버리지 않습니다. 통합하거나 폐기한 페이지는 다음처럼 선언합니다. `sha256`은 `audit-docs` 보고서의 해당 페이지 값을 사용합니다. UTF-8로 읽어 줄바꿈을 정규화한 원고 전체의 해시입니다.

```yaml
documentation:
  enabled: true
  retired_pages:
    - path: old-capture.md
      sha256: "<document-health.json의 64자리 sha256>"
      reason: "조건과 예외를 capture.md에 통합했습니다."
      replacements: [capture.md]
```

폐기 대상은 활성 섹션에서 제거되어 있어야 합니다. 대체 문서가 있으면 실제 활성 문서인지 확인하며, 기능 자체가 제거된 경우 `replacements: []`와 사유를 기록합니다. 남아 있는 폐기 원고가 바뀌면 게시를 중단합니다. 원고 파일은 자동 삭제하지 않고 사이트·검색·이월 대상에서 제외합니다. 기존 게시 산출물은 manifest의 소유권 규칙에 따라 다음 빌드에서 정리합니다. 폐기 문서로 연결된 링크는 검증에 실패하므로 함께 갱신해야 합니다.

## 실패·재시도와 비교 기준

비교 기준은 `build/document-baseline.json`입니다. 처음 생성하기 전 기존 원고를 보존하고, 이후에는 검사와 생성 또는 사이트 빌드가 성공했을 때만 기준을 갱신합니다. `audit-docs`는 기준을 바꾸지 않습니다. 실패한 원고를 재시도해도 분량 증가 검사를 통과할 수 없습니다.

`automate`는 게시 전 검사 실패 시 문서 저장소를 바꾸지 않습니다. 배포 확인에 실패하면 기존 재개 단계에서 이어갑니다. 누락 보완은 임시 원고를 검사한 뒤 반영하며, 임시 사이트 빌드가 실제 비교 기준을 갱신하지 않습니다. 기준 파일은 실행 설정·facts·상태와 함께 보관합니다. 파일을 잃으면 과거 대비 증가율을 복원할 수 없지만 절대 한도와 중복·범위 검사는 계속 적용됩니다.

## 자동 검사의 범위

Feature의 의미를 임의의 코드 변경에서 완전히 추론하거나 유사한 문장을 의미 기준으로 자동 통합하지 않습니다. 현재 검사는 정확히 반복된 문단과 명시한 Feature 계약을 검사합니다. 새 Feature 등록과 의미가 바뀌는 분리·통합·폐기 결정은 검토 대상입니다. 생성된 HTML을 직접 수정하거나 필요한 내용을 잘라내서 한도를 통과시키지 않습니다.

이 관문은 `generate`, `update`, `export-site`, `automate`와 `improve`의 사이트 검증에 연결됩니다. 별도 MkDocs 빌드나 단일 HTML 내보내기를 배포에 쓰는 환경은 먼저 `audit-docs`를 실행해야 합니다. 새 옵션이 없는 기존 설정은 기존 동작을 유지하며, 저장소의 시작 설정과 공개 libcamera 예제에서는 검사를 활성화했습니다.

문서 구조 개선에는 `project-documentation` 스킬의 기준 문서·고유 정보 보존·탐색 검증 원칙을 참고했습니다. 실행과 CI는 개인 스킬 설치나 외부 서비스에 의존하지 않습니다. 사내 LLM·저장소·호스팅은 기존 설정으로 교체합니다.
