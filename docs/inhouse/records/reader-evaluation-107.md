# 공개 libcamera SDD 독자 평가와 사내 적용 가능성 (이슈 #107)

**이 기록은 공개 libcamera 문서를 독자 목표 1~5로 평가한 개선 전후 결과와, 목표 6(사내 적용 가능성)의 판단 근거입니다.** 평가자는 문서 작성에 쓴 생성기를 수정한 에이전트 본인입니다. 독립 평가나 실제 독자 시험이 아니며, 사람 검토와 사내 HAL 검증은 모두 완료되지 않았습니다. 목표 6의 결론은 "libcamera·mini-hal 기준 추정"입니다.

## 평가 조건

| 항목 | 내용 |
|---|---|
| 분석 기준 커밋 | `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f` (공식 upstream의 최신 커밋이며 이번 작업 중 새 커밋이 없었습니다) |
| 문장 생성 모델 | `qwen3.5:9b`를 Hermes CLI로 호출했습니다. 모델 교체는 하지 않았습니다. |

| 개선 전 열람 | 2026-10-26에 공개 사이트를 브라우저로 읽었습니다. |

## 개선 전 판정 (목표 1~5)

| 목표 | 판정 | 근거 |
|---|---|---|
| 1. 제품 이해 | 미흡 | `vendor-overview`는 `introduction.rst`의 한 문장 뒤에 바로 `Camera` 클래스 설명으로 넘어갑니다. 누구의 어떤 문제를 푸는지, 어디까지 지원하는지, 앱·libcamera·커널 계층 그림이 없습니다. |
| 2. 강점 전달 | 미충족 | "구현 근거로 보는 강점"이 `queueRequest` 대기 큐와 `maxQueuedRequestsDevice_ = 32` 같은 내부 구현만 나열합니다. 독자 이점이나 비교 대상이 없습니다. |
| 3. 신입 온보딩 | 부분 충족 | 읽는 순서, 상태 규칙, 소유권, 스레드 제약과 줄 단위 근거는 유용합니다. 설계 이유와 직접 실행해 보는 절차가 없습니다. |
| 4. 타팀 이해 | 미흡 | 메뉴가 For Vendor와 For Developer 두 갈래뿐입니다. `index`는 제품보다 문서 사용법과 검토 상태를 주로 설명합니다. |
| 5. 가독성 | 미충족 | 거의 모든 문장 뒤에 `문단 근거 1개`가 붙어 한 문단이 한 문장으로 끊깁니다. 문장 사이의 연결이 없습니다. |

이슈가 적은 결함 여섯 가지(중복 문장, 질문 문형 누출, 정보 없는 이동 안내 행, slug 링크, 상태 표시 과다, 성능 절 장황함)는 열람한 페이지에서 모두 확인했습니다. 상태 표시(결함 5)는 현재 main에서 이미 한 줄의 짧은 표시입니다.

## 재생성 범위와 실행 기록

**공개 SDD 14개 설계 문서 중 4개만 새 생성기로 다시 만들었고, 나머지는 기존 공개 원고를 그대로 두었습니다.** 문서 간 판 불일치를 알고 진행한 부분 반영이며, 사용자가 이 방식을 승인했습니다.

| 문서 | 이번 실행 | 작성 주체 | 소요 시간 |
|---|---|---|---|
| `vendor-overview` | 재생성 | `response-bundle`, Haiku 5.5 서브에이전트(effort high) | 서브에이전트 작성, 벽시계 시간은 기록하지 않았습니다. |
| `team-overview` (신규) | 생성 | 같은 방식 | 같음 |
| `vendor-assurance` | 재생성 | Hermes CLI, `qwen3.5:9b-ctx64k`, 추론 high | 1,268초(성공한 마지막 실행) |
| `onboarding` (신규) | 생성 | 같은 방식 | 488초(실패) + 663초(성공) |
| 나머지 10개 | 변경 없음 | 기존 공개 원고 | 인용을 최신 facts로 재검증만 했습니다. |

- **재생성하지 못한 문서**: `vendor-integration`, `overview`, `pipeline-handler`, `ipa`, `ipu3-lsc-flow`, `rkisp1-dewarp`은 같은 모델로 시도했으나 모두 실패했습니다. 실패한 시도의 소요 시간은 1,152초(`vendor-integration`), 3,417초(`overview`), 1,259초(`pipeline-handler`), 2,377초(`ipa`), 4,564초(`ipu3-lsc-flow`), 1,799초(`rkisp1-dewarp`)입니다. 원인은 9B 모델이 한 항목에서라도 형식(JSON 구조, 근거 목록 모양, 설명 문단 외 구조 문법)을 어기면 그 문서 전체가 중단되는 구조입니다. `camera-model`, `request-lifecycle`, `ipa-module-validation`은 시작하지 못했습니다.
- **재시도**: `sdd.local.yaml`의 `max_retries`를 7로 올렸습니다. 그래도 이번 실행 중 `onboarding`이 `steps` 항목의 구조 문법 혼입으로 한 번 실패했고, 같은 구간을 다시 실행하자 통과했습니다.
- **전체 재생성이 불가능한 이유**: 근거 대조 정책(`grounding.py`)이 바뀌면 이전 정책으로 만든 모든 LLM 원고를 재사용하지 않습니다. 이번 작업에서 main이 이 정책을 바꾸어, 13개 문서·약 311개 항목·600회 이상의 모델 호출이 필요한 전체 재생성이 되었습니다. 9B 모델로 몇 시간이 걸리고 실패 위험이 높아 시도하지 않았습니다.
- **분석 기준 커밋**: `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`로 같고, 이번 작업 중 upstream에 새 커밋이 없었습니다.

### 영향 분석을 사용한 범위 결정

upstream 소스는 바뀌지 않았으므로 소스 diff 기반 영향 분석은 재생성 대상을 내지 않습니다. 이번 변경은 설정(새 질문과 답변 계약)과 생성기 코드에서 일어났습니다. 그래서 질문이 바뀌거나 새로 생긴 섹션(`vendor-overview`, `vendor-assurance`, 신규 `team-overview`, `onboarding`)만 `generate --sections`로 지정해 재생성했고, 나머지는 입력 해시와 인용 재검증으로 이월했습니다. 일괄 전체 재생성으로 우회하지 않았습니다.

## 개선 후 판정 (목표 1~5)

평가 방법은 개선 전과 같습니다. 같은 6개 페이지를 새 빌드(로컬 서버)에서 브라우저로 읽었습니다. `overview`, `vendor-integration`, `scenarios/queue_request`는 재생성하지 못했으므로 문장 자체는 개선 전과 같고, 사이드바·상단 구조·번역 같은 생성기의 사이트 구성 변경만 반영되었습니다.

| 목표 | 개선 전 | 개선 후 | 남은 한계와 원인 |
|---|---|---|---|
| 1. 제품 이해 | 미흡 | 부분 충족 | `vendor-overview`가 "무엇이며 누구의 어떤 문제를 푸는가", 앱·어댑테이션·libcamera·커널 네 계층 그림(facts로 생성), 지원 플랫폼 목록과 빌드 선택을 첫 절에서 답합니다. 한계: 지원 범위는 `platform_support.rst`와 `meson_options.txt`가 말하는 만큼이며 성능·인증 수치는 근거가 저장소에 없어 쓰지 못했습니다(B6). 일부 문장이 어색합니다("오픈 소스 복잡한 카메라 지원 라이브러리"). |
| 2. 강점 전달 | 미충족 | 부분 충족 | 절 순서가 "독자 이점 → 뒷받침하는 구현 근거"로 바뀌었습니다. 한계: V4L2 직접 사용 같은 비교 대상과 정량 이점은 저장소 안에 근거가 없어 생성하지 못했습니다(B6). "장치 구현자가 공통 계층에서 얻는 것"은 여전히 `queueRequest`·`maxQueuedRequestsDevice_` 같은 구현 사실이 중심입니다. |
| 3. 신입 온보딩 | 부분 충족 | 부분 충족 | `onboarding` 페이지가 `cam -l` 실행 단계와 "요청 접수와 완료를 나눈 이유"를 제공합니다. 한계: 실행 확인 항목 문장에 영어 관사("The cam")와 닫히지 않은 백틱이 남았고, 설계 이유가 한 문단뿐입니다. 이는 9B 모델 출력이고 린트가 잡지 못하는 형태입니다. |
| 4. 타팀 이해 | 미흡 | 부분 충족 | `team-overview`("이 프로젝트가 하는 일")가 For Developer / 구조 이해의 첫 문서로 생겼고 `index` 표에서 연결됩니다. 별도의 타팀 그룹은 사용자 결정으로 두지 않았습니다. 사람 독자가 실제로 이해하는지는 시험하지 않았습니다. |
| 5. 가독성 | 미충족 | 부분 충족 | 재생성한 `vendor-assurance`는 문단 근거 표시가 10개에서 3개로 줄어 문장이 문단으로 묶였습니다. 한계: `overview`·`vendor-integration`·`scenarios/queue_request`와 미재생성 6개 설계 문서는 개선 전 원고여서 한 문장 한 문단 구조가 남아 있습니다. 재생성한 문서에서도 9B 문장(영어 구절 혼입, "반드시 실행된다" 같은 과한 표현)이 남습니다. |

모든 문서는 여전히 "자동 검사 통과 · 사람 검토 전"이며, 이 판정은 사람 검토가 아닙니다.

### 새로 확인한 내용 결함

- `vendor-overview`는 "stop()으로 정지될 때 모든 요청의 자동 완료가 보장됩니다"라고 쓰고, `onboarding`은 "요청이 자동으로 완료되지 않는다"고 씁니다. 앞은 정지 시 대기 요청의 취소, 뒤는 정상 흐름의 완료 책임을 말하는 것으로 보이나, 서로 다른 문서에서 같은 개념을 달리 표현해 독자가 모순으로 읽을 수 있습니다. 사람 검토에서 확인해야 합니다.
- 생성기의 문장 검사는 문장이 참인지 보장하지 않습니다. 위 어색한 문장과 영어 혼입은 모두 검사를 통과했습니다.

## 목표 6: 사내 적용 가능성 (libcamera·mini-hal 기준 추정)

**이 결론은 libcamera와 mini-hal을 기준으로 한 추정입니다. 사내 HAL의 소스와 구성이 제공되지 않았으므로 사내 적용이나 검증이 완료되었다는 뜻이 아닙니다.**

| 항목 | 측정값 | 판정 | 전제 조건 |
|---|---|---|---|
| C1 설정 작성 비용 | libcamera 예제의 `sections.yaml`은 5,718줄(섹션 153개), `visuals.yaml`은 1,743줄입니다. 착수 시점(3,886줄, 1,615줄)보다 약 1,832줄, 128줄 늘었습니다. 이번에 추가한 4개 문서와 답변 계약이 대부분입니다. | 조건부 | 사내 HAL에서 같은 품질을 내려면 문서 하나당 약 400줄의 질문·근거·계약 설정을 소스를 아는 사람이 써야 합니다. 클래스 선택과 근거 후보는 `facts.json`으로 초안을 만들 수 있으나, 질문과 답변 계약은 사람이 정해야 합니다. 초안 자동 생성 기능은 이번에 만들지 않았습니다. |
| C2 실행 환경 | Hermes CLI 뒤의 로컬 모델(`qwen3.5:9b-ctx64k`)로 생성했고, compile DB는 Meson이 만든 것을 썼습니다. 사이트는 `--mermaid`로 로컬 파일을 지정하지 않으면 `cdn.jsdelivr.net`의 Mermaid를 불러옵니다(빌드된 18개 페이지 확인). | 조건부 | 사내망에서는 Mermaid를 로컬 경로로 지정해야 합니다. 사내 CLI와 모델, compile DB 확보 방법은 사내 소스 없이 확인하지 못했습니다. |
| C3 실행 시간과 증분 갱신 | 문서 1개 생성 483초~4,564초(9B, 성공과 실패 포함)이고 성공한 마지막 실행은 `vendor-assurance` 1,268초, `onboarding` 663초입니다. 14개 설계 문서 중 10개는 인용 재검증만으로 재사용했습니다. 전체 재생성은 600회 이상의 호출이 필요해 시도하지 않았습니다. | 조건부 | 증분 운영은 가능합니다. 단, 근거 대조 정책이 바뀌면 모든 원고가 재사용 거부되므로 정책 변경은 전체 재생성과 같은 비용을 낳습니다. 정책 변경 빈도를 낮추거나 정책을 섹션별로 나누는 설계가 필요합니다. |
| C4 사람 검토 부담 | 문서 14개 모두 "사람 검토 전"입니다. 재생성한 4개 문서에는 인용 위치 17~67개가 붙어 있습니다. | 조건부 | 문서당 검토 시간은 측정하지 않았습니다(추정만 가능). 인용 대조를 문서당 건당 1~2분으로 가정하면 이번 4개 문서는 약 1~3시간입니다. 코드 변경 시 연결된 인용이 바뀐 문서만 다시 검토하는 범위는 영향 분석이 계산합니다. |
| C5 품질 한계 | 목표 1~5가 모두 "충족"이 아닌 "부분 충족"에 그쳤습니다. 원인은 세 가지입니다. (a) 근거 부재: 비교 대상·성능 수치·사내 조직 역할은 저장소에 없습니다. (b) 모델 문장력: 9B 모델이 영어 혼입, 과한 표현, 구조 문법 혼입을 반복했고 한 항목의 실패가 문서 전체를 중단시켰습니다. (c) 구조: 문장 단위 검사는 의미의 참을 보장하지 않습니다. | 조건부 | 사내 모델이 9B보다 작으면 같은 결과가 어렵습니다. 같거나 크더라도 문서별 실패 복구(항목 단위 재시도)가 없으면 운영 비용이 큽니다. 모델 교체는 이번 범위가 아니므로 제안만 하며, 같은 질문 집합으로 모델 크기별 성공률을 비교하는 시험을 권합니다. |

종합: **조건부 가능**입니다. 파이프라인 구조(추출·영향 분석·인용 검증·증분 갱신)는 사내 HAL에서도 쓸 수 있는 형태이나, 질문 설계에 사람이 필요하고 사람 검토 없이 쓰기에는 문장 품질이 부족합니다.

## 작성 주체와 한계 공개

- **영어 번역**: 카탈로그 약 580개 문자열과 이후 추가분 85개는 Haiku 5.5 서브에이전트(effort high)가 작성했고, 생성기의 번역 검사(자리표시자, 한글 잔존, 의무 표현 약화)를 통과한 것만 반영했습니다. 선택한 CLI(Hermes) 밖의 작성이므로 사용자가 이 세션에 한해 승인한 예외입니다. 영어판도 사람 검토 전입니다.
- **`team-overview`, `vendor-overview`**: Haiku 5.5 서브에이전트가 `response-bundle` 경로로 작성했고 생성기의 모든 검증을 거쳤습니다. 사용자 승인에 따른 예외입니다.
- **모델 설정**: 별칭 모델 `qwen3.5:9b-ctx64k`(`num_ctx` 65,536)와 Hermes의 추론 high를 사용자 승인으로 썼습니다. 개선 전 공개 문서의 `qwen3.5:9b`와 다릅니다.
- **부분 반영**: 위 6개 설계 문서와 3개 기타 문서는 이전 공개판입니다. 같은 사이트 안에 새 생성기 출력과 이전 출력이 섞여 있습니다.
- **미완료**: 사람 검토, 실제 독자 시험, 실기기 검증, 사내 HAL 검증은 수행하지 않았습니다. 공개 libcamera 결과만으로 사내 적용 완료를 선언하지 않습니다.
