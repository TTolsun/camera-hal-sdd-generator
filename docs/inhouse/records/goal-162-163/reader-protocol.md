# #163 고정 독자 평가 절차

이 절차는 개선 후 결과를 읽기 전에 2026-10-30에 고정했습니다. 공개 libcamera 문서만 평가하며 사내 HAL 검증이나 내용 승인 절차가 아닙니다. 실제 참여 결과는 아직 없습니다.

## 비교할 페이지와 대표 절

| 경로 | 고정 대표 절·관측 문제 | 고정 이해·탐색 질문 |
| --- | --- | --- |
| index.html | For Vendor / For Developer 진입 안내 | ‘처음 읽는 개발자의 순서’에서 처음 열 문서와 그다음에 요청을 따라갈 문서·절을 찾고 선택 이유를 설명하세요. |
| vendor-overview.html | 카메라 스택과 지원 범위 | 공통 프레임워크와 장치별 구현은 각각 무엇을 맡습니까? 지원 보장의 한계도 찾으세요. |
| vendor-assurance.html | 성능 측정 범위 | 내장 벤치마크가 포함하는 처리와 제외하는 처리는 무엇입니까? |
| overview.html | 요청 생성·소유권·재사용 | createRequest가 돌려주는 요청의 소유자는 누구이며, 요청을 재사용해 큐에 넣기 전에 무엇을 해야 합니까? 근거를 찾으세요. |
| vendor-integration.html | 구현할 설정 인터페이스 / 요청을 장치에 전달하고 반환하기 | 마지막 버퍼 완료가 요청 완료를 뜻합니까? 누가 어느 스레드에서 어떤 함수를 호출해야 합니까? |
| scenarios/queue_request.html | 이동 안내 / 주요 확인 지점 / 추적 범위와 경계 | Camera가 요청을 넘기는 호출 대상과 예약된 호출 표기를 찾고, 정적 호출 목록으로 실행 순서나 실제 스레드를 확정할 수 있는지 설명하세요. |

선정한 연동 문단에는 `completeRequest()`의 명시 호출 의무가 인접 문장으로 반복됩니다. `configure()`의 추가 검증 금지도 인접 문장에 반복되며 두 번째 문장에는 사용자 정의 필드에 의존할 수 있다는 별도 사실이 있습니다. 별도 사실·조건·주체·스레드는 보존하고 중복 부분만 생성 질문에서 분리합니다. 시나리오 표에는 제목에 `절을 확인합니다`만 붙인 행이 있습니다. 그림의 텍스트 추출 줄바꿈은 실제 잘림과 별도로 판정합니다.

## 자동 전후 비교

같은 여섯 경로를 앞 세 페이지·뒤 세 페이지 두 그룹으로 읽습니다. 기존 #107의 다섯 목표(제품 이해, 근거 있는 강점, 온보딩, 타팀 경계 이해, 가독성·유용한 이동)를 같은 질문과 `supported / partial / unsupported / not-applicable` 기준으로 평가합니다. 작성 이력·개선 여부를 모델에 제공하지 않습니다. 독립 Codex CLI / gpt-6.1-terra / high를 사용하고 페이지 원문, 문단 ID, 요청·응답·영수증·시간을 보존합니다. 두 그룹을 합친 점수를 만들지 않습니다. 자동 평가는 사람의 즐거움·실제 과업 수행을 입증하지 않습니다.

## 실제 참여자에게 전달할 안내

문서 작성에 참여하지 않은 3명 이상을 모집하세요. 신입 관점 1명과 타팀 관점 1명을 반드시 포함하세요. 이름 대신 P01·P02·P03을 사용하고 역할 관점만 기록합니다. 완성한 후보의 고정 build_id와 공개 URL을 각 평가 기록에 넣으세요. 작성자는 시작 URL과 과업 문구만 전달하고 답이나 이동 경로를 설명하지 않습니다. 도움을 주면 그 과업은 무설명 완료로 계산하지 않습니다. 10분을 넘기면 중단 여부를 기록하고 실패 원인을 남깁니다. 소요 시간을 채우기 위해 임의의 값을 넣지 않습니다.

각 참여자는 아래 2과업을 수행합니다. 다른 참여자의 답은 보지 않습니다.

| 참여자 | 과업 1 | 과업 2 |
| --- | --- | --- |
| P01 신입 관점 | index의 ‘처음 읽는 개발자의 순서’에서 시작 경로와 다음 문서·절을 찾고 선택 이유를 설명합니다. | overview에서 요청 소유권과 큐에 넣기 전 재사용 절차의 책임·근거를 찾습니다. |
| P02 타팀 관점 | vendor-overview에서 공통 계층과 장치 구현의 책임·지원 한계를 구분합니다. | vendor-assurance에서 내장 벤치마크가 포함·제외하는 처리를 찾습니다. |
| P03 비작성자 | vendor-integration에서 버퍼 완료와 요청 완료의 차이·명시 호출자·스레드를 찾습니다. | queue_request에서 요청 전달 대상과 예약된 호출 표기, 정적 추적의 한계를 찾습니다. |

과업마다 페이지·앵커, 본인 답변, 답의 근거, 시작·종료 시각과 실제 소요 초, 작성자의 도움 유무, 막힌 이유, 주관적 읽기 경험을 기록합니다. 읽기 부담은 1=매우 부담됨, 2=부담됨, 3=보통, 4=부담이 낮음, 5=부담이 매우 낮음으로 응답합니다. 정답 대조자는 답의 정확성과 근거를 확인하되 평가 중에는 피드백하지 않습니다. 시간이 짧다는 이유만으로 완료로 판정하지 않습니다.

## 수용 기준과 제출

최소 6과업 중 5과업 이상을 작성자의 설명 없이 정확히 완료하고, 모든 과업의 읽기 부담 점수 중앙값이 4 이상이어야 합니다. 미응답·중단·도움을 받은 과업도 원래 분모에 보존합니다. 적은 표본의 결과이며 전체 사용자 성공률로 확대하지 않습니다. 추가 참여자는 같은 기준으로 모두 기록하며 좋은 결과만 선택하지 않습니다.

옆의 `human-results.csv`는 빈 기록 양식입니다. 실제 수행 후 여섯 행의 빈칸을 채워 이 채팅에 전달하거나 해당 파일에 저장해 주세요. 익명 관점과 과업 결과만 있으면 되며 실명·연락처는 필요하지 않습니다. 평가 자료의 build_id가 고정되기 전에는 측정을 시작하지 마세요. #150의 분량 증가 필요성과 정지/완료 계약 표현은 [기준 공개본에 한정한 사용자 승인](https://github.com/TTolsun/camera-hal-sdd-generator/issues/150#issuecomment-6485027153)으로 완료됐습니다. 그 기존 승인을 이번 과업 평가나 새 후보의 포괄적 승인으로 확대하지 않습니다.

실제 결과가 없거나 기준에 미달하면 #163과 전체 Goal을 완료 처리하지 않습니다.

채점자는 [진행자용 채점 기준](facilitator-rubric.md)을 사용합니다. 참여자에게는 이 기준이나 정답을 과업 전에 보여 주지 않습니다. 기준 페이지를 확인하면서 overview의 과업을 실제 요청 수명 절로, queue_request의 과업을 실제 표시된 예약 대상까지 찾는 것으로 정정했습니다. 개선 후 결과나 사람 수행 결과를 보고 과업을 바꾼 것이 아니며 실제 사람 평가는 아직 시작하지 않았습니다.
