# 배포 문서만으로 수행한 독립 읽기 시험

2026-10-24에 작성 맥락을 받지 않은 새 에이전트가 공개 libcamera SDD만 읽었습니다. 첫 코드, 요청 흐름, 완료 누락, 구성 실패·정지 진단을 찾아 답하고 문서 안 발췌를 대조했습니다. 저장소와 외부 코드 원문은 보지 않았습니다. 실제 사람이나 실기기 시험은 아닙니다.

## 첫 평가에서 막힌 곳

첫 평가는 18:08 KST에 끝났습니다. 관찰한 문서의 소스는 `2c4b67c0792f88f69bcdf9cbf73e81b3d8cf4b6f`였습니다. 개요의 생성 시각은 08:27:20 UTC, 상세 문서는 05:28:37 UTC였으며 배포 manifest는 확보하지 못했습니다. 따라서 특정 배포 전체의 평가로 확대하지 않고 읽은 페이지의 결과로 기록합니다. 평가 도중 별도 원고 갱신이 있었으므로 재평가에는 같은 build_id의 사이트를 사용합니다.

| 과제 | 찾은 답과 장애 | 보완 |
|---|---|---|
| 첫 코드 | 홈 → 개요에서 `camera_manager.cpp`, `CameraManager::start()`, `cameras()`·`get()`을 찾았습니다. | 첫 코드 안내를 유지했습니다. |
| 요청 흐름 | 생성·버퍼 연결·제출 예약·준비·장치 전달·버퍼 완료·명시적 요청 완료를 찾았습니다. 제출 0과 완료도 구분했습니다. | 기존 계약을 유지했습니다. |
| 완료 누락 | 조사 단계는 찾았지만 큐 한도·준비 상태·반환 순회를 다른 문서와 발췌에서 조합해야 했습니다. | 진단 절에 파일·함수·읽을 값·다음 분기를 모았습니다. |
| 구성 실패 | 검색 결과가 없었고 정적 시나리오의 여러 후보만으로 실제 구현을 고르기 어려웠습니다. | 상태·validate·파이프라인 반환·스트림 연결을 순서대로 조사하는 절과 홈 바로가기를 추가했습니다. |
| 정지 문제 | 정지 계약은 찾았지만 함수 내부 대기와 반환 뒤 콜백을 직접 구분해야 했습니다. | stopDevice 진입·복귀, 두 큐의 검사, 콜백 후속 작업을 분리했습니다. |
| 근거·용어 | 문단 근거가 외부 호스트로만 연결됐고 fence·Pending·컨트롤 정보 맵·활성 스트림 설명이 부족했습니다. | 로컬 발췌를 먼저 연결하고 네 용어를 용어집 한 곳에 정의했습니다. |

문서 안 로컬 발췌가 하나로 정해지면 문단 근거의 첫 링크에서 펼칩니다. 기존 커밋·파일·줄을 가리키는 전체 소스 링크도 유지합니다. 후보가 둘 이상이면 임의의 발췌를 선택하지 않습니다.

## 보완의 범위

공식 upstream에는 새 커밋이 없었습니다. 최신 생성기와 별도 작업에서 갱신한 LLM 원고를 보존한 뒤 요청 진단과 개요를 다시 생성했습니다. 설명은 이 Codex 세션이 소스에서 작성한 응답을 입력 해시에 묶어 `response-bundle`로 가져왔습니다. Qwen 실행이나 사람 승인으로 기록하지 않았습니다. 설정에는 고정 설계 답변을 추가하지 않았습니다.

진단 내용은 소스 기반 조사 계획입니다. 중단점·계측을 둘 함수와 읽을 값은 제공하지만 기기별 추적 수집 명령, 정상 지연, 복구 성공 결과는 만들지 않았습니다. `validate()`처럼 상태를 바꿀 수 있는 함수를 관측 목적으로 재호출하지 않도록 했습니다.

문서 증가 검사에서 한 번 차단된 뒤, 앞 절과 겹치는 검토 문장을 줄여 기존 한도 안으로 맞췄습니다. 같은 계약의 상세 설명을 다른 문서에 복사하거나 검사 한도를 완화하지 않았습니다. 사내 가이드·스킬·설정·handoff에는 독립 읽기 과제와 실제 답·관측 분기·배포 식별자 기록을 추가했습니다.

사내 소스·사내 게시·실기기 검증은 수행하지 않았습니다.

## 보완 후 독립 읽기

별도의 새 에이전트에게 로컬 검증 사이트 주소와 같은 과제만 전달했습니다. 평가자가 직접 읽은 build_id는 `dbeeb6af1d09b31250f81fef340014720636982e4304d03e1a5965981050c212`입니다. 첫 코드·요청 흐름·완료 누락·구성 실패·정지 문제를 모두 찾았고, 문서 내부 발췌와 대조해 필수 과제 합격으로 평가했습니다.

- 완료 누락에서는 `prepared_`, 두 큐의 크기·한도, 장치 반환값, 선두 `RequestPending`에 따른 다음 분기를 답했습니다.
- 구성 실패에서는 접근 검사·원래 validate 반환·장치 반환·스트림 연결을 구분하고 validate 재호출의 위험도 찾았습니다.
- 정지에서는 함수 내부 대기·미완료 큐·별도 콜백 작업을 나눴습니다.
- 검색어 `구성 실패`로 결과 한 개를 찾고 해당 절에 도달했습니다. 문단 근거에서 로컬 발췌도 열었습니다.

평가자가 남긴 경미한 지적은 개요 하단의 “코드를 처음 읽는 순서”가 요청 제출 시나리오를 뜻한다는 점이었습니다. 이후 생성기 제목을 “선택한 시나리오의 코드 읽기 순서”로 바꿨습니다. 설정 파일 표현 정리 후 88개 사이트 파일이 같고 manifest만 바뀐 것도 비교했습니다. 해당 평가자의 후속 manifest 재확인은 브라우저 연결 부재로 완료하지 못했으므로, 최종 공개 배포본 검증과 구분합니다.

## 최종 공개 배포본 재평가

2026-10-24에 마지막 보완과 공개 배포를 마친 뒤, 기존 작업 맥락이 없는 다른 새 에이전트에게 공개 사이트만 전달했습니다. 평가 전후 manifest의 build_id는 모두 `7e7913217dc0422eaec3803f29a20d2ee8094d5070e99a2b36a6c47a34550e70`이었습니다. 로컬 파일이나 외부 코드에 접근하지 않고 다섯 과제에 모두 합격했습니다.

| 과제 | 실제로 찾은 답 |
|---|---|
| 코드 진입점 | `camera_manager.cpp`의 `CameraManager::start()` → `cameras()`·`get()` → 하드웨어 연결의 `PipelineHandler::match()` |
| 요청 흐름 | 요청 생성 → 버퍼 연결 → 제출 예약 → 준비·장치 전달 → 버퍼 완료 → 명시적 요청 완료 → 제출 순서의 완료 통지. 제출 반환값 0과 완료를 구분했습니다. |
| 완료 누락 | `prepared_`, 큐 크기·한도, fence, `cancelled_`, 장치 반환값, 선두 `RequestPending`에 따른 다음 조사 위치를 찾았습니다. |
| 구성 실패 | 접근 검사 → 원래 validate 반환과 변경 전후 구성 → Valid 여부 → 구체 파이프라인 반환값 → 스트림 연결을 구분했습니다. |
| 정지 문제 | 실행 상태 → blocking 호출 → stopDevice 진입·복귀 → 지역 큐 취소·완료 → 두 큐 검사 → Configured 복귀를 찾고, 반환 뒤 수신자 작업 큐도 구분했습니다. |

CUA 브라우저에서 `구성 실패` 검색 결과 한 개를 선택해 해당 절로 이동했습니다. 문단 근거에서 로컬 발췌를 열고 camera.cpp의 1163·1308·1431행과 pipeline_handler.cpp의 428·547·359행을 대조했습니다. 필요한 함수·관측값·다음 분기 중 찾지 못한 항목은 없었습니다.

생성기 [PR #79](https://github.com/TTolsun/camera-hal-sdd-generator/pull/79)는 `3066527e44f5ee843acb0f192cc7505afdc16c9e`로, 공개 문서 [PR #27](https://github.com/TTolsun/libcamera-sdd/pull/27)는 `f508b46710dc9f1bdfaa6180ab4ee98fb64c4e39`로 병합됐습니다. 당시 GitHub Pages의 산출물 88개와 manifest가 로컬 검증본과 일치했습니다. 이 기록은 해당 배포에 대한 결과이며 이후 배포의 평가를 대신하지 않습니다.

[검증 버전 릴리스](https://github.com/TTolsun/camera-hal-sdd-generator/releases/tag/inhouse-2026-10-24)에 당시 반입 ZIP, 체크섬, 시작 프롬프트와 최종 평가 기록을 보관합니다. ZIP의 파일 263개가 실행 검증한 후보와 같고, 별도 위치에서 공개 mini 입력으로 generate·audit-docs·export-site·verify-site를 통과했습니다. 실제 독자 사용자 시험·사내 HAL·실기기 검증과 사람 승인은 별도이며, 사람 승인 상태는 pending으로 유지했습니다.
