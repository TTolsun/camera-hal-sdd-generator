# 복구 뒤 답변 사전 순서가 바뀔 때의 의미 감사 재사용

PR #154 병합 커밋 `ee776c82`의 전체 CLI 생성은 19/19·신규 호출 0·42.578초였다. 이어진 실제 main 감사에서는 같은 설명·근거·정책인데 요청이 달라져 추가 호출이 발생했다. 이 감사가 0호출이었다고 보고하지 않는다.

원래 부분 복구는 고친 resources 주제를 unchanged stopping 뒤에 추가했고, 전체 재사용은 질문 설정의 순서로 다시 저장했다. `generated_design.answers`의 사전 삽입 순서가 주 문서 peer 순서와 schema enum에 전파됐다. 실제 첫 요청에서 `request-lifecycle.md/stopping/6`과 `request-lifecycle.md/resources/13`의 순서가 뒤집혔다. 주장의 값·원문·근거는 같지만 literal user 지문은 `bd639681…`에서 `b8089704…`로 달라졌고, 영수증·정책 검사가 이를 다른 요청으로 취급한 것은 올바른 동작이었다.

추가 호출을 막기 위해 이 작업의 `final_main_verify.py` 프로세스 트리만 종료했다. 실행 기록은 완료 21호출·진행 중 1호출, 기록 시점 272.235초를 남겼다. 진행 중 호출을 완료·실패 중 하나로 추정하지 않으며, 원본 요청·응답·완료 영수증과 부분 보고서를 보존했다. 다른 세션의 프로세스나 자료는 건드리지 않았다.

의미 감사 입력을 조립할 때 답변 주제 사전의 키를 안정된 순서로 읽도록 수정한다. 설명 목록의 순서·주장 ID·원문·직접 근거·주 문서 문맥은 유지한다. 캐시 지문이나 기존 정책을 고정하지 않고 실제 요청과 schema를 안정화한다. 새 회귀는 부분 복구와 전체 재사용의 사전 순서를 바꿔도 여러 배치의 literal system/user/schema와 요청 해시가 같으며, 설명이 바뀌면 같지 않음을 확인한다. 수정 전 1 failed, 수정 후 관련 전체 52 passed다.

감사 코드 변경으로 정책 지문이 달라지므로 현재 정책의 전체 계약과 고정 사례를 새 Terra High CLI로 다시 검토한다. 그 검토와 이후 병합 main에서의 실제 0호출 재사용, 반복 사이트 빌드, 공개 배포 결과는 별도로 기록한다. 자동 검사는 사람 승인이나 사내 HAL 검증이 아니다.
