# 질문과 근거를 자동으로 보완하는 루프

**실패한 답변을 소스와 대조하고, 질문·발췌를 보완해 다시 작성하려면 `sdd.reader_loop`를 실행합니다.** 결과는 별도 시험 폴더에 저장합니다. 운영 설정·소스·원고를 덮어쓰거나 문서를 승인·게시하지 않습니다.

```powershell
python -m sdd.reader_loop --config project/sdd.yaml --section vendor-contract --out build/reader-loop --max-rounds 3 --max-calls 80 --max-seconds 1800 --max-stalls 2
```

기존 실제 HTTP 시험에서 이어가려면 `--seed build/reader-trial`을 추가합니다. 같은 소스 커밋·모델·생성 설정이며 요청·응답 해시가 맞는 기록만 재사용합니다. 변경된 질문이나 근거는 새로운 요청이므로 모델을 다시 호출합니다. 소스 커밋이 바뀌면 `sdd update`를 사용합니다.

## 모델이 수정할 수 있는 내용

1. 생성기가 필수 답변과 인용·계약 검사를 실행합니다.
2. 진단 모델이 원래 질문, 현재 답변, 검사 오류와 **현재 인용한 발췌만** 비교합니다. 주체·조건·의무와 허용·반환·순서·답변 누락을 각각 판정합니다. 확장 후보가 현재 인용의 부족을 가리지 않도록 이 단계에는 넓은 발췌를 보내지 않습니다.
3. 오류가 있으면 별도 보완 호출에 진단과 허용된 확장 후보를 제공합니다. 모델은 원문 구절과 원인을 제시하고, 추가 질문과 확장할 근거 후보 ID를 반환합니다.
4. 생성기가 수정안을 검사한 뒤 격리된 설정 사본에 적용합니다. 다음 회차는 그 설정으로 작성과 검토를 반복합니다.

추가 질문은 원래 질문 뒤에 붙입니다. 요구사항, 답변 계약, 필수 용어, 거부 패턴과 검사 임계값은 모델이 변경할 수 없습니다. 모델은 문서 본문을 직접 수정하지 않고 다시 작성할 질문만 제안합니다. 추가 질문의 의미가 원래 요구를 약화하지 않는지도 최종 검토에서 확인하세요.

근거는 현재 발췌 전체를 포함하는 범위로만 확장합니다. 기존 `sources[].scope`를 후보로 사용하거나, 운영자가 같은 파일의 허용 범위를 지정할 수 있습니다.

모델은 구절을 다시 쓰지 않고 근거 ID를 선택합니다. 생성기가 해당 발췌를 그대로 인용 기록에 연결하므로, 모델이 원문의 연산자나 공백을 바꿔 쓰는 오류를 줄입니다. `&&`나 `||`로 끝난 조건식은 명백히 잘린 발췌로 판정하고, 허용된 완전한 후보 중 가장 작은 범위를 보완안에 요구합니다. 이 검사는 일반적인 코드 완전성 판정이 아닙니다. 보완안이 요구된 확장을 빠뜨리면 구체적인 오류와 함께 `review.max_retries` 범위에서 다시 요청하고 전체 호출·시간 예산도 적용합니다.

```yaml
review:
  reader_loop:
    evidence_scopes:
      vendor-contract/request/submit:
        start: "int Device::submit(Request *request)"
        end: "return result;\n}"
```

키는 `섹션/주제/소스 ID`입니다. 위 이름과 앵커는 형식을 보여 주는 예시이며 실제 HAL에 맞춰 설정해야 합니다. 모델은 경로·Git 커밋·앵커를 만들거나 다른 파일을 읽도록 지시할 수 없습니다. 후보는 고정된 Git 커밋에서 읽고 현재 발췌를 포함하는지 검사합니다. 함수의 바깥 조건과 실패 분기를 포함하는 앵커를 선택하세요. 이는 C++ 구문 분석을 통한 함수 경계 추론이 아닙니다.

## 한도와 종료 조건

| 조건 | 기록되는 종료 사유 |
|---|---|
| 선택한 답변의 모델 검토와 문서의 자동 검사가 모두 완료됨 | `model_review_complete` |
| 초기 생성을 포함한 최대 회차에 도달함 | `round_limit` |
| 생성·진단을 합한 실제 HTTP 시도 한도에 도달함 | `call_limit` |
| 경과 시간 한도를 넘음 | `time_limit` |
| 원문을 생략하지 않고는 입력 예산 안에 넣을 수 없음 | `input_limit` 또는 생성 검사 실패 |
| 같은 대상에서 같은 오류 종류·소스·구절이 연속해서 반복됨 | `repeated_failure` |
| 수정안이 설정을 바꾸지 않거나 이전 설정으로 되돌아감 | `no_progress` |
| 앞선 생성 실패 때문에 선택한 질문에 도달하지 못함 | `unreached_targets` |
| 모델이 제공된 후보만으로 답을 뒷받침할 수 없다고 판정함 | `insufficient_evidence` |
| 모델은 적합하다고 했으나 실제 답변 계약 검사가 실패함 | `unresolved_automatic_failure` |
| 실행 중 입력·생성 코드·집필 규칙 파일이 바뀜 | `inputs_changed` |
| 잘못된 수정안·해시·설정 또는 모델 연결 실패 | `invalid_or_unavailable` |
| 사용자가 실행을 중단함 | `interrupted` |

실패한 HTTP 시도도 호출 한도에 포함합니다. 재생은 HTTP 호출로 세지 않습니다. 시간 한도는 호출 전과 회차 경계에서 확인하고, 남은 시간으로 HTTP 타임아웃을 제한합니다. 파일 읽기·검증·타임아웃 정리 시간 때문에 실제 종료 시각이 한도와 정확히 같지는 않습니다.

`--target vendor-contract/request/submit`처럼 특정 답변만 진단할 수도 있습니다. `parts`가 없는 주제는 `섹션/주제`를 사용합니다. 이때 `excluded_units`에 나머지 답변을 기록하므로 전체 문서의 의미 검토로 보고하지 않습니다. 그림은 기존 생성 검사를 통과해야 하지만 이 루프의 의미 진단 대상은 본문 답변입니다.

## 결과를 사내 운영에 연결하기

`loop.json`에서 종료 사유, 회차별 수정안, 실제 호출 수와 검토 범위를 확인합니다. 각 회차의 `sections.yaml`은 실제 적용한 설정이고 `proposed-sections.yaml`은 다음 회차용 수정안입니다. `trial/evaluation.json`, 원요청·원응답·HTTP 영수증과 `diagnosis-prompts/`를 함께 보존합니다. 성공 조건에 도달했을 때만 `candidate_trial`이 지정됩니다.

`model_review_complete`도 의미 정확성 보장이나 사람 승인이 아닙니다. 같은 모델이 작성과 검토를 맡으면 같은 오류를 놓칠 수 있습니다. `publishable: false`, `human_approval: pending`은 종료 사유와 관계없이 유지합니다. 검토자가 원래 요구와 소스에 대조한 뒤 설정 변경을 반영하고 기존 생성·배포 절차를 진행하세요. 사내 모델 주소와 인증은 기존 `agent.kind: ollama` 또는 `openai-compatible` 설정을 사용하며 외부 서비스는 필요하지 않습니다.
