# 설계 이유를 근거로 연결하기

**소스 발췌가 연결된 설계 주제 하나를 골라, 그 코드를 만든 커밋과 리뷰에서 "왜"를 찾아 근거로 연결하세요.** 소스 발췌만 연결한 문서는 "무엇을 하는가"까지만 설명하므로 코드 설명서처럼 읽힙니다. 이유·제약·기각한 대안은 코드에 없고, 커밋 메시지와 Gerrit 리뷰에 남아 있는 경우가 많습니다.

이 절차는 사내 HAL에서 처음 적용하는 순서입니다. 섹션 하나로 효과를 측정한 뒤 범위를 넓힙니다. 설정 키와 명령의 정확한 형식은 [커밋 메시지 근거](../reference/sections.md#커밋-메시지-근거), [리뷰 코멘트 근거](../reference/sections.md#리뷰-코멘트-근거), [명령 참조](../reference/cli.md#그-밖의-명령)에 있습니다.

| 지금 할 일 | 이동할 절 |
|---|---|
| 환경이 조건을 만족하는지 확인합니다. | [0. 시작 조건](#0-시작-조건) |
| 시범 섹션과 주제를 고릅니다. | [1. 시범 범위](#1-시범-범위) |
| 커밋 후보를 찾고 읽습니다. | [2. 커밋 후보](#2-커밋-후보) |
| 리뷰 코멘트를 가져옵니다. | [3. 리뷰 코멘트](#3-리뷰-코멘트) |
| 근거를 등록하고 다시 생성합니다. | [4. 등록과 생성](#4-등록과-생성) |
| 결과를 대조합니다. | [5. 결과 대조](#5-결과-대조) |
| 효과를 측정하고 확대 여부를 정합니다. | [6. 효과 측정과 확대](#6-효과-측정과-확대) |
| 코드 변경 뒤 근거를 유지합니다. | [7. 변경 반영](#7-변경-반영) |

## 0. 시작 조건

**아래 다섯 가지를 모두 확인한 뒤 시작합니다.** 하나라도 맞지 않으면 후보가 잘못 나오거나 근거가 `needs-review`로 남습니다. 명령은 생성기 루트에서 실행하고, `<HAL>`은 소스 체크아웃, `<CFG>`는 사내 설정 파일입니다.

| 확인할 것 | 명령 또는 방법 | 통과 값 |
|---|---|---|
| 생성기 버전 | `git -C <생성기> merge-base --is-ancestor 978b1f9 HEAD` 또는 `uv run sdd import-reviews --help` | 종료 코드 0. 이전 반입본에는 `history-candidates`·`import-reviews`가 없습니다. |
| 전체 Git 이력 | `git -C <HAL> rev-parse --is-shallow-repository` | `false`. shallow clone이면 모든 줄이 잘린 지점의 커밋에서 도입된 것으로 보입니다. CI 체크아웃은 대부분 shallow이므로 `git fetch --unshallow`가 필요합니다. |
| facts와 체크아웃 | facts의 `meta.source_commit`과 `git -C <HAL> rev-parse HEAD` | 같은 해시. 다르면 `extract`를 다시 실행합니다. |
| Change-Id trailer | `git -C <HAL> log -20 --format=%B` 에서 `Change-Id:` 줄 확인 | 병합 커밋 메시지 끝에 `Change-Id: I…`가 남아 있습니다. 없으면 리뷰 근거를 쓸 수 없고 커밋 근거만 씁니다. |
| Gerrit REST 접근 | Gerrit 설정 화면에서 HTTP 비밀번호 발급 | `curl.exe -u <사용자> "<GERRIT>/a/accounts/self"`가 계정 정보를 돌려줍니다. 막혀 있으면 3단계를 건너뜁니다. |

**보관 위치도 먼저 정합니다.** 리뷰 스냅숏은 `paths.reviews_dir`(기본값 `<설정 루트>/reviews/`)에 생깁니다. 작성자 이름과 사내 논의가 들어 있으므로 사내 설정 저장소에서만 관리합니다. 공개 저장소·공개 채팅·이슈에 올리지 않습니다.

## 1. 시범 범위

**섹션 하나에서 주제 2~3개를 고릅니다.** 이유가 중요한 주제일수록 효과가 잘 드러납니다.

1. 질문에 "왜", "보장", "금지", "제한"이 들어가는 주제를 우선합니다. 예를 들면 요청 큐의 깊이 제한, 정지 시 미완료 요청 처리, 콜백 스레드 규약이 있습니다.
2. 그 주제의 소스 근거가 `available`인지 확인합니다. facts의 `evidence["<섹션>/<주제>/<근거>"].status`를 봅니다. `available`이 아니면 [발췌와 답변 연결](contract-authoring.md#2-발췌와-답변-연결)부터 마칩니다.
3. 시범 섹션 ID와 주제 ID, 시작 시각을 `handoff.md`에 적습니다. 6단계의 측정이 이 기록을 기준으로 합니다.

**통과 값:** 선택한 주제마다 `available` 소스 근거가 하나 이상 있습니다.

## 2. 커밋 후보

**소스 발췌의 줄 범위에서 출발해 그 코드를 만든 커밋을 찾습니다.** 이 명령은 설정과 facts를 바꾸지 않고 모델도 부르지 않습니다.

1. 후보 목록을 만듭니다.

    ```powershell
    uv run sdd --config <CFG> history-candidates --sections <섹션>
    ```

2. `build/history-candidates.md`를 엽니다. 주제별로 발췌 범위와 후보 커밋, 메시지 전문, YAML 조각이 있습니다.
3. 후보마다 메시지 전문을 읽고 아래 표의 신호로 우선순위를 정합니다.
4. 이유·제약·대안을 실제로 설명하는 메시지에 표시해 둡니다. 4단계에서 그 조각만 등록합니다.

| 후보 정보 | 읽는 방법 |
|---|---|
| `이 파일에서 범위 최초 도입` | `git log -L`이 이 파일 안에서 찾은 가장 오래된 커밋입니다. 설계 의도가 자주 남지만 같은 파일 안의 위치 이동일 수도 있으므로 `현재 줄의 출처`와 함께 봅니다. |
| `현재 줄 N개의 출처 (원래 파일: …)` | `git blame -w -M -C`가 파일 이동·복사를 거슬러 찾은 커밋입니다. 리팩터링으로 파일이 옮겨져도 원래 도입 커밋을 찾습니다. |
| `이후 변경` | 그 뒤 같은 범위를 바꾼 커밋 수입니다. 1 이상이면 메시지의 의도와 현재 코드가 다를 수 있으므로 현재 소스와 대조합니다. |
| `제목만 있음`, `정리성 변경으로 보이는 제목` | 이유를 거의 담지 않는 커밋입니다. 목록에서 빼지 않고 표시만 합니다. |
| `Change-Id`, `리뷰 링크` | 실제 논의가 리뷰에 있을 수 있습니다. 3단계에서 가져옵니다. |

**통과 값:** 시범 주제마다 "이유가 적힌 커밋"과 "리뷰를 볼 커밋"이 정해졌습니다. 이유가 적힌 커밋이 하나도 없어도 실패가 아닙니다. 그 사실을 6단계 측정에 기록합니다.

## 3. 리뷰 코멘트

**생성기는 Gerrit에 접속하지 않습니다.** 사람이 REST 응답을 저장하고, 생성기는 저장한 파일만 읽습니다. 그래서 인증 정보를 생성기 설정이나 로그에 넣지 않아도 됩니다.

1. 리뷰 스냅숏이 없는 커밋 후보 아래에는 아래와 같은 명령이 표시됩니다. 주소는 커밋의 `Reviewed-on` trailer에서 가져오며, 없으면 `<GERRIT>`를 사내 주소로 바꿉니다.

    ```powershell
    curl.exe -u <사용자> "<GERRIT>/a/changes/<Change-Id>?o=MESSAGES" -o reviews-raw/<id>-change.json
    curl.exe -u <사용자> "<GERRIT>/a/changes/<Change-Id>/comments" -o reviews-raw/<id>-comments.json
    ```

2. 저장한 응답을 스냅숏으로 가져옵니다.

    ```powershell
    uv run sdd --config <CFG> import-reviews --change reviews-raw/<id>-change.json --comments reviews-raw/<id>-comments.json
    ```

3. 출력에서 `코멘트 N개`와 저장 경로를 확인합니다. 이메일은 저장하지 않습니다. `reviews-raw/`의 원본 응답은 가져온 뒤 지워도 됩니다.
4. `history-candidates`를 다시 실행합니다. 커밋 후보 아래에 코멘트가 붙습니다. 사람이 쓴 코멘트와 발췌와 같은 파일에 단 코멘트가 먼저 나오고, 투표·빌드·업로드 알림은 `Gerrit 자동 알림`으로 표시되어 뒤로 갑니다.
5. 질문 코멘트보다 그 질문에 답한 코멘트를 고릅니다. "왜 막지 않고 거절합니까?"보다 "막으면 요청 스레드가 멈추므로 거절합니다"가 근거로 적합합니다.

| 증상 | 원인과 해결 |
|---|---|
| `Multiple changes found` | 같은 Change-Id가 여러 브랜치에 있습니다(cherry-pick). `<project>~<branch>~<Change-Id>` 또는 변경 번호로 요청합니다. |
| `401 Unauthorized` | 로그인 비밀번호가 아니라 HTTP 비밀번호가 필요합니다. 주소의 `/a/`도 확인합니다. |
| `변경 응답에 messages가 없습니다` | 첫 요청에 `?o=MESSAGES`가 빠졌습니다. |
| 코멘트가 변경 메시지뿐입니다. | `--comments` 응답을 지정하지 않았습니다. 인라인 코멘트에 실제 논의가 많습니다. |

**통과 값:** 시범 주제의 "리뷰를 볼 커밋"마다 스냅숏이 있고, 고른 코멘트에 `kind: review` 조각이 표시됩니다.

## 4. 등록과 생성

**고른 조각을 주제의 `sources`에 넣고, 그 근거를 쓰는 "왜" 질문을 함께 추가합니다.** 근거만 넣고 질문을 바꾸지 않으면 생성 결과에 이유가 들어가지 않습니다.

1. 후보 파일의 YAML 조각을 그 주제의 `sources`에 복사합니다. 조각의 앵커는 trailer 앞까지의 메시지 전체 또는 코멘트 전체를 선택합니다. 필요하면 이유가 적힌 문단으로 좁힙니다.
2. `design_generation: llm` 섹션은 모든 소스 ID가 어느 `parts`에든 포함되어야 합니다. 이유 근거를 쓰는 part를 추가합니다.

    ```yaml
    parts:
      - id: behavior
        question: 큐가 요청을 거절하는 조건과 반환값은 무엇입니까?
        sources: [guard]
      - id: rationale
        question: 이 제한을 둔 이유와 기각한 대안을 커밋·리뷰 기록으로 설명하고, 현재 코드에 그대로 남아 있는지 구분하세요.
        sources: [guard, why-1a2b3c4d, review-c2]
    ```

3. 생성합니다.

    ```powershell
    uv run sdd --config <CFG> generate --sections <섹션>
    ```

4. facts의 `evidence["<섹션>/<주제>/<근거>"]`에서 새 근거가 `available`인지 확인합니다. `needs-review`이면 `reason`을 읽고 아래 표로 해결합니다.
5. 내용을 대조한 근거만 `sha256`을 설정에 옮깁니다. 해시를 옮기는 일은 사람 승인을 대신하지 않습니다.

| `reason` | 해결 |
|---|---|
| `근거 커밋이 facts 커밋의 이력에 없습니다` | 다른 브랜치나 병합되지 않은 커밋입니다. 현재 제품 브랜치에 병합된 커밋을 고릅니다. |
| `facts 커밋의 이력에 이 Change-Id로 병합된 커밋이 없습니다` | 병합되지 않은 변경이거나, 병합 커밋에 `Change-Id` trailer가 없습니다. 본문에서 언급만 한 Change-Id는 인정하지 않습니다. |
| `리뷰 스냅숏이 없습니다`, `코멘트 id가 없습니다` | 3단계의 가져오기를 다시 확인합니다. |
| `시작 앵커가 없거나 유일하지 않습니다` | 앵커를 메시지 안에서 한 번만 나오는 문장으로 바꿉니다. |

**통과 값:** 새 근거가 모두 `available`이고 `build/design-review.json`에 미해결 필수 질문이 없습니다.

## 5. 결과 대조

**이유 문장과 현재 동작 문장이 서로 다른 근거를 인용하는지 확인합니다.** 커밋과 리뷰는 당시의 의도와 논의입니다. 현재 사실처럼 쓰면 틀린 문서가 됩니다.

| 대조할 항목 | 통과 기준 |
|---|---|
| 이유 문장의 인용 | `` `@commit/…` `` 또는 `` `@review/…` `` 인용이 붙어 있습니다. |
| 현재 동작 문장의 인용 | 소스 파일 인용(`파일:줄`)이 붙어 있습니다. 커밋·리뷰 인용만으로 현재 동작을 설명하지 않습니다. |
| 시점 표현 | "도입 당시", "리뷰에서"처럼 과거 기록임이 드러납니다. |
| 이후 변경이 있는 근거 | `이후 변경`이 1 이상인 커밋의 의도가 현재 코드와 맞는지 확인했습니다. 다르면 다르다고 적습니다. |
| 리뷰 제안의 채택 여부 | 답글과 최종 코드로 제안이 채택됐는지 확인했습니다. 채택되지 않은 제안을 설계 결정처럼 쓰지 않습니다. |
| 원문 상세 | 사이트의 원문 상세에 `커밋 기록`·`리뷰 기록` 표지와 해시·날짜·작성자가 보입니다. 코드 저장소 링크는 붙지 않습니다. |

**통과 값:** 시범 주제의 모든 이유 문장이 표를 통과합니다. 통과하지 못한 문장은 근거나 질문을 고친 뒤 4단계를 다시 실행합니다.

## 6. 효과 측정과 확대

**확대하기 전에 사내 저장소에서 이유가 어디에 남는지 측정합니다.** 이 결과로 다음 투자 방향이 정해집니다.

1. 시범 주제마다 아래 값을 `handoff.md`에 기록합니다.

    | 측정값 | 계산 |
    |---|---|
    | 커밋 근거 비율 | 이유가 적힌 커밋을 찾은 주제 수 ÷ 시범 주제 수 |
    | 리뷰 근거 비율 | 이유가 적힌 리뷰 코멘트를 찾은 주제 수 ÷ 시범 주제 수 |
    | 근거 없음 | 커밋과 리뷰 모두에서 이유를 찾지 못한 주제 수 |
    | 소요 시간 | 주제 하나에 2~5단계를 마치는 데 걸린 시간 |

2. 측정값으로 다음 방향을 정합니다.

    | 결과 | 다음 방향 |
    |---|---|
    | 커밋 근거 비율이 높습니다. | 같은 방식으로 다른 섹션에 확대합니다. 리뷰 가져오기는 커밋에 이유가 없는 주제에만 합니다. |
    | 커밋은 비고 리뷰에 이유가 있습니다. | 리뷰 가져오기를 표준 단계로 만듭니다. 팀에 "결정은 커밋 메시지에도 남긴다"는 규칙을 제안합니다. |
    | 둘 다 비어 있습니다. | 기록에서 찾을 수 없는 이유입니다. 사내 설계 문서를 `kind: product`의 `project-document`로 연결하거나, 담당자에게 주제별 설계 의도를 짧게 받아 문서화한 뒤 그 문서를 근거로 연결합니다. 이유를 추측해서 채우지 않습니다. |

3. 확대할 때는 섹션 단위로 1~5단계를 반복합니다. 한 번에 전체 섹션을 처리하지 않습니다.

**통과 값:** 측정값과 선택한 방향이 `handoff.md`에 있습니다.

## 7. 변경 반영

**코드가 바뀌어도 커밋·리뷰 근거 자체는 바뀌지 않지만, 그 근거가 설명하는 코드는 바뀔 수 있습니다.**

1. 소스 발췌가 바뀌어 `needs-review`가 되면, 같은 주제의 커밋·리뷰 근거로 쓴 이유가 아직 맞는지 함께 다시 확인합니다. [근거 변경 재검토](contract-authoring.md#4-근거-변경-재검토)를 따릅니다.
2. 바뀐 주제에 `history-candidates`를 다시 실행합니다. 새로 범위를 바꾼 커밋이 `범위 최근 변경`으로 나옵니다. 그 커밋이 설계 의도를 바꿨다면 새 근거로 추가합니다.
3. 리뷰를 다시 가져온 뒤 `바뀐 코멘트`·`사라진 코멘트`가 출력되면, 그 코멘트를 인용한 근거가 다음 수집에서 `needs-review`가 됩니다. 원문을 다시 읽고 설명과 해시를 정리합니다.

## 지켜야 할 것

- 후보는 근거가 아닙니다. 메시지와 코멘트를 읽지 않고 조각을 일괄 등록하지 않습니다.
- 자동 검사 통과(`available`, 해시 일치)를 사람 승인으로 기록하지 않습니다. 승인 장부는 사람이 기록합니다.
- 사내 커밋 메시지, 후보 파일, 리뷰 스냅숏은 사내 파생물입니다. 공개 저장소에 올리지 않습니다.
- 기록에서 이유를 찾지 못한 주제를 추측으로 채우지 않습니다. 근거 없음으로 남기고 6단계의 방향을 따릅니다.

다음 단계: 시범 섹션의 결과를 [완료 기록](agent.md#5-완료-기록) 형식으로 `handoff.md`에 남기고, 측정값에 따라 확대할 섹션을 정합니다.
