프롬프트 파일은 이 검증 버전과 함께 보관하는 사본입니다. 이후 버전의 절차는 해당 버전의 이 안내를 기준으로 확인합니다. [최종 공개 평가 요약](records/deployed-reader-evaluation.md#최종-공개-배포본-재평가)은 GitHub에서도 바로 읽을 수 있습니다.

GitHub가 자동 제공하는 `Source code (zip)`이나 일반 clone에는 반입용 `IMPORT-MANIFEST.json`과 대체 `AGENTS.md`가 없습니다. 그 상태에서 `verify_import.py`를 실행하면 검증할 수 없습니다. 저장소로부터 직접 준비하려면 승인된 준비 환경에서 위 기준 커밋을 받아 [패키지 재생성](#패키지-재생성)을 실행하세요. 사내 에이전트는 생성된 반입 디렉터리에서 시작합니다.

ZIP 안의 `camera-hal-sdd-generator/START_HERE.md`가 입구입니다. `IMPORT-MANIFEST.json`에는 생성기 기준 커밋과 파일별 SHA-256이 있습니다. 함께 전달된 `.zip.sha256`과 ZIP 해시를 대조한 뒤 압축을 풉니다. 해시는 전달 중 변경을 검출하며 출처 인증을 대신하지 않습니다. 승인된 전달 경로의 파일·체크섬을 사용하세요.

**의존성을 설치하거나 파일을 수정하기 전에** 압축을 푼 생성기 루트에서 실행합니다. Python 3.11 이상이 필요합니다.

```bash
python tools/verify_import.py
```

종료 코드 0과 `verified_files`를 기록합니다. 누락·변조·추가 파일이 있으면 깨끗한 디렉터리에 원본 ZIP을 다시 풀어 확인합니다. manifest를 수정해 통과시키지 않습니다. 이후 사내 작업은 아래처럼 별도 디렉터리에 둡니다.

```text
workspace/
  camera-hal-sdd-generator/   반입한 생성기와 가이드
  hal-camera-analysis/        사내 HAL 분석 전용 Git 체크아웃
  hal-sdd-project/            사내 설정·원고·근거·로그
  wheelhouse/                대상 환경에 맞게 승인·반입한 Python wheel
```

### 무엇이 들어 있고, 무엇을 따로 준비합니까?

| 포함 | 별도 준비 |
|---|---|
| 생성기 소스, 가이드, 스킬, 설정 템플릿, 공개 예제·테스트, 집필 규칙과 라이선스 | 사내 HAL 소스·제품 compile DB·생성 헤더·컴파일러·Git |
| 고정 커밋, 파일별 해시, `uv.lock`에서 만든 `requirements-inhouse.txt` | 대상 OS·CPU·Python에 맞는 Python 실행 환경과 wheel |
| 모델 없이 시작하는 템플릿, 로컬 Mermaid를 쓰는 설정 | 승인된 Mermaid 배포본 또는 사내 자산 서버 |
| 로컬 초안·품질·복구 절차 | 사람 검토자, 사내 게시·모델 접근 권한 |

이 ZIP만으로 폐쇄망 의존성 설치까지 완료되지는 않습니다. `.venv`나 다른 OS의 libclang 바이너리를 복사하지 않습니다. **대상과 같은 OS·CPU·Python 환경**의 승인된 준비 장비에서 다음 명령으로 wheel을 모으고, 별도 해시 목록과 조직의 라이선스 검토 자료를 함께 반입합니다. 지원 wheel이 없으면 대상 환경을 확인하고 준비를 중단합니다.

```bash
python -m pip download --only-binary=:all: --dest ../wheelhouse -r requirements-inhouse.txt
```

이 명령은 준비 장비에 설정된 패키지 저장소에 접속합니다. 사내 미러가 있으면 그 미러를 사용합니다. 반입 후에는 새 가상 환경에서 네트워크 없이 설치합니다.

```bash
python -m venv ../sdd-runtime
```

Linux에서는 `../sdd-runtime/bin/python`, Windows PowerShell에서는 `../sdd-runtime/Scripts/python.exe`를 사용합니다. 다음 `<PY>`는 선택한 실행 파일로 바꿉니다.

```text
<PY> -m pip install --no-index --find-links ../wheelhouse -r requirements-inhouse.txt
<PY> tools/run_sdd.py --help
```

`tools/run_sdd.py`는 동봉한 `src/`를 사용하고 CLI 종료 코드를 그대로 전달합니다. 생성기 자체를 pip로 설치할 필요가 없습니다. 기존 승인된 가상 환경도 사용할 수 있습니다. `uv`는 필수가 아니며 아래 실행표는 이 래퍼 기준입니다. 상세 가이드의 `uv run sdd`는 `<PY> tools/run_sdd.py`로 바꾸면 같습니다.

Mermaid는 대상 사내망에서 승인된 tarball을 `fetch-mermaid --tarball <파일>`로 가져오거나 승인된 사내 자산 주소를 설정합니다. tarball 반입·ESM 구성은 [사이트 자산 절차](../concepts/site.md)를 따릅니다. 모델, GitHub, 공개 CDN은 사내 운영의 필수 조건이 아닙니다.

## 실행 순서

**각 단계가 통과한 뒤 다음으로 이동합니다.** 생성기 루트에서 실행하며 `<CFG>`는 실제 사내 `sdd.yaml`의 절대 경로입니다. 명령과 종료 코드는 [CLI 참조](../reference/cli.md)가 기준입니다.

| 순서 | 할 일과 실행 명령 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1. 설정 | `examples/inhouse-template/`을 `../hal-sdd-project/`로 복사합니다. 환경과 최종 로컬 덮어쓰기를 확인합니다. | 소스 SHA·제품 변형·실제 DB 생성 명령·사내 경로가 정해졌습니다. |
| 2. 빌드 근거 | NDK-build면 `<PY> tools/run_sdd.py --config <CFG> compdb`를 실행합니다. 다른 빌드는 제품의 DB 생성 명령을 실행하고 `ndk_build.enabled: false`로 둡니다. | 제품과 같은 매크로·헤더·TU를 담은 DB가 있습니다. |
| 3. 환경·추출 | `doctor` → `extract` 순서로 실행합니다. 두 명령에도 `--config <CFG>`를 지정합니다. | 필수 환경 오류, 파싱 오류, 미해결 필수 진입점이 없습니다. |
| 4. 계약 작성 | [계약 작성 절차](contract-authoring.md)에 따라 발췌 원문을 읽고 `sources`, `statements`, `evidence`, `covers`, 해시를 채웁니다. 약어도 정의합니다. | Vendor·Developer 질문에 실제 소스로 답하고 조건·예외·수명을 대조했습니다. |
| 5. 생성·검사 | `generate` → `audit-docs`를 실행합니다. | 자동 검사를 통과하고 미해결 필수 계약이 없습니다. |
| 6. 로컬 사이트 | `fetch-mermaid --tarball <승인된 파일>`로 자산을 준비한 뒤 `export-site` → `verify-site`를 실행합니다. | 내부 링크 오류 0, manifest 검증 성공, 외부 자산 의존 없음 또는 승인된 사내 자산입니다. |
| 7. 독자·복구 시험 | 아래 품질 기준으로 대조하고 별도 시험 사본에서 반복·실패 보존·수정 후 재개를 확인합니다. | 자동 검사와 의미 검토의 증거, 실패 전후 해시가 있습니다. |
| 8. 인수인계·게시 | `handoff.md`를 작성합니다. 허용된 사내 게시와 승인 절차가 있으면 수행하고 원격 해시를 대조합니다. | 로컬 완료·게시·사람 승인·실기기 시험을 각각 보고합니다. |

상세 실행은 [에이전트 가이드](agent.md), NDK 사례는 [첫 실행](02-first-run.md)을 따릅니다. 다른 빌드에 NDK 설정을 강제로 적용하지 않습니다. `site.intro`는 본문 문자열이 아니라 Markdown 파일 경로입니다. 템플릿의 비어 있는 계약은 정상적인 작성 출발점이며, 그대로 실행해 실패한 것을 생성기 고장으로 판단하지 않습니다.

## 품질 합격 기준

**자동 검증 합격과 내용·운영 인수 합격을 구분합니다.** 아래 필수 기준을 모두 만족한 경우에만 검토 가능한 로컬 문서가 완성된 것으로 표시합니다. 실제 소스가 없는 경계는 담당자와 범위를 정하고 미검증이라고 남깁니다.

| 관문 | 합격 증거 | 불합격 예 |
|---|---|---|
| 입력·추출 | 소스 SHA, 제품·ABI·변형, TU·모듈 범위, 파싱 오류 0, 필수 진입점 누락 0 | 다른 변형의 DB·헤더로 오류만 없앴습니다. |
| 계약 | 두 `reader_profile`의 필수 질문에 답변과 유효한 발췌·해시·covers가 있습니다. | 색인이나 실행 확인 항목만으로 필수 답변을 대체했습니다. |
| 의미 | Vendor는 입력·소유권·완료·실패·실행 한계를, 신입·타팀 개발자는 첫 진입점에서 요청과 결과를 따라가고, 증상별 확인 코드·수정 범위·검증 조건을 찾습니다. 수명·동시성 근거도 대조합니다. | 재진입, 종료 후 사용, 제출 반환 전 콜백, 매크로 조건을 누락했습니다. |
| 읽기 | 한 계약의 상세 설명은 한 문서가 맡습니다. 결론을 먼저 읽고 필요한 근거만 펼쳐 확인할 수 있습니다. | 문장을 줄이면서 조건·예외를 삭제하거나 다른 문서에 상세 내용을 복제했습니다. |
| 독립 읽기 | 사이트만 받은 평가자의 과제별 답·URL·관측값·다음 분기와 전후 build_id, 보완 후 재평가 기록이 있습니다. | 작성자 설명이나 외부 소스로 답을 채웠고, 구성 실패·완료 누락·정지 문제의 조사 위치를 못 찾았습니다. |
| 자동·사이트 | generate·audit-docs·verify-site의 종료 코드와 보고서, 깨진 링크 0, 전체 manifest 해시 일치 | `needs-review`나 실패를 숨기고 성공 요약만 남겼습니다. |
| 반복·복구 | 같은 입력의 manifest가 같고, 실패 시험에서 기존 원고·사이트가 보존되며 수정 후 재개됩니다. | 해시 비교 없이 보존됐다고 주장하거나 상태·승인 장부를 삭제했습니다. |
| 화면 | 넓은 화면·390px 화면, 메뉴·검색·근거 접기와 이동·그림 확대·Escape를 조작한 기록이 있습니다. | HTML 검사만 하고 실제 화면 조작도 통과했다고 기록했습니다. |

자세한 읽기 과제는 [독자별 품질](../concepts/reader-quality.md), 화면 동작은 [사이트 계약](../concepts/site.md), 집필은 [style/README.md](../../style/README.md)가 단일 기준입니다. 결과를 바꾸는 의미 오류·필수 누락·끊어진 근거는 해결 전 합격 처리하지 않습니다. 경미한 편집 항목은 영향·담당자·후속 조치를 남깁니다. 실제 ADHD 독자의 이해도는 측정하지 않았으므로 보장하지 않습니다.

사내 게시 완료에는 허용된 목적지, 조직의 승인 정책, 게시된 산출물의 해시 대조가 추가로 필요합니다. 사람 승인과 실기기 결과는 자동 검사나 에이전트 평가로 대신하지 않습니다.

## 실패 시 복구

**실패한 단계 이후로 진행하지 말고, 직전 정상 결과와 현재 증거를 보존합니다.** [문제 해결의 공통 복구 절차](troubleshooting.md#공통-복구-절차)가 기준입니다.

| 막힌 지점 | 돌아갈 단계 |
|---|---|
| ZIP 무결성·의존성 | 원본 ZIP 재확인 → 대상 OS·CPU·Python과 wheel 확인. 제품 소스를 바꾸지 않습니다. |
| compile DB·헤더·진입점 | 실행 순서 1~3. 제품 빌드 근거를 고쳐 다시 추출합니다. |
| 필수 답변·근거 해시·서로 다른 커밋 | 실행 순서 4. 이전 설명과 바뀐 소스를 대조한 뒤 추출·계약·생성을 함께 갱신합니다. |
| 중복·한도·깨진 링크·자산 | 실행 순서 5~6. 설정 또는 생성기를 수정하고 다시 생성합니다. |
| update의 범위 검토·기준 이력 변경 | [갱신 복구](troubleshooting.md#갱신-update). 기존 상태를 보존한 새 설정에서 기준을 재설정합니다. |
| 사람 승인·게시·원격 불일치 | 검증된 로컬 결과와 기존 게시본을 유지하고 승인 또는 게시 단계만 재개합니다. |

## 완료 기록

사내 설정 저장소에 [handoff 템플릿](../../examples/inhouse-template/handoff.md)을 채웁니다. 실행 명령·종료 코드·로그, 입력 SHA, 역할별 답변, 반복·실패 전후 파일 해시, 화면 증거와 남은 결정의 경로를 적습니다. 체크 표시만 남기지 않습니다. `build/`와 승인 장부의 백업·복구 위치도 기록합니다.

## 패키지 재생성

공개 생성기 관리자는 검토·커밋한 버전에서 다음 명령으로 ZIP과 체크섬을 만듭니다. 작업 트리의 미커밋 파일은 포함하지 않습니다. 사내 설정·산출물을 추가한 저장소에서 공개 반입 패키지를 만들지 않습니다.

```bash
python tools/build_inhouse_package.py --ref HEAD --out build/import/camera-hal-sdd-inhouse.zip
```

같은 커밋은 같은 파일과 ZIP 해시를 만듭니다. 기존 ZIP을 덮어쓰지 않으므로 새 출력 이름을 사용합니다. Git 이력·원격, 로컬 설정·로그·facts·생성 원고, 호스트 가상 환경과 공개 배포용 에이전트 지시는 제외합니다. 루트 `AGENTS.md`는 반입 환경용 지시로 대체하며 원본 위치를 manifest에 기록합니다. 공개 시험의 작은 요약 기록은 문서 링크를 위해 포함하지만 깊은 경로의 과거 모델 원시 응답·프롬프트 묶음은 제외합니다. 과거 실험 전체 재현에는 원래 공개 저장소의 보관 자료가 필요합니다. 공개 예제와 회귀 소스는 참고용으로 포함되며 사내 계약 답변의 대체물이 아닙니다.


## 이 패키지에서 확인한 범위

최초 반입 패키지 검증에서는 공개 mini HAL의 기존 검증 입력으로, ZIP을 공백이 있는 다른 경로에 풀어 동봉한 생성기를 실행했습니다. 반입 파일 해시와 안내 문서의 로컬 링크를 검사했고 doctor·generate·audit-docs·export-site·verify-site가 통과했습니다. 반복 manifest는 같았고, 필수 답변을 제거한 시험에서는 생성·사이트 반영이 차단되면서 기존 파일 123개가 보존됐습니다. 설정을 복구한 뒤 같은 명령으로 정상 재개했습니다.

독자 기준 수정 뒤에도 ZIP을 별도 경로에 풀어 동봉한 생성기와 Vendor·Developer 계약으로 generate·audit-docs·export-site·verify-site를 다시 실행했습니다. 현재 독자 기준과 공개 검증 범위는 [수정 기록](records/developer-reader-correction.md)에 있습니다.

이후 공개 배포 문서만 읽은 새 에이전트가 발견한 진단·근거 탐색 장애와 보완 결과는 [독립 읽기 시험](records/deployed-reader-evaluation.md)에 있습니다. 사내에서도 같은 과제를 제품 문서로 다시 수행해야 합니다.

패키지 회귀는 같은 커밋의 ZIP 동일성, 미커밋·로컬 산출물 제외, 파일 변조·누락·추가 차단, 복구 후 성공, 다른 작업 디렉터리에서의 실행과 실패 종료 코드 보존을 검사합니다. 실제 압축 해제 중 발견한 Windows 긴 경로 문제는 반입에 필요하지 않은 과거 모델 원시 실행 자료를 제외해 해결했습니다.

이 시험은 기존 Windows Python 환경과 이미 검증한 공개 facts·계약을 사용했습니다. 새 사내 계약 작성, 사내 OS별 폐쇄망 의존성 설치, 제품 툴체인·ABI·실기기·사내 게시를 수행한 결과는 아닙니다. 사내 에이전트는 위 합격 기준을 해당 제품으로 다시 확인해야 합니다.
