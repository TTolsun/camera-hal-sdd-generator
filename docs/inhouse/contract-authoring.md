# 소스에서 계약 작성하기

**사내 에이전트가 실제 소스를 읽고 `config/sections.yaml`에 계약 초안을 작성합니다.** 빈칸을 사람에게 넘기는 절차가 아닙니다. 작성할 수 없는 답은 근거 부족을 드러내고, 확인 가능한 계약은 계속 완성합니다.

| 지금 할 일 | 이동할 절 |
|---|---|
| 문서가 답할 질문을 정합니다. | [1. 질문과 담당 문서](#1-질문과-담당-문서) |
| 답을 소스에 연결합니다. | [2. 발췌와 답변 연결](#2-발췌와-답변-연결) |
| 의미와 읽기 흐름을 확인합니다. | [3. 문장별 대조](#3-문장별-대조) |
| 코드 변경을 반영합니다. | [4. 근거 변경 재검토](#4-근거-변경-재검토) |

## 1. 질문과 담당 문서

**요청 제출 → 작업 큐 → 완료 통지 → 정지 경로를 먼저 조사합니다.** 함수 이름만 보고 의미를 추정하지 않습니다. 실제 제품에 다른 경로가 있으면 그 경로를 사용합니다.

1. facts의 기준 SHA와 같은 소스에서 공개 인터페이스, 호출자·피호출자, 큐 생산자·소비자, 콜백, 오류 분기, 종료 코드를 읽습니다. 테스트·기존 문서는 보조 근거로 사용합니다. 주석과 구현이 다르면 둘의 차이를 남깁니다.
2. Vendor와 아키텍처의 질문을 [독자 프로필](../reference/sections.md#독자-프로필)에 맞춥니다. 아래 표를 출발점으로 쓰되 실제 코드 식별자와 조건으로 구체화합니다.
3. 한 계약의 상세 설명을 소유할 문서를 정합니다. 다른 문서에서는 독자에게 필요한 결론과 그 문서의 절 링크를 제공합니다. 질문·근거를 삭제해서 중복을 줄이지 않습니다.
4. 제출·완료·정지 한 경로가 완성되면 제품의 다른 파이프라인·장치·빌드 변형에 빠진 계약이 있는지 확인합니다. 색인에 심볼이 있다는 사실은 설계 설명의 완성을 뜻하지 않습니다.

| 확인할 계약 | Vendor의 질문 | 아키텍처 개발자의 질문 |
|---|---|---|
| 입력과 책임 | 입력 포맷·상태·유효성 조건은 무엇입니까? | 책임을 어느 모듈이 맡습니까? |
| 소유권과 경계 | 요청과 버퍼를 누가 언제까지 소유합니까? | 프로세스·드라이버·콜백 경계에서 무엇을 넘깁니까? |
| 완료와 수명 | 제출 반환과 완료 통지는 어떻게 다릅니까? | 생성·재구성·종료 시 자원 수명은 어떻게 변합니까? |
| 오류와 동시성 | 오류·취소 후 무엇을 회수해야 합니까? | 스레드와 잠금은 무엇을 보호합니까? |
| 검증 | 어떤 로그·상태·테스트로 결과를 확인합니까? | 변경 시 어떤 경로와 실행 조건을 검증해야 합니까? |

예를 들어 소유권 상세는 객체·버퍼 문서, 완료 구현은 파이프라인 문서, 증상별 확인 순서는 진단 문서가 담당할 수 있습니다. 문서 이름과 분할은 실제 HAL에 맞춰 정합니다.

## 2. 발췌와 답변 연결

**형식은 [sections.yaml 참조](../reference/sections.md#설계-질문과-근거)를 사용합니다.** `<CFG>`는 사내 설정 파일이며 모든 명령은 생성기 루트에서 실행합니다.

1. `design_requirements`에 필수 질문과 프로필의 `aspects`를 선언합니다. `design_topics`에는 질문·제목과 `sources`를 적습니다. 최초 발췌 수집 전에는 `statements`와 `sha256`을 비워 둡니다. 시작 앵커는 파일 안에서 유일해야 하고, 끝 앵커는 그 뒤에서 처음 만나는 지점이므로 실제 발췌 끝을 반드시 확인합니다.
2. `uv run sdd --config <CFG> extract`를 실행합니다. facts의 `evidence["<섹션>/<주제>/<근거>"]`에서 `commit`, `file`, `line`, `end_line`, `text`, `sha256`, `status`를 확인합니다. `available`이 아니면 `reason`을 읽고 선택자를 고칩니다. 경로는 소스 루트 기준입니다.
3. 발췌와 주변 호출 경로를 읽고 `statements`를 작성합니다. 각 주장에 필요한 근거 ID를 `evidence`로 연결하고 답하는 질문 ID를 `covers`에 적습니다. 설명을 확인한 발췌의 해시만 `sources[].sha256`에 옮깁니다.
4. `uv run sdd --config <CFG> generate`를 실행합니다. CLI는 변경한 선택자로 근거를 다시 수집합니다. Python 내부 API를 직접 호출한다면 먼저 `evidence.collect`로 모델을 갱신해야 합니다. 이전 선택자 상태의 facts로 검사를 우회하지 않습니다.
5. `build/design-review.json`에서 모든 필수 질문의 답변·근거 상태를 확인합니다. 계약 초안이 완성되면 [문장별 대조](#3-문장별-대조)를 수행합니다. 이후 사이트 빌드가 이전 facts를 읽지 않도록 CLI가 저장한 facts와 원고의 커밋을 함께 확인합니다.

해시는 발췌가 변하지 않았다는 표시입니다. 에이전트가 작성했다는 사실이나 해시 일치만으로 사람 승인이 생기지 않습니다. `statements`를 채운 계약은 생성기가 그대로 렌더링하므로 별도의 생성기용 LLM 없이도 작성할 수 있습니다.

완성된 형식은 [mini HAL 독자 계약](../../examples/mini-hal/config/reader-sections.yaml)을 참고합니다. 이 예제에는 작업 스레드가 쓰는 포인터의 수명이 보장되지 않는 동작도 포함됩니다. 올바른 HAL 구현으로 복사하지 말고, 실제 동작과 한계를 구분하는 작성 방식만 참고합니다.

## 3. 문장별 대조

**조건 → 동작 → 결과·예외 순서로 설명하고, 증거가 뒷받침하는 범위까지만 주장합니다.** [집필 규칙](../../style/README.md)과 두 원문을 읽고 적용합니다.

| 대조할 항목 | 통과 기준 |
|---|---|
| 근거 범위 | 인용한 발췌에 조건·반환·콜백·해제 동작이 실제로 있습니다. 여러 함수가 필요한 주장은 여러 근거를 연결합니다. |
| 비동기 경계 | 제출 성공을 완료로 바꾸지 않습니다. 함수 포인터·가상 후보·큐를 넘는 실행 순서는 정적 호출 그림만으로 확정하지 않습니다. |
| 수명과 동시성 | 객체·버퍼의 생성자와 해제자, 잠금 범위, 큐에 남은 작업, 정지·재구성 순서를 함께 확인합니다. |
| 실패와 관측 | 실패 반환값·취소·부분 완료를 빠뜨리지 않습니다. 시험 명령·로그 이름은 실제 저장소에서 찾은 것만 적습니다. 실행하지 않은 시험은 계획으로 표시합니다. |
| 읽기와 중복 | 한 문단에 한 주제를 두고 주어와 행동을 밝힙니다. 상세 계약은 담당 문서 한 곳에 두며, 요약 링크로 필요한 답에 도달할 수 있습니다. |

나쁜 설명: “정지하면 모든 작업이 안전하게 끝납니다.” `stop`이라는 이름과 단일 호출만으로는 이 주장을 뒷받침할 수 없습니다.

더 정확한 설명: “정지 함수는 큐를 비운 뒤 작업 스레드가 끝날 때까지 기다립니다.” 이 문장은 두 동작과 순서를 확인한 근거가 있어야 합니다. 실행 중 작업이 참조하는 객체를 먼저 지우는 코드가 있다면 그 사실도 같은 계약에서 설명해야 합니다.

확인하지 못한 드라이버 동작이나 실기기 경쟁 조건은 `kind: limitation`으로 적습니다. 필수 질문에는 별도로 소스로 확인한 동작이 있어야 합니다. 근거가 없으면 “문제없음”으로 채우거나 `limitation`만 붙여 통과시키지 않습니다.

검증 질문에는 확인 가능한 관측 지점과 앞으로 시험할 조건을 구분해 씁니다. “오류를 시험해야 합니다”만으로 끝내지 말고, 소스에 있는 오류 분기·반환·콜백 중 무엇을 관찰할지 연결합니다. 설계 이유나 성능 수치는 코드·결정 기록·측정 근거가 있을 때만 씁니다.

주변 문서를 참조했더라도 필수 질문의 `covers`·근거 연결은 유지합니다. 링크만 있는 답으로 검사를 만족시키지 않습니다. 실제 Vendor와 아키텍처 독자가 할 과제는 [읽기 검증](../concepts/reader-quality.md#역할별-읽기-검증)에 있습니다.

## 4. 근거 변경 재검토

**해시가 달라졌을 때는 기존 설명과 새 구현을 먼저 비교합니다.** 설정 변경 때문에 선택 범위가 달라진 경우도 같은 방식으로 대조합니다.

1. 이전·새 SHA에서 발췌와 주변 경로의 diff를 읽습니다. 변경된 조건·상태·소유권·완료·오류를 정리합니다.
2. 기존 설명이 틀리면 설명과 연결 근거를 수정합니다. 여전히 맞으면 왜 그런지 인수인계 기록에 남깁니다. 판단하지 못하면 기존 해시를 유지하고 미완료 질문으로 기록합니다.
3. 대조가 끝난 발췌에만 새 해시를 적고 `generate`와 문서·사이트 검증을 다시 실행합니다. `needs-review`나 갱신 실패가 해시 변경만으로 해결되었다고 보고하지 않습니다.
4. 사람이 이미 승인한 본문이 바뀌었다면 다시 검토 대상으로 전달합니다. 에이전트는 자동 검사 결과를 사람 승인 장부에 대신 기록하지 않습니다.
