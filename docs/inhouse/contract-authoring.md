# 소스에서 계약 작성하기

기본 사내 템플릿의 `design_generation: llm`에서는 에이전트가 질문·`covers`·소스 범위를 작성하고 사내 LLM이 답변을 생성합니다. `statements`를 직접 작성하지 않습니다. 아래의 해시·`statements` 작성 방식은 직접 검토한 고정 계약을 선택할 때 사용하며 그 섹션의 `design_generation`은 제거합니다. 그림은 `config/visuals.yaml`의 `generation: llm` 질문에서 별도로 자동 생성합니다.

**사내 에이전트가 실제 소스를 읽고 `config/sections.yaml`에 계약 초안을 작성합니다.** 빈칸을 사람에게 넘기는 절차가 아닙니다. 작성할 수 없는 답은 근거 부족을 드러내고, 확인 가능한 계약은 계속 완성합니다.

| 답을 소스에 연결합니다. | [2. 발췌와 답변 연결](#2-발췌와-답변-연결) |

| 코드 변경을 반영합니다. | [4. 근거 변경 재검토](#4-근거-변경-재검토) |

## 1. 질문과 담당 문서

**요청 제출 → 작업 큐 → 완료 통지 → 정지 경로를 먼저 조사합니다.** 함수 이름만 보고 의미를 추정하지 않습니다. 실제 제품에 다른 경로가 있으면 그 경로를 사용합니다.

1. facts의 기준 SHA와 같은 소스에서 공개 인터페이스, 호출자·피호출자, 큐 생산자·소비자, 콜백, 오류 분기, 종료 코드를 읽습니다. 테스트·기존 문서는 보조 근거로 사용합니다. 주석과 구현이 다르면 둘의 차이를 남깁니다.
2. For Vendor는 기술 채택을 검토하고 연동·구현 범위를 정하는 담당자, For Developer는 신입·타팀 개발자입니다. 처음 읽을 파일과 진입점, 용어 설명, 한 요청을 따라갈 순서를 먼저 정합니다. Vendor와 Developer의 질문을 [독자 프로필](../reference/sections.md#독자-프로필)에 맞춥니다. 아래 표를 출발점으로 쓰되 실제 코드 식별자와 조건으로 구체화합니다.
3. 한 계약의 상세 설명을 소유할 문서를 정합니다. 다른 문서에서는 독자에게 필요한 결론과 그 문서의 절 링크를 제공합니다. 질문·근거를 삭제해서 중복을 줄이지 않습니다.
4. 제출·완료·정지 한 경로가 완성되면 제품의 다른 파이프라인·장치·빌드 변형에 빠진 계약이 있는지 확인합니다. 색인에 심볼이 있다는 사실은 설계 설명의 완성을 뜻하지 않습니다.

| 확인할 계약 | Vendor의 질문 | 신입·타팀 개발자의 질문 |
|---|---|---|
| 기능·강점·제약 | 무엇을 제공하며 어떤 구현이 강점을 뒷받침합니까? 어떤 조건에서 지원되지 않거나 별도 검증이 필요합니까? | 기능의 구현 위치와 변경 영향을 어디에서 찾습니까? |
| 첫 코드 탐색 | 구현할 인터페이스는 어디에 있습니까? | 어느 파일·함수부터 읽고 요청·결과를 어떻게 따라갑니까? |
| 입력과 책임 | 입력 포맷·상태·유효성 조건은 무엇입니까? | 책임을 어느 모듈이 맡습니까? |
| 소유권과 경계 | 요청과 버퍼를 누가 언제까지 소유합니까? | 프로세스·드라이버·콜백 경계에서 무엇을 넘깁니까? |
| 완료와 수명 | 제출 반환과 완료 통지는 어떻게 다릅니까? | 생성·재구성·종료 시 자원 수명은 어떻게 변합니까? |
| 오류와 동시성 | 오류·취소 후 무엇을 회수해야 합니까? | 스레드와 잠금은 무엇을 보호합니까? |
| 검증 | 어떤 로그·상태·테스트로 결과를 확인합니까? | 변경 시 어떤 경로와 실행 조건을 검증해야 합니까? |

제품 개요는 `vendor-overview`로 기능·강점, 연동 가이드는 `vendor`로 구현 계약, 지원 범위와 검증은 `vendor-assurance`로 조건·검증 근거를 채웁니다. 제품별 해상도·성능·지원 조합을 소스만으로 확정할 수 없으면 검증 범위를 밝히고 근거가 있는 동작까지만 설명합니다. 측정 결과가 없는 상태를 미지원 판정으로 바꾸지 않습니다. 공통 프로필에는 제품명·빌드 시스템·호스트·모델·게시 방식을 넣지 않습니다.

제목(`title`)은 “요청과 버퍼 수명”처럼 짧은 주제로, 질문(`question`)은 “누가 언제까지 소유합니까?”처럼 검토할 문장으로 나눕니다. `routes`에는 독자의 할 일을 쓰고 담당 절로 연결합니다. 다른 페이지로 보내는 링크에도 절 앵커를 붙여 독자가 긴 페이지에서 다시 찾지 않게 합니다.

예를 들어 소유권 상세는 객체·버퍼 문서, 완료 구현은 파이프라인 문서, 증상별 확인 순서는 진단 문서가 담당할 수 있습니다. 문서 이름과 분할은 실제 HAL에 맞춰 정합니다.

## 2. 발췌와 답변 연결

**형식은 [sections.yaml 참조](../reference/sections.md#설계-질문과-근거)를 사용합니다.** `<CFG>`는 사내 설정 파일이며 모든 명령은 생성기 루트에서 실행합니다.

1. `design_requirements`에 필수 질문과 프로필의 `aspects`를 선언합니다. `design_topics`에는 질문·제목과 `sources`를 적습니다. 최초 발췌 수집 전에는 `statements`와 `sha256`을 비워 둡니다. 시작 앵커는 파일 안에서 유일해야 하고, 끝 앵커는 그 뒤에서 처음 만나는 지점이므로 실제 발췌 끝을 반드시 확인합니다.
2. `uv run sdd --config <CFG> extract`를 실행합니다. facts의 `evidence["<섹션>/<주제>/<근거>"]`에서 `commit`, `file`, `line`, `end_line`, `text`, `sha256`, `status`를 확인합니다. `available`이 아니면 `reason`을 읽고 선택자를 고칩니다. 경로는 소스 루트 기준입니다.
3. 발췌와 주변 호출 경로를 읽고 `statements`를 작성합니다. 각 주장에 필요한 근거 ID를 `evidence`로 연결하고 답하는 질문 ID를 `covers`에 적습니다. 설명을 확인한 발췌의 해시만 `sources[].sha256`에 옮깁니다.
4. `uv run sdd --config <CFG> generate`를 실행합니다. CLI는 변경한 선택자로 근거를 다시 수집합니다. Python 내부 API를 직접 호출한다면 먼저 `evidence.collect`로 모델을 갱신해야 합니다. 이전 선택자 상태의 facts로 검사를 우회하지 않습니다.
5. `build/design-review.json`에서 모든 필수 질문의 답변·근거 상태를 확인합니다. 계약 초안이 완성되면 [문장별 대조](#3-문장별-대조)를 수행합니다. 이후 사이트 빌드가 이전 facts를 읽지 않도록 CLI가 저장한 facts와 원고의 커밋을 함께 확인합니다.

해시는 발췌가 변하지 않았다는 표시입니다. 에이전트가 작성했다는 사실이나 해시 일치만으로 사람 승인이 생기지 않습니다. `statements`를 채운 계약은 생성기가 그대로 렌더링하므로 별도의 생성기용 LLM 없이도 작성할 수 있습니다.

완성된 형식은 [mini HAL 독자 계약](../../examples/mini-hal/config/reader-sections.yaml)을 참고합니다. 이 예제에는 작업 스레드가 쓰는 포인터의 수명이 보장되지 않는 동작도 포함됩니다. 올바른 HAL 구현으로 복사하지 말고, 실제 동작과 한계를 구분하는 작성 방식만 참고합니다.

## 3. 문장별 대조

**조건 → 동작 → 결과·예외 순서로 설명하고, 증거가 뒷받침하는 범위까지만 주장합니다.** [집필 규칙](../../style/README.md)과 두 원문을 읽고 적용합니다.

| 대조할 항목 | 통과 기준 |
|---|---|
| 근거 범위 | 인용한 발췌에 조건·반환·콜백·해제 동작이 실제로 있습니다. 여러 함수가 필요한 주장은 여러 근거를 연결합니다. 가능한 경우 함수·분기 단위로 발췌를 좁히고, 전체 파일이 필요하면 확인할 함수 이름을 설명에 적습니다. `available`은 의미 대조를 대신하지 않습니다. |
| 비동기 경계 | 제출 성공을 완료로 바꾸지 않습니다. 함수 포인터·가상 후보·큐를 넘는 실행 순서는 정적 호출 그림만으로 확정하지 않습니다. 콜백 실행 스레드와 호출 시점을 확인하고, 제출 반환 전 통지가 가능한지도 구분합니다. |
| 수명과 동시성 | 객체·버퍼의 생성자와 해제자, 잠금 범위, 큐에 남은 작업, 정지·재구성 순서를 함께 확인합니다. 객체 생성과 내부 자원의 지연 초기화를 구분합니다. |
| 콜백 재진입 | 외부 콜백을 부르는 동안 유지되는 포인터·잠금·스레드를 확인합니다. 콜백에서 정지·종료·재제출할 수 있는지 호출 경로를 따라가고, 금지 규약이 없다면 해제 후 접근·동일 스레드 join·잠금 재획득 가능성과 미확인 조건을 적습니다. |
| 빌드 변형 | 사용한 매크로의 정의 여부와 값, 실제 `#ifdef`·`#if` 조건을 대조합니다. 값 0과 미정의를 같은 동작으로 추정하지 않습니다. 분석한 변형과 실행하지 않은 변형을 구분합니다. |
| 실패와 관측 | 실패 반환값·취소·부분 완료를 빠뜨리지 않습니다. 시험 명령·로그 이름은 실제 저장소에서 찾은 것만 적습니다. 실행하지 않은 시험은 계획으로 표시합니다. |
| 읽기와 중복 | 한 문단에 한 주제를 두고 주어와 행동을 밝힙니다. 상세 계약은 담당 문서 한 곳에 두며, 요약 링크로 필요한 답에 도달할 수 있습니다. |

나쁜 설명: “정지하면 모든 작업이 안전하게 끝납니다.” `stop`이라는 이름과 단일 호출만으로는 이 주장을 뒷받침할 수 없습니다.

더 정확한 설명: “정지 함수는 큐를 비운 뒤 작업 스레드가 끝날 때까지 기다립니다.” 이 문장은 두 동작과 순서를 확인한 근거가 있어야 합니다. 실행 중 작업이 참조하는 객체를 먼저 지우는 코드가 있다면 그 사실도 같은 계약에서 설명해야 합니다.

확인하지 못한 드라이버 동작이나 실기기 경쟁 조건은 `kind: limitation`으로 적습니다. 필수 질문에는 별도로 소스로 확인한 동작이 있어야 합니다. 근거가 없으면 “문제없음”으로 채우거나 `limitation`만 붙여 통과시키지 않습니다.

검증 질문에는 확인 가능한 관측 지점과 앞으로 시험할 조건을 구분해 씁니다. “오류를 시험해야 합니다”만으로 끝내지 말고, 소스에 있는 오류 분기·반환·콜백 중 무엇을 관찰할지 연결합니다. 설계 이유나 성능 수치는 코드·결정 기록·측정 근거가 있을 때만 씁니다.

주변 문서를 참조했더라도 필수 질문의 `covers`·근거 연결은 유지합니다. 링크만 있는 답으로 검사를 만족시키지 않습니다. 실제 Vendor와 신입·타팀 개발자가 할 과제는 [읽기 검증](../concepts/reader-quality.md#역할별-읽기-검증)에 있습니다.

## 4. 근거 변경 재검토

**해시가 달라졌을 때는 기존 설명과 새 구현을 먼저 비교합니다.** 설정 변경 때문에 선택 범위가 달라진 경우도 같은 방식으로 대조합니다.

1. 이전·새 SHA에서 발췌와 주변 경로의 diff를 읽습니다. 변경된 조건·상태·소유권·완료·오류를 정리합니다.
2. 기존 설명이 틀리면 설명과 연결 근거를 수정합니다. 여전히 맞으면 왜 그런지 인수인계 기록에 남깁니다. 판단하지 못하면 기존 해시를 유지하고 미완료 질문으로 기록합니다.
3. 대조가 끝난 발췌에만 새 해시를 적고 `generate`와 문서·사이트 검증을 다시 실행합니다. `needs-review`나 갱신 실패가 해시 변경만으로 해결되었다고 보고하지 않습니다.
4. 사람이 이미 승인한 본문이 바뀌었다면 다시 검토 대상으로 전달합니다. 에이전트는 자동 검사 결과를 사람 승인 장부에 대신 기록하지 않습니다.

다음 단계: [문서와 화면 검증](agent.md#3-문서와-화면-검증)으로 이동합니다.


## 사내 LLM 생성 시험

실패 원인을 모델이 분석하고 질문·근거 수정안을 반복 적용하게 하려면 [자동 보완 루프](reader-loop.md)를 사용합니다. 반복·호출·시간 한도와 중단 사유를 기록하며 운영 원고를 승인하거나 게시하지 않습니다.

실제 모델 연결과 제품별 근거를 설정한 뒤 별도 출력 폴더에서 시험합니다. libcamera 공개 예제의 세 문서는 다음 명령으로 평가할 수 있습니다. 사내 템플릿은 먼저 빈 sources와 질문을 실제 HAL 근거로 채우고 `design_generation: llm`으로 전환해야 합니다.

```powershell
python -m sdd.evaluate_reader --config project/sdd.yaml --section vendor-overview --section vendor-integration --section vendor-assurance --out build/reader-trial
```

`--section`에는 해당 설정의 id를 사용합니다. 사내 템플릿의 연동 가이드 id는 `vendor-contract`입니다. `agent.kind`는 `ollama` 또는 `openai-compatible`이어야 합니다. 시험마다 새 폴더를 지정하면 해당 커밋의 근거를 다시 읽고 실제 모델을 호출하여 원고·원응답·검사 결과를 보관합니다. 운영 원고는 덮어쓰지 않습니다. 보고서의 자동 검사 통과는 의미 검토나 게시 승인이 아니며 `publishable`은 항상 false입니다.

질문은 책임 주체 하나와 성공·실패 조건 하나를 중심으로 나눕니다. 선언의 `shall`을 실제 장치가 이미 수행한 동작으로 바꾸거나, 특정 스레드에서 호출하라는 의무를 스레드 안전성의 증거로 확대하지 않도록 질문에 근거 유형을 명시하세요. 결과와 필수 통지 의무는 모두 질문 목록에 남깁니다. 소형 모델이 둘 중 하나를 계속 빠뜨리면 같은 주제 안에서 책임별 질문으로 나누고 두 답변을 함께 게시합니다. 여러 반환 상태를 계속 빠뜨리면 상태마다 질문을 나누되 전체 상태를 빠짐없이 유지합니다.

[답변 계약](../reference/sections.md#답변의-누락과-알려진-오류-검사)에 실제 소스의 필수 용어·대안과 관측한 오류 패턴을 넣습니다. libcamera의 함수 이름이나 정답 문장을 사내 설정에 복사하지 않습니다. 실패 응답을 회귀 사례로 보존하고, 올바른 의무 문장·부정 표현도 함께 시험하여 검증기의 오탐을 확인합니다. 통과를 위해 검사 항목만 없애거나 근거에 없는 단어를 강요하지 않습니다.

소형 모델이 첫 동작만 쓰거나 페이지 지침을 반복하면 `review.design_prompt: focused`를 비교 시험합니다. 이 모드에서는 `paths.prompts` 아래 `focused-design-system.md`를 읽고, 한 번의 호출에 해당 질문·근거·JSON 출력 예시만 보냅니다. `design-system.md`와 전체 페이지 집필 지침을 문단 호출에 덧붙이지 않습니다. 모델에 보내지 않는 집필 규칙도 최종 페이지와 검토에 적용하며, 스타일 파일 변경은 기존 답변 재사용을 무효화합니다. 기본 `standard` 모드는 기존 프로젝트 프롬프트를 유지합니다. 공개 9B 비교에서는 짧은 지침이 일부 개별 질문을 개선했지만 전체 문서 정확성을 안정적으로 확보하지 못했습니다. 집중 작성을 기본값으로 채택하지 말고 실제 대상 문서에서 비교하세요.

하나의 분할 질문에서는 주체와 근거 유형도 맞춥니다. 호출자의 의무와 함수의 반환 정보·허용 동작을 함께 묻고 모든 답에 의무형을 강제하면, 소형 모델이 설명 부분을 빠뜨릴 수 있습니다. 필수 의무에는 `basis: contract`, 문서에 명시된 기능·허용 범위에는 `basis: description`, 실제 코드 동작에는 `basis: implementation`을 사용하고 각각의 질문을 같은 주제 안에 모읍니다. 공통 프롬프트에 넣은 사실 예시가 다른 함수의 답변으로 복사되는지도 확인하세요. 실제 근거가 아닌 예시 문장을 현재 프로젝트의 사실로 제공하지 않습니다.

발췌를 줄일 때는 **질문에 필요한 조건과 결과를 함께 남깁니다.** 같은 발췌에 있는 서로 다른 함수 계약은 나누고, 선언의 의무와 공통 구현의 관측 동작도 구분합니다. 제어 흐름을 설명할 때는 바깥 조건·실패 분기·마지막 검사를 잘라내지 않습니다. 질문에서도 객체 등록과 클래스 등록처럼 대상이 다른 동작을 구분하세요. 용어 검사는 실제로 관측한 올바른 번역을 대안으로 인정하되, 누락한 조건까지 통과시키지 않습니다.

동일한 반환·스레드 문구가 여러 함수에 반복되면 `sources[].scope`로 해당 함수 안에서만 발췌를 찾습니다. `scope`를 지정한 근거는 표준·집중 작성 모두 선택한 발췌 전체를 하나의 인용 ID로 제공합니다. 집중 작성에서는 나머지 근거도 같은 방식으로 제공합니다. 따라서 조건문·루프·최종 검사를 함께 설명할 때 모델이 여러 ID를 하나로 합칠 필요가 없습니다. 실제 원문과 줄 번호·해시는 그대로 검증합니다. 짧은 선언 계약은 책임별로 분리하되, 구현의 제어 흐름은 필요한 범위를 온전히 유지하세요.

프롬프트 변경은 같은 질문·근거·JSON 스키마로 비교하고, 전체 문서 시험으로 이어갑니다. “더 짧게”, “전체 집필 규칙 준수” 같은 지시를 추가했다고 정확도가 높아진다고 가정하지 마세요. 첫 문장만 남기는지, 의무를 동작으로 바꾸는지, 근거 밖 이유를 붙이는지 원응답으로 확인합니다. 실패를 사람 원고로 대신 채운 결과를 모델 작성 성공으로 세지 않습니다.

같은 입력과 모델 설정으로 반복 실행한 뒤 자동 검사와 작성자의 소스 대조 결과를 따로 기록합니다. 평가 폴더에는 질문 설정 사본, 질문·생성 코드 해시, 실제 HTTP 요청·응답 기록이 남습니다. 실행 중 코드·집필 규칙을 바꾸지 말고 새 시험으로 분리하세요. 답변의 주체, 조건, 반환값, 의무 표현과 측정 범위를 문장마다 대조하고, 독립 검토가 아니면 작성자 자체 대조라고 표시합니다. 공개 9B 재시험은 [오류 분석과 후속 작성 시험](../libcamera/records/vendor-9b-focused.md)을 참고합니다.

같은 소스에서 질문을 고친 뒤에는 다음 명령으로 원응답을 검증해 재사용하면서 바뀐 요청만 실제 모델에 보낼 수 있습니다.

```powershell
python -m sdd.repair_reader --config project/sdd.yaml --seed build/reader-trial --section vendor-contract --out build/reader-repair
```

이 경로는 **HTTP 응답 재생과 새 모델 호출을 결합한 보완 실행**입니다. `evaluate_reader`의 새 전체 모델 시험과 구분합니다. 원요청·원응답 해시, 실제 HTTP 출처, 모델 이름과 생성 설정이 모두 맞아야 가져옵니다. 서로 다른 응답이 같은 입력에 연결되면 선택하지 않고 실패합니다. 소스 커밋도 같아야 하며 코드가 바뀌면 `sdd update` 경로를 사용합니다. 모델 이름이 가리키는 실제 버전도 운영 환경에서 고정하세요.

재사용한 응답도 현재 근거·스키마·답변 계약으로 다시 검사합니다. 바뀐 질문·근거·프롬프트는 요청 해시가 달라 실제 모델 호출을 거칩니다. 원고에는 `response-bundle/<모델>`을 기록하고, 원래 HTTP 영수증은 `calls/`, 새 호출은 `new-prompts/`, 재생 영수증은 `replay-prompts/`에 분리합니다. 보고서에는 재사용 수, 새 HTTP 시도·완료 수를 따로 적습니다. 원응답을 고쳐 쓰거나 재생을 새 전체 모델 성공으로 세지 않습니다. 자동 검사·의미 대조·사람 승인은 여전히 별개입니다.

구매·홍보에 사용할 문서에는 코드뿐 아니라 제품 사양, 지원 조합, 측정 환경·방법·결과와 적용 버전도 필요합니다. 같은 소스 저장소의 버전 관리된 사양·시험 보고서를 `sources`로 연결할 수 있습니다. 근거가 없으면 성능 우위·지원 보장·양산 준비 완료를 만들지 않습니다. 고객 요구 충족 여부와 대외 공개 가능 범위는 제품 담당자가 확인합니다. 공개 예제의 자동 생성 성공을 사내 모델·실제 HAL의 검증 완료로 바꾸지 않습니다.

영어판도 한국어 원고와 별도로 대조합니다. 번역기는 명시적인 프로젝트 용어집의 기존 번역만 용어 힌트로 제공하며, 화면 버튼 이름을 본문의 일반 명사 번역으로 사용하지 않습니다. 코드 자리표시자가 빠지면 누락·중복된 ID를 재질문에 명시하고, 의무 표현이 사라지면 다시 작성하게 합니다. `must`가 한 번 있다는 사실만으로 모든 절의 의무가 보존됐다고 판단할 수는 없습니다. 조건·주어·복수 대상·부정과 허용 범위를 문장별로 확인하세요.
