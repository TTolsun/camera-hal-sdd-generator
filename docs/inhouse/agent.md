## 전달할 지시문

아는 경로만 채우세요. 스킬 설치 없이도 생성기 저장소의 파일을 직접 읽고 수행할 수 있습니다. 반복 사용 시에는 [스킬 설치 안내](../../skills/README.md)를 따릅니다.

```text
생성기 저장소: <사내에 반입한 camera-hal-sdd-generator 절대 경로>
HAL 소스: <알고 있으면 사내 경로>
제품·빌드 변형: <알고 있으면 기입>

생성기 저장소의 skills/camera-hal-sdd/SKILL.md를 읽고 적용해줘.
docs/inhouse/agent.md의 실행 절차에 따라 설정부터 계약 작성·검증까지 수행해줘.
설정 예시만 만들거나 빈 계약을 사람에게 채우라고 넘기는 것으로 끝내지 마.

환경에서 소스·제품 빌드·compile DB·생성 헤더·기준 커밋을 조사하고,
찾을 수 없는 필수 정보만 질문해줘. 나머지 독립적인 작업은 계속해줘.
Vendor와 아키텍처 개발자가 필요한 답을 찾도록 두 reader_profile을 유지하고,
실제 소스에 근거한 design_requirements와 design_topics를 직접 작성해줘.
요청 제출·완료·정지 경로를 먼저 연결한 뒤, 확인한 제품 범위에 확장해줘.
한 계약은 한 문서에서 자세히 설명하고 다른 문서는 요약과 링크로 연결해줘.

생성 원고와 HTML은 직접 고치지 말고 설정 또는 생성기에서 수정해줘.
소스에서 확인한 동작, 에이전트의 검토, 실기기 시험, 사람 승인을 구분해줘.
사람 승인이나 실행 결과를 만들어 내지 마. 승인 전 검증 가능한 일은 끝내줘.
소스·설정·facts·원고·프롬프트·로그는 사내에만 보관해줘.
공개 libcamera 배포 지시는 사내 입력에 적용하지 마.

게시와 예약 설치는 이미 허용된 사내 대상·범위에서만 진행해줘.
대상이 없으면 검증된 로컬 산출물과 남은 게시 단계를 남겨줘.
끝나면 사내 설정 저장소에 handoff.md를 작성하고 단계별 완료 증거를 보고해줘.
```

## 1. 환경과 데이터 경계

**공개 생성기와 사내 입력·출력을 별도 저장소에 둡니다.** 분석 전용 HAL 체크아웃을 쓰며 개발 중인 체크아웃의 변경을 지우거나 전환하지 않습니다.

1. 생성기 버전, 소스 SHA, 제품·ABI·빌드 변형, 빌드 명령, 생성 헤더와 compile DB를 확인합니다. [준비물](01-prepare.md)은 NDK-build 사례입니다. 다른 빌드 시스템이면 실제 제품의 DB 생성 절차를 조사합니다.
2. [사내 템플릿](../../examples/inhouse-template/)을 사내 설정 저장소로 복사합니다. `sdd.yaml`의 경로와 `paths.*`를 실제 배치에 맞춥니다. 로컬 덮어쓰기 파일도 읽어 최종 설정을 확인합니다.
3. 소스 열람 주소·코드 링크 형식·게시 대상·LLM 목적지·정적 자산 위치를 정합니다. 사내 정책에서 허용된 대상만 사용하고, 자격 증명은 환경 변수나 사내 비밀 저장소로 전달합니다. 로그에 토큰을 남기지 않습니다.
4. 승인 전 로컬 미리보기와 게시 정책을 구분합니다. 새 템플릿의 `site.require_approval: false`는 초안 확인용입니다. 기존 게시 관문을 실패 회피 목적으로 내리지 않습니다. 사내 게시 전에는 사람 승인 정책에 맞춰 관문을 적용합니다.

설정 키의 기준은 [sdd.yaml 참조](../reference/config.md)입니다. 다음 선택은 제품에 맞게 결정합니다.

| 확인한 환경 | 적용할 설정과 작업 |
|---|---|
| NDK-build | 템플릿의 `source.ndk_build`를 사용하고 제품과 같은 인자로 `compdb`를 실행합니다. |
| 다른 빌드 시스템 | `source.ndk_build.enabled: false`로 두고 제품 빌드에서 얻은 DB를 `source.compile_commands`에 지정합니다. 필요하면 `compdb --normalize`를 사용합니다. `simple_compdb`의 시험용 플래그를 제품 빌드 대신 쓰지 않습니다. |
| 커밋별 갱신 | NDK 자동 재생성을 쓰거나 실제 DB 재생성 명령을 `update.compdb_cmd`에 인자 목록으로 지정합니다. 이전 커밋의 헤더·DB를 재사용하지 않습니다. |
| 생성기용 모델이 없음 | `agent.kind: dry-run`을 유지합니다. 사내 에이전트가 근거 있는 `statements`를 모두 작성하고 나머지는 facts 기반으로 생성하면 문장 모델을 호출하지 않습니다. 모델 설명용 빈 주제를 dry-run 상태로 남기고 완성했다고 하지 않습니다. |
| 외부망이 없음 | 사내 패키지 미러 또는 반입한 의존성을 사용합니다. Mermaid는 승인된 tarball을 `fetch-mermaid --tarball <파일>`로 준비합니다. 외부 CDN 기본값에 의존하지 않습니다. |

에이전트 자체도 사내 소스를 처리하도록 허용된 환경에서 실행되어야 합니다. 생성기의 `agent.kind`는 작업 중인 에이전트의 연결 대상을 바꾸지 않습니다.

**완료 증거:** 비밀 값을 제외한 환경 결정, 실제 경로, 제품 빌드 명령, 기준 SHA, 사내 보관·게시 대상입니다. 제품 변형을 확인하지 못했다면 해당 분석의 범위를 확정하지 않습니다.

## 2. 추출과 계약 작성

**클래스 색인에서 멈추지 않고 두 독자의 계약을 작성합니다.** 아래 명령은 생성기 루트에서 실행합니다. `<CFG>`는 사내 설정 파일의 실제 경로로 바꿉니다.

1. 제품의 compile DB와 생성 헤더를 준비합니다. NDK-build이면 `uv run sdd --config <CFG> compdb`를 먼저 실행합니다. 다른 빌드에서는 위에서 확인한 DB 생성 명령을 실행합니다.
2. `uv run sdd --config <CFG> doctor`로 환경을 확인합니다. 시나리오는 실제 정의의 완전한 시그니처를 사용합니다. [진입점 규칙](../reference/sections.md#hal3-진입점-작성-규칙)에 따라 큐 소비 함수와 콜백 경계를 구분합니다.
3. `uv run sdd --config <CFG> extract`로 사실을 추출합니다. 파싱 오류·진입점 누락이 없고, compile DB의 TU와 주요 모듈이 실제 빌드 범위에 맞는지 확인합니다. 클래스 수가 많다는 사실만으로 완전성을 판단하지 않습니다.
4. [소스에서 계약 작성하기](contract-authoring.md)를 수행합니다. Vendor·아키텍처의 필수 질문에 답하고, 발췌·해시·`covers`를 연결합니다. `components` 색인은 유지하되 계약 설명을 대신하게 하지 않습니다.
5. `config/glossary.yaml`에 약어의 뜻과 문맥을 채우고 `generate`를 실행합니다. 근거가 부족한 필수 질문이 있으면 관련 구현과 테스트를 더 조사합니다. 여전히 모르면 해당 질문과 막힌 이유를 남기고 생성 완료로 처리하지 않습니다.

**완료 증거:** facts의 `meta.source_commit`, 추출 범위, 두 프로필의 질문별 답변, 발췌 위치·해시, `build/design-review.json`입니다. 전부 `documented`여도 의미가 맞다는 승인으로 간주하지 않습니다.

## 3. 문서와 화면 검증

**자동 검사 뒤에 에이전트가 문장과 원문을 다시 대조합니다.** 자동 검사·에이전트 의미 검토·실기기 시험·사람 승인은 서로 다른 결과로 남깁니다.

1. [집필 규칙](../../style/README.md)과 [독자별 품질 기준](../concepts/reader-quality.md)을 적용합니다. 첫 문장은 할 일이나 결론으로 시작하고, 조건·예외를 유지하면서 문단을 나눕니다. 같은 계약의 상세 설명을 여러 페이지에 복사하지 않습니다.
2. `uv run sdd --config <CFG> audit-docs`를 실행합니다. `build/document-health.md`의 분량·중복 문제는 원본 설정에서 고칩니다. 같은 문장 검사로 발견되지 않는 의미 중복도 읽고 정리합니다.
3. `export-site`, `verify-site`를 같은 설정으로 실행합니다. 입력 커밋과 근거, 링크·해시·용어 검사를 통과시킵니다. 같은 facts·원고·설정으로 `export-site`를 다시 실행해 manifest의 build ID와 파일 해시가 같은지 확인합니다. LLM 재생성까지 동일해야 한다는 뜻은 아닙니다.
4. [로컬 HTTP 미리보기](../concepts/site.md#로컬에서-보기)에서 넓은 화면과 좁은 화면을 확인합니다. 본문·메뉴 넘침, 검색 이동, 코드 링크의 커밋·줄, 그림 확대·검색·Escape 후 초점 복귀, 접힌 근거 열기와 다음 문서 연결을 확인합니다. 브라우저 도구가 없으면 이 항목을 미검증으로 남깁니다.
5. 생성된 문서만 읽고 [역할별 과제](../concepts/reader-quality.md#역할별-읽기-검증)에 답해 봅니다. 찾은 페이지·절과 답변을 기록한 뒤 소스와 대조합니다. 답을 찾지 못하거나 조건을 오해했다면 설정의 설명·이동 경로를 고치고 다시 생성합니다. 이 결과는 에이전트 검토이며 실제 독자 시험을 대신하지 않습니다.

**완료 증거:** 명령·종료 코드, 질문별 대조 결과, 중복 정리 내용, 두 번의 manifest, 화면 확인 결과, 역할별 답변입니다. ADHD 독자의 이해를 자동으로 인증했다고 표현하지 않습니다.

## 4. 반복 운영과 게시

**검증용 상태와 운영 상태를 분리한 뒤 갱신·실패 복구를 확인합니다.** 정확한 명령과 상태 파일은 [갱신 시스템](03-update-system.md)과 [CLI 참조](../reference/cli.md)를 따릅니다.

1. 사내의 별도 분석 체크아웃과 시험 설정에서 실제 변경 전후 두 커밋을 선택합니다. 기준 커밋의 DB·facts·원고를 만든 뒤 `update --to <대상 ref>`를 실행합니다. 기본 브랜치 이름을 `origin/main`으로 추정하지 않습니다.
2. 변경된 계약 발췌가 있는 사례에서 이전 설명·해시가 재검토 대상으로 차단되는지 확인합니다. `contract-authoring.md`의 재검토 절차로 수정한 뒤 같은 명령으로 재개합니다. 그런 이력이 없다면 시험용 복제본에만 명시적인 변경을 만들고, 실제 변경 시험과 구분합니다.
3. 별도 시험 설정에서 필수 답변 하나를 제거해 `generate`와 `export-site`가 실패하는지 확인합니다. 이전 원고·사이트의 해시가 보존되어야 합니다. 시험 설정을 복구해 성공 여부를 확인하며 운영 상태나 승인 장부를 지우지 않습니다.
4. 허용된 사내 게시 방식과 승인 정책으로 게시합니다. HTTP 사이트라면 `verify-publication --url <사내 URL> --site <검증한 사이트>`로 원격 파일을 대조합니다. 인증 방식이 CLI와 맞지 않으면 사내 인증 도구로 같은 manifest·파일 해시를 대조하고 방법을 기록합니다. URL이 열린다는 사실만으로 같은 산출물이 게시되었다고 하지 않습니다.
5. 요청된 CI·예약만 설치합니다. 전용 계정, 커밋별 DB 생성, 영속 상태, 실패 시 재개 위치와 배포 확인을 연결합니다. 공개 libcamera 저장소·Pages·예약을 사내 기본값으로 복사하지 않습니다.

승인이 필요한 경우에도 설정, 원고, 자동 검사와 에이전트 검토까지 끝낸 뒤 [사람 검토](04-review.md) 대상으로 전달합니다. 승인 문서의 내용이 바뀌면 다시 승인을 받아야 합니다.

## 5. 완료 기록

**사내 설정 저장소에 `handoff.md`를 남깁니다.** 이것은 에이전트가 작성하는 인수인계 문서이며 생성기가 자동으로 만드는 보고서가 아닙니다. 아래 항목의 경로는 그 사내 저장소 기준으로 기록합니다.

| 기록 | 반드시 포함할 내용 |
|---|---|
| 입력과 범위 | 생성기 SHA, 소스 SHA, 제품·ABI·빌드 변형, 포함·제외 모듈, 실제 설정과 DB 경로 |
| 계약과 읽기 검토 | 질문 ID → 담당 문서·절 → 근거 → 에이전트 대조 결과, 실패·취소·경계의 미확인 사항, 역할별 과제 답변 |
| 검증 | 실행한 명령·종료 코드·로그 경로, 문서 검사, 반복 빌드, 실패 시 보존·재개, 화면 확인, 실기기 시험 결과 또는 미실행 사유 |
| 운영 | 정확한 재실행 명령, 상태 보존·백업 위치, 사내 게시 대상, 원격 해시 대조 결과, 요청된 CI·예약 정의 |
| 남은 결정 | 사람 승인 대상·상태, 담당자가 확인할 질문, 소스가 없는 경계, 재개할 단계·명령 |

완료 상태는 **초기 경로 검증 / 제품 범위 확장 / 사내 게시 / 사람 승인·실기기 검증**으로 나눠 보고합니다. 미완료 항목이 있으면 다음 실행자가 그대로 이어갈 수 있게 원인과 재개 조건을 적습니다.
