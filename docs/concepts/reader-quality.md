# 사내 HAL에서도 유지할 문서 품질

**Vendor와 신입·타팀 개발자에게 필요한 계약을 먼저 정하고, 실제 소스로 답을 확인한 뒤 생성하세요.** libcamera의 문장이나 클래스 이름을 복사하는 방식으로는 같은 품질을 얻을 수 없습니다.

## 독자별 기준

| 독자 | 반드시 찾을 수 있어야 하는 내용 | 문서에서 할 일 |
|---|---|---|
| Vendor (For Vendor) | 제공 기능, 근거가 있는 강점, 연동 순서와 책임, 지원 조건·제약 및 상세 구현 계약 | 채택·연동 범위를 판단하고 구현·검증 계획을 세웁니다. |
| 신입·타팀 개발자 (For Developer) | 첫 파일·진입점, 용어, 요청과 결과 흐름, 증상별 코드, 수정 후 확인 | 구조를 배우고 코드를 찾아 수정·디버깅합니다. |

처음 읽는 사람에게는 시스템 개요 → 한 요청의 흐름 → 작업별 상세 계약 순서로 안내합니다. 책임·수명·동시성은 이 경로를 이해하는 데 필요한 설명입니다. 아키텍처 설계를 이미 아는 독자를 전제하지 않습니다. 각 읽기 과제는 사전 설명 없이 문서에서 답과 코드 위치를 찾을 수 있어야 통과합니다. 찾지 못한 용어·단계·링크와 실제 답을 기록하고 수정 후 다시 확인합니다.

Vendor 문서는 제품 개요(`vendor-overview`), 연동 가이드(`vendor`), 지원 범위와 검증(`vendor-assurance`)으로 나눕니다. 개요는 고객 문제와 기능·강점, 가이드는 입력·소유권·완료·실패·실행 확인, 검증 문서는 지원 조건과 근거의 한계를 다룹니다. 강점은 구체적 공통 기능이나 확장 경계에 연결하며, 개발 기간 단축·성능 우위·지원 기종을 추정하지 않습니다. 지원하지 않는 조건과 아직 확인하지 않은 조건도 구분합니다. Vendor 공유 범위와 인터넷 공개 범위는 운영 환경에서 별도로 정합니다.

공통 `reader_profile` 검사는 이 항목들이 설계 질문으로 선언되고, 각 질문에 소스 발췌와 연결된 답변이 있는지 확인합니다. libcamera와 사내 템플릿 모두 같은 검사를 사용합니다. 키와 허용 값은 [설정 참조](../reference/sections.md#독자-프로필)에 있습니다.

이 검사는 문장 의미를 승인하지 않습니다. 설명을 잘못 작성해도 소스 해시가 맞을 수 있으므로 [사람 검토](../inhouse/04-review.md)가 필요합니다. 설계 선택의 이유, 성능 예산, 실기기 결과는 추가 근거 없이 추정하지 않습니다.

## 사내에서 처음 채우는 순서

사내 에이전트의 전체 실행은 [에이전트 가이드](../inhouse/agent.md), 발췌·답변 작성은 [계약 작성 절차](../inhouse/contract-authoring.md)를 따릅니다.

1. [사내 템플릿](../../examples/inhouse-template/)의 Vendor·Developer 질문을 실제 모듈과 진입점에 연결합니다.
2. 소스 발췌 위치를 정하고 `extract`로 현재 커밋의 근거를 확보합니다.
3. 각 질문에 답하는 설명과 발췌 해시를 작성합니다. 실패·취소 경로도 확인합니다.
4. `generate`와 `verify-site`를 실행하고, 역할별 독자가 아래 과제를 수행하게 합니다.

빈 답변과 필수 질문 누락은 생성을 중단합니다. 기존 원고와 사이트는 유지합니다. 템플릿의 빈 계약을 채우기 전에는 게시 가능한 첫 문서가 나오지 않습니다.

완성된 작은 예제는 [mini HAL 독자 계약](../../examples/mini-hal/config/reader-sections.yaml)입니다. 이 예제는 종료 시 포인터 수명을 보장하지 못하는 구현까지 설명합니다. 제품용 HAL 구현이나 사내 검증 결과로 취급하지 않습니다. 회귀 테스트는 이 소스의 Git 커밋에서 발췌해 두 독자의 원고와 사이트를 생성하고, 답변 삭제 시 출력이 보존되는지 검사합니다.

## 중복 없이 읽는 구조

한 계약의 상세 설명은 한 문서가 소유합니다. 다른 문서는 필요한 결론을 짧게 요약하고 그 문서로 연결합니다. 예를 들어 소유권은 객체 모델 문서, 완료 구현은 파이프라인 문서, 증상별 확인 순서는 진단 문서에서 관리합니다.

페이지 첫 문장에는 할 일을 적고, 이동 안내는 주요 절까지만 보여 줍니다. 설명을 먼저 싣고 설계 질문 검증표와 소스 원문은 접어 둡니다. 기본 화면은 문단별 근거 행 없이 읽습니다. 절 끝의 `절 전체 근거 N개`를 펼치면 해당 절의 모든 고유 근거를 찾을 수 있습니다. 문단별 연결은 원고 기록과 HTML의 `data-sdd-evidence` 속성에서 검토합니다. 같은 페이지의 동일 발췌는 한 번만 표시하고 설명에서 연결합니다. 원고의 인용을 삭제하지 않으며, 본문 중간의 인용은 그대로 보여 줍니다. 페이지를 따로 전달해도 근거를 볼 수 있도록 서로 다른 페이지의 근거 반복은 허용합니다.

[집필 규칙](../../style/README.md)은 한 문단에 한 주제, 짧은 문장, 단계별 안내를 요구합니다. 독자 프로필은 지나치게 긴 산문 문단도 차단합니다. 자동 중복 검사는 동일 문단을 찾으며 의미가 비슷한 설명의 정리는 편집 검토가 필요합니다. ADHD 독자의 이해를 보장하는 판정이나 임상 검사는 수행하지 않습니다.

## 항목별 시각화 검토

생성·변경·검토 때 사용자의 별도 요청 없이 [집필 규칙](../../style/README.md)의 시각화 기준을 적용합니다. 문장 단위 응답이나 페이지의 그림 수가 아니라 **최종 조립 문서에서 독립된 질문을 설명하는 항목**을 점검합니다. H2와 독립 주제를 가진 H3 이하를 포함하며 부모·자식의 본문을 중복 집계하지 않습니다. 접힌 소스 발췌·검증 로그·원시 호출 목록은 설명 분량과 분리합니다.

설명 본문 600자 이상 또는 설명 문단 3개 이상을 장문 후보의 초기 기준으로 사용합니다. 언어·프로젝트에 맞춰 조정할 때는 기준과 이유를 기록합니다. 여러 상태·단계·조건 분기·책임 주체·소유권을 설명하는 항목은 길이와 관계없이 점검합니다. 이 수치는 후보를 찾는 보조 기준이며 그림의 필요성이나 정확성을 자동으로 판정하지 않습니다. 제목을 잘게 나누거나 근거를 숨겨 점검을 피하지 않습니다.

| 판정 | 검토 기록에 남길 내용 |
|---|---|
| 적절한 그림 있음 | 항목의 질문에 답하는 그림 ID·위치, 본문·근거와의 일치 여부를 기록합니다. |
| 보완 필요 | 빠진 관계·흐름·분기·수명과 필요한 그림의 질문을 기록합니다. |
| 생략 가능 | 짧고 단순함, 간단한 표로 충분함, 같은 질문을 설명하는 인접 그림으로 충분함 등 구체적인 사유를 기록합니다. |
| 근거 부족·미검토 | 확보하지 못한 근거 또는 아직 검토하지 않은 범위를 기록하며 완료로 집계하지 않습니다. |

점검 기록에는 페이지·앵커·항목 ID, 독자 질문, 설명 분량, 그림 ID 또는 생략 사유, 실제 검토한 소스 창과 미검토 범위를 남깁니다. 전체 점검에서는 Vendor·Developer·시나리오·홈·참조 문서와 영어 대응 페이지의 목록을 먼저 확정합니다. 일부 표본의 결과를 전체 완료로 바꾸지 않습니다. 새로 길어진 항목, 이동·분할된 항목, 삭제되거나 오래된 근거 때문에 생략된 그림도 재검토합니다. `visuals.on_stale: omit`으로 그림이 빠졌다면 필요한 그림까지 충족한 것으로 간주하지 않습니다.

핵심 설명 → 그림 → 조건·예외의 배치, 질문과 그림의 대응, 한영 의미, 근거 링크, 모바일 가독성과 기존 그림 조작을 확인합니다. LLM 근거 대조가 필요하면 별도 Codex CLI `gpt-6.1-terra` / `high` 프로필로 검토하고 기존 사람 승인 상태를 유지합니다. focused 모드처럼 짧은 응답만 생성하는 경로도 최종 조립 후 이 검토를 거칩니다. 미해결 보완 필요·근거 부족·미검토는 발행 전에 해결하거나 미완료로 보고하고 직전 정상 산출물을 보존합니다.

위 기준은 작업자의 상시 생성·검토 절차입니다. 공통 자동 누락 검사와 libcamera 전체 보완·배포의 구현 상태는 [이슈 #215](https://github.com/TTolsun/camera-hal-sdd-generator/issues/215)에서 추적합니다. 집필 규칙 변경으로 원고 해시가 달라지면 필요한 재검토를 수행하며 기존 검토 기록을 새 결과처럼 바꾸지 않습니다. 공개 작업의 완료는 생성기 병합, 공개 SDD PR 병합, Pages 배포와 공개 산출물 확인까지 구분하여 기록합니다.

## 역할별 읽기 검증

### 작성 맥락 없이 읽는 시험

새 에이전트나 독자에게는 아래 과제와 **검사할 사이트 주소만** 전달합니다. 작성 대화·설정·저장소·정답표는 주지 않습니다. 사내 문서는 사내에 허용된 에이전트만 사용합니다. 평가 전후의 `site-manifest.json` build_id를 기록하고, 중간에 배포가 바뀌면 섞어 채점하지 말고 같은 배포본에서 다시 수행합니다.

```text
당신은 이 HAL을 처음 맡은 신입·타팀 개발자입니다.
자료는 <검사할 사이트 주소>와 그 안의 코드 발췌뿐입니다.
저장소나 외부 지식으로 빠진 답을 채우지 마세요.
1. 처음 열 파일·함수와 다음 읽을 곳을 찾으세요.
2. 요청 제출부터 완료까지 설명하고 성공 반환과 완료를 구분하세요.
3. 완료가 없을 때 확인할 함수·값·분기와 기록할 항목을 찾으세요.
4. 구성 실패와 정지 문제를 각각 어디서부터 좁힐지 찾으세요.
각 과제의 실제 답, 방문 URL·앵커, 검색어, 막힌 부분을 기록하세요.
근거를 문서 안에서 펼쳐 답을 대조하고, 찾지 못한 것은 미발견으로 남기세요.
실제 실행 결과와 소스에 근거한 조사 계획을 구분하세요.
```

각 과제는 **답·코드 위치·관측값·다음 분기**를 문서에서 찾을 수 있어야 통과합니다. 설정의 질문 선언이나 해시 통과만으로 읽기 시험을 대신하지 않습니다. 구성 실패는 입력·상태 검사와 장치 구현 실패를, 완료 누락은 준비 대기·큐 한도·장치 전달·완료 반환을 구분해야 합니다. 정지 문제는 정지 함수 안의 대기와 반환 뒤 큐·콜백 문제를 나눕니다. 제품에 없는 단계는 근거와 함께 해당 없음으로 기록합니다.

진단 문서는 소스에 있는 함수와 값으로 중단점·계측 위치를 제안할 수 있습니다. 존재하지 않는 로그·실행 명령·지연 기준을 만들지 않으며, 상태를 바꾸는 함수를 관측 목적으로 재호출하지 않습니다. 실제 빌드·기기·추적 수집 방법이 없으면 그 경계를 명시하고 조사 계획으로 표시합니다.

결과를 바꾸는 오답, 필수 단계 미발견, 근거 접근 실패가 있으면 보완 후 같은 과제를 다시 수행합니다. 재평가에는 정답과 수정 내용을 주지 않습니다. 새 에이전트가 없으면 작성자의 자체 검토로 기록하고 독립 평가 합격이라고 쓰지 않습니다. 실제 신입이나 ADHD 독자의 이해도 시험과도 구분합니다.

| 과제 | 확인할 결과 |
|---|---|
| Vendor가 채택·연동 여부를 판단합니다. | 제공 기능과 지원 조건, 강점의 구현 근거와 한계, 연동 순서·구현 책임, 별도 검증할 항목을 문서와 발췌에서 찾습니다. |
| Vendor가 제출 성공 후 완료가 오지 않는 요청을 추적합니다. | 대기 단계, 실패 반환, 완료 통지 조건과 실행 확인 항목을 찾습니다. |
| Vendor가 버퍼를 재사용하려고 합니다. | 누가 언제까지 소유하는지, 재사용 전에 확인할 조건을 찾습니다. |
| 신입 개발자가 처음 소스를 엽니다. | 읽을 첫 파일과 함수, 낯선 용어의 뜻을 찾고 요청 제출부터 결과 통지까지 설명합니다. |
| 타팀 개발자가 완료 누락을 조사합니다. | 증상별 확인 순서와 실제 함수·반환값·콜백을 찾고, 제출 성공과 완료를 구분합니다. |
| 신입·타팀 개발자가 종료 경로를 바꿉니다. | 수정할 파일, 함께 확인할 호출자·스레드·자원 수명과 실행 확인 조건을 찾습니다. |
| 처음 읽는 사람이 설명의 근거를 확인합니다. | 절 전체 근거를 펼쳐 원문을 찾고 분석 커밋과 검토 상태를 구분합니다. |

사내 첫 적용에서는 실제 Vendor와 신입·타팀 개발자가 이 과제를 수행한 기록을 남기세요. 공통 검사는 구조와 근거의 누락을 줄이지만, 실제 HAL 소스와 독자 검토 없이 사내 문서 품질이 검증되었다고 할 수는 없습니다.

공개 mini HAL에서 새 에이전트가 실제로 작성한 결과와 가이드 보완 내역은 [독립 작성 시험 기록](../inhouse/records/mini-hal-forward-test.md)에 있습니다. 이 기록은 자동 검사 통과와 독립 내용 평가가 달랐던 사례를 포함합니다.

신입·타팀 Developer 기준으로 바꾼 내용과 현재 작성 에이전트의 공개 소스 대조 결과는 [독자 기준 수정 기록](../inhouse/records/developer-reader-correction.md)에 있습니다.

배포 문서만 읽은 새 에이전트의 장애와 개선은 [독립 읽기 시험 기록](../inhouse/records/deployed-reader-evaluation.md)에 있습니다.
