# 코드 변경의 문서 범위 검사

`sdd impact`는 재생성할 문서를 고르는 작업과 함께, 변경 파일의 클래스·함수를 선택하는 문서가 있는지 검사합니다. `watch`에 걸려 문서가 재생성된다는 사실만으로 내용까지 포함된다고 판단하지 않습니다. 공통 구현은 `src/sdd/coverage.py`에 있으며 특정 HAL, 빌드 도구나 게시 서비스에 의존하지 않습니다.

## 결과 파일의 뜻

명령과 옵션은 [명령 참조](../reference/cli.md), 사람이 처리하는 절차는 [4단계: 사람 검토](../inhouse/04-review.md#범위-검토-항목-종료-코드-2)에 있습니다.

- `build/impact.json`의 `coverage`에는 항목별 선택 섹션, 이전·현재 근거 위치, 검토 이유, 자동 분류, 제외 파일이 기록됩니다.
- `build/impact-review.md`는 LLM 없이 작성하는 검토 보고서입니다. 문서 생성 시 LLM 요약이 누락하더라도 이 기록은 남습니다.
- 검토 항목이 있으면 `needs-review`, 없으면 `mapped`입니다. `mapped`는 생성된 설명의 정확성이나 사람의 승인을 뜻하지 않습니다.
- 현재 facts는 `--head`, `--base-facts`는 `--base`와 커밋이 일치해야 합니다. 이전 facts가 없으면 같은 파일에서 삭제된 심볼을 놓칠 수 있습니다.
- 승인(accepted)된 항목은 관문 판정에서 빠지고, 보류(deferred)는 기록만 남기고 관문을 유지합니다.


## 판단을 줄이는 두 단계

검토 항목은 파일 단위로 생기므로, 변경되지 않은 클래스가 같은 파일에 있다는 이유만으로 관문에 걸리기 쉽습니다. 사람에게 넘기기 전에 두 단계로 걸러 냅니다.

```
범위 검토 항목
   ├─ 1단계 규칙: 주석·공백·#include 만 다름, 빌드가 읽지 않은 파일,
   │             설계 근거가 파일 전체를 고정한 파일 ──────────▶ 자동 분류 (관문 제외, 승인 아님)
   ├─ 2단계 LLM: 남은 항목의 diff 와 문서 목록으로 판정 ────▶ build/coverage-triage.json (사람 검토 전)
   └─ 3단계 사람: sdd accept --finding (승인 장부)
```

### 1단계: 의미 없는 변경과 빌드 밖 파일의 자동 분류

**빌드 밖 파일.** `extract`는 Clang이 실제로 읽은 소스 루트 안의 파일(컴파일한 TU와 그 include)을 `facts.json`의 `meta.parsed_files`에 남깁니다. 바뀐 C/C++ 파일이 이전·현재 facts의 목록 어디에도 없으면, 그 파일은 분석한 빌드 구성에서 컴파일되지 않는 코드입니다(다른 플랫폼, 꺼진 빌드 옵션, 설치되지 않은 라이브러리). 이런 파일의 변경은 문서 내용을 바꾸지 않으므로 `outside-analyzed-build`로 분류하고, `watch`에 걸려도 문서를 다시 만들지 않습니다.

- 빌드 파일(`meson.build`, `Android.mk`)은 빌드 범위 자체를 바꿀 수 있으므로 분류하지 않습니다.
- 이전 빌드에서 읽던 파일이 빠진 경우는 분류하지 않습니다. 빌드에서 빠진 이유를 사람이 확인해야 하기 때문입니다.
- 이전·현재 facts 중 한쪽이라도 `parsed_files`가 없으면(이전 버전 추출, `--skip-comments`) 분류하지 않습니다.
- 수동 문서의 `evidence_files`에 있는 파일은 사람이 다시 볼 자리이므로 분류하지 않습니다.
- 이 분류는 "분석한 빌드 구성이 문서의 범위"라는 전제를 따릅니다. 그 코드도 문서화하려면 빌드 구성에 넣습니다.

**설계 근거가 고정한 파일.** 튜닝 YAML이나 설정 XML처럼 클래스·함수가 추출되지 않는 파일은 원래 항상 검토 대상입니다. 다시 만드는 문서의 [설계 근거](design-evidence.md)가 그 파일 **전체**를 발췌하고, 그 발췌가 이번 커밋의 내용과 `sha256`으로 일치하면 `pinned-design-evidence`로 분류합니다. 그 문서의 설계 설명이 바로 이 내용을 다루기 때문입니다.

- 발췌 앞뒤에 공백 말고 다른 내용이 있으면 분류하지 않습니다. 발췌 밖의 변경은 설명이 다루지 않습니다.
- `sha256`이 없거나 내용과 다르면 분류하지 않습니다. 파일이 다시 바뀌면 해시가 어긋나서 관문이 다시 멈추고, 설명을 다시 검토하게 됩니다.
- 그 문서가 이번 커밋에서 다시 만들어지지 않으면(`watch`에 걸리지 않으면) 분류하지 않습니다.
- 설명의 내용이 맞는지는 이 분류가 보장하지 않습니다. 그 문서의 사람 검토 대상으로 남습니다.

**의미 없는 변경.** `sdd impact`와 `sdd update`는 변경된 C/C++ 파일의 이전·현재 판을 Git에서 읽습니다. 줄 이음(`\` + 줄바꿈)을 합치고 주석을 지운 뒤, `#include` 줄을 빼고, 리터럴 밖의 공백만 줄여 줄 단위로 비교합니다. 일반·원시 문자열 리터럴은 원문 그대로 비교하고, 줄 경계는 유지합니다. 결과가 같으면 그 파일을 `comment-whitespace-include-only`로 분류합니다. 설정은 없고 항상 동작합니다.

분류한 파일에만 걸린 항목도 **이전·현재 facts에서 구조(종류·기반 클래스·메서드 이름)가 같을 때만** `findings`에서 `coverage.classified`로 옮기고, 보고서의 "자동 분류한 변경" 절에 표시합니다. `#include` 변경이 매크로로 선언을 바꾼 경우를 놓치지 않기 위해서입니다. 이전 facts가 없으면(`--base-facts` 생략) 클래스·함수 항목은 분류하지 않습니다.

- 결과가 늘 같은 규칙이므로 모델을 부르지 않습니다.
- 추가·삭제된 파일과 빌드 파일은 분류하지 않습니다. 빌드 파일 한 줄이 무엇을 바꾸는지는 내용만으로 알 수 없기 때문입니다.
- `__LINE__`이나 `#line`을 쓰는 파일은 주석·빈 줄만 바뀌어도 값이 달라지므로 분류하지 않습니다. 닫히지 않은 주석·리터럴처럼 해석할 수 없는 파일, 토큰 사이 공백까지 바뀐 재정렬도 분류하지 않고 다음 단계로 넘깁니다.
- `#include` 변경이 인라인 함수 본문처럼 facts가 담지 않는 동작을 바꾸는 경우는 구조 비교로도 잡지 못합니다. 이 분류는 "문서 범위 판단이 필요 없다"는 뜻일 뿐이며, 사람의 승인이 아니고 장부에 기록하지 않습니다.

### 2단계: LLM 판정

```yaml
review:
  coverage_triage:
    enabled: true
    pass_gate: false          # true 이면 "범위 밖" 판정이 관문을 통과시킨다
    max_diff_chars: 6000      # 모델에 보여 줄 diff 상한
    agent:                    # 생략한 값은 agent 설정을 따른다
      kind: openai-compatible
      base_url: https://<사내 엔드포인트>
      model: <판정 모델>
```

사람이 승인하지 않은 항목마다 diff와 문서 목록(id, 제목, 독자, 선택 규칙)을 모델에 보여 주고 `out-of-scope`(범위 밖), `needs-document`(문서 추가 필요), `unsure`(판단 불가)와 한 문장 이유를 JSON으로 받습니다.

- 판정은 사람 승인 장부(`sdd/approvals.json`)가 아니라 `build/coverage-triage.json`에 모델 이름·비교 범위·시각과 함께 남습니다. 비교 범위, 항목, 문서 목록, 모델, 지시문이 모두 같을 때만 기록을 재사용합니다. 파일은 원자적으로 쓰고 다른 항목의 기록을 지우지 않습니다.
- 판정 모델의 `base_url`이 문장 생성용 `agent.base_url`과 다르면 `SDD_AGENT_API_KEY` 대신 `SDD_TRIAGE_API_KEY`의 토큰만 보냅니다. 토큰 변수 이름은 설정으로 바꿀 수 없습니다.
- `enabled`와 `pass_gate`는 YAML 불리언(`true`/`false`)만 받습니다. `"false"` 같은 문자열은 설정 오류로 멈춥니다.
- `pass_gate: false`(기본)이면 판정은 보고서에만 표시되고 관문은 그대로입니다. `true`이면 `out-of-scope` 판정만 관문에서 뺍니다. 이 경우에도 보고서에 "사람 검토 전 · 관문 제외"로 표시됩니다.
- 응답이 JSON이 아니거나, 허용되지 않은 값이거나, 이유가 비었거나, 호출이 실패하면 `unsure`로 기록하고 관문을 유지합니다. `agent.kind: dry-run`이면 모델을 부르지 않고 `unsure`로 남깁니다.
- diff와 소스는 지시가 아니라 자료로 다루도록 지시문에 적었지만, 판정의 정확성은 모델에 달려 있습니다. 변경된 소스에 모델을 속이는 문장이 들어 있으면 `pass_gate: true`에서 관문을 통과할 수 있습니다. 그래서 `pass_gate`는 기본값이 꺼져 있고, 외부 기여를 받는 저장소나 사람 승인이 필요한 운영에서는 켜지 않습니다. 켜는 경우에도 판정 기록을 주기적으로 사람이 대조하세요.

## 검토 대상으로 올리는 조건

| 이유 코드 | 의미 | 검토 방법 |
|---|---|---|
| `entity-outside-document-scope` | 변경 파일의 클래스·함수를 선택하는 자동 문서가 없습니다. | 적절한 절의 `facts.classes` 또는 `facts.functions`를 보완하거나 새 절을 정의합니다. |
| `document-not-scheduled` | 대응 문서가 있지만 영향 분석에서 재생성 대상으로 선택되지 않았습니다. | 해당 절의 `watch`와 `impact_classes` 설정을 확인합니다. |
| `no-extracted-entity` | 변경 파일을 클래스·함수 근거에 연결하지 못했습니다. | 빌드 설정·주석 전용 파일·추출 누락·삭제 파일인지 확인합니다. |

클래스는 prose 또는 per-package 문서의 클래스 선택 규칙, 자유 함수는 prose 문서의 함수 선택 규칙과 대조합니다. 전체 이름과 짧은 이름을 모두 지원합니다. 패키지 요약, 시나리오의 일부 호출, 수동 문서의 파일 참조를 클래스·함수 전체가 설명된 근거로 취급하지 않습니다. 수동 문서의 `evidence_files`는 사람이 재검토할 위치로 안내합니다.

libclang이 익명 구조체·공용체에 붙이는 이름은 검사에서 제외합니다. 그 이름에는 파싱한 기계의 절대 경로와 줄 번호가 들어 있어서(`Ctx::(unnamed struct at /home/…/ipa_context.h:33:2)`) 설정의 어떤 패턴으로도 고를 수 없고, 줄이 밀리면 같은 구조체가 둘로 보입니다. 보고해도 해결할 방법이 없는 항목이며, 그 구조체를 담은 바깥 클래스가 같은 파일을 이미 검사 대상으로 잡습니다. libcamera 두 커밋으로 실측했을 때 검토 항목 10개 중 8개가 이것이었고, 제외한 뒤 2개가 남았습니다.

`source.exclude`에 해당하는 파일은 검사에서 제외하되 목록을 남깁니다. 단순히 경고를 없애기 위해 제외 범위를 넓히지 말고 프로젝트의 실제 분석 대상에 맞추세요. 검토를 마친 개별 항목의 승인·보류는 `sdd accept --finding`이 장부에 사람·시각과 함께 기록하며, 검사 결과 자체를 바꾸지는 않습니다.

## 검사 범위와 한계

변경 파일 안에 선언 또는 메서드·함수 정의가 있는 엔티티를 보수적으로 검사합니다. 주석·공백·`#include`만 바뀐 파일은 1단계에서 걸러 내지만, 그 밖의 변경은 줄의 의미를 분석하지 않으므로 같은 헤더에 있는 변경되지 않은 클래스도 검토 목록에 포함될 수 있습니다. 이전 facts를 제공하면 양쪽 파일과 엔티티를 확인합니다. 이름 변경은 이전·이후 경로를 모두 검사하며, Windows에서도 공백과 한글 경로를 보존합니다.

이 검사는 설정상 문서 범위와 재생성 연결을 확인합니다. 문서 파일의 존재·최신성, LLM 입력 예산으로 생략된 내용, 파싱의 완전성, 메서드별 설명 범위와 문장의 참·거짓을 보장하지 않습니다. 설명 정확성 검사는 별도 후속 작업입니다.
