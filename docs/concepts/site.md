# 설계 문서 사이트 구성

**문서 생성과 디자인 기술은 `camera-hal-sdd-generator`에서 관리하고, 출력만 문서 저장소에 배포합니다.**

`sdd export-site`는 기존 Markdown과 facts를 읽어 여러 페이지로 구성된 정적 사이트를 만듭니다. LLM을 다시 호출하지 않으며 원본 Markdown, 자동 인용 검사 결과, 생성 시각을 변경하지 않습니다.

문서 메뉴·페이지 목차와 중복되는 `지금 확인할 내용 / 이동할 절` 표는 사이트에서 제거합니다. 기존 원고는 보존하며 예전 표 행의 주소로 진입할 때만 해당 목적지 링크를 표시합니다. 생성기 형식과 다른 사용자 정의 셀 내용은 임의로 삭제하지 않습니다.

`reading_cleanup.py`는 검증 범위 표의 반복 열을 공통 안내와 질문별 목록으로 바꾸고, 한 행 호출 표는 열 이름이 있는 정의 목록으로 표시합니다. 첫 화면의 문서 상태는 검사·사람 검토 결과가 정확히 같은 항목끼리 묶습니다. 각 문서 링크와 실패·미승인 상태는 유지합니다. 관련 클래스는 전체 행이 유일한 색인 행과 일치할 때만 해당 행으로 연결하며, 다르거나 색인이 없으면 표를 보존합니다. 본문의 마지막 `다음 단계`와 하단 이동 버튼은 같은 주소일 때만 합치고 별도의 안내 문구도 유지합니다. 원고 파일은 감사용 원본으로 보존합니다.

`site.overview_visual: {section: <섹션 ID>, visual: <그림 ID>}`를 지정하면 해당 문서의 검증된 질문 그림을 인덱스의 첫 문단 뒤에서도 보여 줍니다. 원래 문서의 현재 소스·원고·그림 검사를 통과한 정의를 인덱스 경로로 다시 렌더링하며 새 설명을 작성하거나 HTML을 복사하지 않습니다. 근거 링크는 원래 문서의 검증된 발췌로 연결합니다. 그림이나 섹션을 찾지 못하거나 근거가 달라졌으면 빌드를 실패시키고 기존 출력을 보존합니다. 프로젝트별 계층·그림 선택은 예제 설정에 둡니다.

`paths.consistency_file`을 지정하면 [문서 간 계약 대조](contract-consistency.md)의 현재 검토와 원본 CLI 영수증을 확인한 뒤 빌드합니다. 확정 모순·오래된 입력·손상 기록은 게시를 막고, 자동 미판정 목록과 사람 검토 전 상태를 보존합니다. 통과한 보고서는 `contract-consistency.json`으로 동봉하여 같은 manifest에서 대조할 수 있게 합니다.

`documentation.enabled: true`이면 [문서 수명주기 검사](document-lifecycle.md)를 먼저 수행합니다. 분량·중복·Feature 범위·폐기 계획에 문제가 있으면 기존 사이트를 보존한 채 중단합니다. 폐기 원고는 메뉴·검색에서 제외하며 기존 링크는 다시 검증합니다.

사람의 승인은 `sdd accept`가 원고 옆의 장부(`sdd/approvals.json`)에 기록합니다. 사이트는 각 페이지에 승인 상태(승인·승인 이후 본문 변경·사람 검토 전)를 표시하고, `site.require_approval: true`를 두면 승인되지 않은 문서가 있을 때 게시를 중단합니다. 승인은 본문 해시에 붙으므로 본문이 바뀌면 자동으로 재검토 대상이 되고, 근거 재검증만 거친 이월(본문 동일)에서는 유지됩니다.

```yaml
site:
  require_approval: true    # 미승인·본문 변경 문서가 있으면 export-site 를 중단한다
```

유지보수 기준은 [DESIGN.md](../../DESIGN.md)입니다. 그림 생성은 `src/sdd/diagrams.py`, 페이지 배치는 `src/sdd/export_site.py`, 출력 검증·관리는 `src/sdd/site_build.py`, 공통 화면 자산은 `src/sdd/site_assets/`에서 관리합니다. 변경을 생성기에 반영하면 다음 빌드부터 모든 페이지에 적용됩니다.

## 반복 실행 계약

질문별 시각화의 선언과 근거 검사는 아래 [질문별 그림](#질문별-그림)을 따릅니다.

libcamera 설정은 `site.enabled: true`이므로 `sdd generate`와 `sdd run`이 문서와 Mermaid 원문을 만든 뒤 사이트 빌드·검증까지 이어서 수행합니다. 다른 프로젝트도 같은 옵션으로 연결합니다.

```powershell
# 현재 facts에서 문장과 Mermaid를 다시 생성하고 사이트까지 만듭니다.
uv run sdd --config examples/libcamera/sdd.yaml generate
# 문장은 유지하고 그림·화면·검색 목록만 최신 facts와 공통 규칙으로 다시 만듭니다.
uv run sdd --config examples/libcamera/sdd.yaml export-site
uv run sdd --config examples/libcamera/sdd.yaml verify-site
```

`site-manifest.json`에는 입력 facts·Markdown·섹션 설정과 생성 코드·출력 파일의 SHA-256을 남깁니다. 같은 입력으로 사이트를 두 번 만들면 같은 결과와 build ID가 나옵니다. 문장을 새로 생성하는 LLM 호출 자체의 결정성을 뜻하지 않습니다.

빌드는 먼저 임시 위치에서 내부 링크를 확인합니다. 검증 실패 시 기존 사이트에 반영하지 않습니다. 다음 빌드에서 사라진 페이지·그림은 직전 manifest에 기록된 생성 파일만 정리합니다. 사람이 수정한 생성 파일은 덮어쓰지 않고 오류를 냅니다. 원고나 공통 테마에서 수정한 뒤 다시 생성하세요.

새 출력 경로에 manifest가 관리하지 않는 파일이 이미 있거나, 필요한 디렉터리 자리에 파일이 있으면 반영 전에 중단합니다. 기존 사이트를 처음 가져올 때에도 해당 파일을 별도로 보존하고 빈 출력 디렉터리에서 빌드하세요.

설계 근거 검사가 활성화된 페이지의 이월에는 인용뿐 아니라 선택한 구조·주제·발췌의 지문도 같아야 합니다. 근거가 달라지면 재생성이 필요합니다. [설계 근거 검사](design-evidence.md)의 자동 검사 통과는 사람의 의미 검토나 실행 검증을 뜻하지 않습니다.

`design_requirements`가 있는 페이지는 필수 질문별 설명·근거 연결도 검사합니다. `generate`는 선택된 섹션을 사전 검사하고 실패하면 원고를 덮어쓰지 않습니다. `design_generation: llm`이면 LLM 답변 생성과 검사까지 끝낸 뒤 원고를 교체합니다. `export-site`는 원고에 보존된 답변 기록·입력 지문·본문 지문도 다시 검사하므로 불완전한 계약을 현재 입력 지문만 맞춰 게시할 수 없습니다. `show_evidence`를 켜면 설명 아래에서 발췌 원문과 해시를 펼쳐 대조할 수 있습니다. 설정 예시는 [필수 설계 항목 검사](design-evidence.md#필수-설계-항목-검사)를 참고하세요.

사이트는 현재 facts와 원고의 커밋이 같아야 합니다. 새 커밋에서 일부 원고만 갱신해 나머지 원고가 이전 커밋에 남으면 게시를 중단합니다. `generate --from-impact`는 영향이 없던 원고의 `파일:줄` 인용을 새 facts로 재검증한 뒤 통과한 원고의 `source_commit`을 이월하므로(`carryover.py`, frontmatter에 `revalidated_from` 기록), 통상적인 증분 실행에서는 전체 재생성 없이 기준이 맞습니다. 인용이 어긋난 원고는 이월하지 않고 재생성 대상으로 보고하며, 그때는 해당 섹션을 다시 생성해야 게시할 수 있습니다.

Git push는 생성 명령에 포함하지 않습니다. 검증된 출력 디렉터리를 `libcamera-sdd/docs`로 지정해 만들고 해당 저장소에서 커밋·push하면 기존 Pages가 게시합니다. 생성기 CI는 push/PR마다 Windows·Linux, Python 3.11·3.14에서 회귀 검사를 실행하도록 구성했습니다. 원격 CI 통과 여부는 실제 실행 결과로 확인해야 합니다.


## 디자인 기준

[libcamera 공식 문서](https://docs.libcamera.org/master/)의 좌측 탐색 메뉴·중앙 본문·우측 목차를 참고했습니다. OMM 저장소의 `DESIGN.md`, `docs/design.md`, `assets/reading.css`, `templates/jekyll/_layouts/default.html`에서 읽기 중심 배치와 다이어그램 상호작용 규칙을 적용했습니다. 참고한 로컬 OMM 기준 커밋은 `12a704c603136308b87b26c4081bd6102d42395e`입니다.

별도의 Mermaid 이름을 가진 `SKILL.md`는 해당 저장소에서 찾지 못했습니다. 실제로 적용한 것은 위 디자인 문서와 템플릿의 규칙입니다. OMM 실행기를 설치하거나 OMM 저장소를 수정하지 않았습니다.

본문 너비는 최대 720px이며 글자 크기는 16px, 줄 간격은 1.8입니다. 흰 배경에 짙은 녹색을 제한적으로 사용합니다. 좁은 화면에서는 메뉴를 접고 목차를 본문 위에 표시합니다. 외부 글꼴은 내려받지 않습니다.

목차 페이지에 딸린 하위 문서는 왼쪽 메뉴에서 접었다 펼 수 있습니다. 읽고 있는 가지만 펴 두고 나머지는 접어서 목록을 짧게 유지합니다. `details`/`summary` 로 만들었으므로 스크립트 없이도 동작합니다.

데스크톱 메뉴는 `scrollbar-gutter: stable`로 스크롤바 자리를 미리 확보합니다. 하위 문서를 펼쳐 메뉴가 길어져도 다른 제목의 너비와 줄바꿈은 유지합니다. 검증할 때는 접힌 메뉴는 화면에 들어가고 펼친 메뉴에는 스크롤이 생기는 높이에서 두 상태의 제목 너비와 줄 수를 비교합니다. 모바일 메뉴에는 이 여백을 적용하지 않습니다.

메뉴 오른쪽 경계의 손잡이를 드래그하면 너비가 바뀌고 메뉴 제목과 본문이 자동으로 줄바꿈됩니다. 데스크톱 메뉴의 너비는 180~420px이며 전체 레이아웃의 45%를 넘지 않습니다. 손잡이에 Tab으로 초점을 옮긴 뒤 좌우 방향키로 10px씩, Shift와 함께 누르면 40px씩 조절합니다. Home·End는 최소·최대 너비로 이동하고, 두 번 클릭하면 기본 너비(넓은 화면 240px, 중간 화면 220px)로 돌아갑니다. 선택값은 브라우저에 저장되어 같은 사이트의 페이지·언어 이동과 새로고침 후에도 유지됩니다. 저장 공간이 차단되면 현재 페이지에서만 조절합니다. 모바일 메뉴와 인쇄 화면에는 손잡이를 표시하지 않습니다.

사이드바를 아래로 스크롤한 뒤 다른 문서로 이동해도 같은 탭에서는 메뉴 위치를 복원합니다. 새로고침·한국어와 영어 전환·뒤로 가기도 지원합니다. 세로 위치는 사이트별 탭 저장 공간에 보관하므로 다른 탭의 탐색 위치를 덮어쓰지 않습니다. 새 메뉴가 짧으면 이동 가능한 끝 위치로 제한합니다. 모바일 본문 스크롤은 변경하지 않으며, 탭 저장이 차단되면 브라우저의 기본 동작을 유지합니다.

손잡이를 누르거나 드래그할 때는 중앙의 짧은 손잡이만 강조합니다. 키보드 초점도 손잡이 주변에만 표시하여 화면 전체 높이의 테두리가 생기지 않게 합니다. 현재 문서는 둥근 옅은 배경과 강조 글자로 구분하며, 메뉴의 키보드 초점은 해당 항목 안에 표시합니다.

검증할 때는 실제 포인터 드래그와 키보드 조작, 긴 한영 제목의 줄바꿈, 페이지·언어 이동 후 너비 복원, 창 크기 변경 시 상한, 저장 차단 시 검색·그림 조작을 확인합니다. 클릭·드래그·키보드 초점 각각의 화면을 비교하여 전체 높이에 강조가 생기지 않는지도 확인합니다. 모바일에서는 가로 넘침 없이 메뉴를 열고 닫을 수 있어야 합니다.

검색은 실제 문서 제목과 모든 페이지의 절 제목을 대상으로 합니다. Ctrl/⌘+K로 열고 Escape로 닫습니다. 표와 코드 블록은 가로로 스크롤할 수 있습니다. 이전·다음 링크는 실제 문서 순서에서 생성합니다.

명시적인 이동 안내가 없는 시나리오·자동 페이지는 절 본문의 첫 설명 문장으로 내부 이동 안내를 만듭니다. 제목에 상투적인 확인 문구만 붙이지 않습니다. 표·코드·근거 접기만 있는 절에서는 안내 문구를 추측하지 않으며, 코드 블록 안의 제목도 이동 대상으로 읽지 않습니다. 기존 절 앵커와 명시적인 `routes` 설정은 유지합니다.

왼쪽 메뉴는 독자 그룹 안에서 수행할 작업별로 문서를 묶습니다. `sections.yaml`의 선택 항목 `nav_section`에 같은 작업 이름을 쓰면 한 소분류로 모입니다. 소분류는 처음 나온 순서대로, 그 안의 문서는 선언한 순서대로 표시하며 시나리오 하위 문서는 목록 문서의 소분류를 따릅니다. 생략하면 기존 메뉴가 유지됩니다. libcamera 예제는 Vendor의 도입 판단·연동 구현·장치별 기능 구현, Developer의 구조 이해·동작 추적과 문제 진단·코드 탐색으로 나눕니다.

## 로컬에서 보기

```powershell
python -m http.server 8765 --bind 127.0.0.1 --directory <설정 디렉터리>/build/site
```

브라우저에서 `http://127.0.0.1:8765/`를 엽니다. 검색과 Mermaid 모듈을 불러오려면 파일을 직접 여는 대신 HTTP 서버를 사용하세요. 사이트 설정 키(`title`, `intro`, `source_url`, `source_link`, `source_link_template`)는 [설정 참조](../reference/config.md#site)에 있습니다.

인용 링크는 facts에 기록된 정확한 파일·줄과 40자리 커밋이 일치할 때만 만듭니다. 원고와 facts의 커밋이 다르면 prose 페이지의 새 그림 생성을 거절합니다. `export-site --out <디렉터리>`는 출력만 갱신하며 Git push를 하지 않습니다. 출력 디렉터리는 전용으로 씁니다.


## 한국어·영어 전환

`site.english_catalog`를 설정하면 기존 한국어 페이지와 같은 경로를 가진 `en/` 영어판을 함께 만듭니다. 상단 메뉴에서 한국어 또는 English를 선택하세요. 영어 메뉴·목차·본문·검색과 그림 조작 안내를 제공합니다. 절 식별자는 같으므로 자바스크립트가 켜져 있으면 전환할 때 읽던 절도 유지합니다. 자바스크립트 없이도 언어 메뉴와 문서 링크를 사용할 수 있습니다.

```yaml
site:
  english_catalog: english.json  # 설정 파일 기준 경로. 생략하면 기존 한국어 사이트만 만든다.
```

번역은 빌드 입력인 JSON 카탈로그에 보관하므로 사이트 열람·빌드에는 LLM 연결이 필요하지 않습니다. 새 문장 번역에는 설정한 로컬·사내 LLM을 선택적으로 사용할 수 있습니다. 공통 기능은 `src/sdd/site_localization.py`에 있고, 공개 libcamera 번역은 `examples/libcamera/english.json`에 있습니다. 사내 문서에는 해당 프로젝트의 별도 카탈로그를 사용하세요.

원고를 바꾼 뒤에는 다음 순서로 번역을 갱신합니다.

1. 원고의 근거 검사를 통과시킨 뒤 검토용 카탈로그를 준비합니다.

   ```powershell
   python -m sdd.site_localization --config <설정>/sdd.yaml --out <설정>/english.json
   ```

새 문장을 설정된 LLM으로 번역하려면 위 명령에 `--translate`를 붙입니다. `agent.kind: ollama`이면 같은 로컬 Qwen을 호출하며, 정확히 같은 기존 문자열의 번역은 유지합니다. 새 번역은 자리표시자와 출력 형식을 검사한 뒤 카탈로그에 반영합니다. 실패하면 기존 카탈로그를 보존하며, 호출 기록은 `build/translation-prompts/calls/`에 남습니다. 자동 번역도 사람 검토 전 상태입니다.

2. 카탈로그 diff와 원문을 함께 검토합니다. 기존 문장과 정확히 같은 번역은 유지되고, 새 문장은 빈 값으로 남습니다. `strings`의 값을 영어로 작성하고 `{{0}}` 같은 자리표시자는 각각 한 번씩 보존하세요. 자리표시자는 코드·링크 등 인라인 요소이며 영어 어순에 맞게 옮길 수 있습니다. 원문의 조건·예외·근거를 빠뜨리지 마세요.
3. `paths.consistency_file`이 있으면 번역 갱신 후 `audit-consistency`로 관련 한영 계약을 대조하고, `export-site`와 `verify-site`를 실행합니다. 원문 페이지 집합과 SHA-256, 번역 누락, 자리표시자 보존 및 링크를 검사합니다. 실패하면 기존 배포는 보존합니다. 카탈로그 준비 명령은 지문을 갱신하므로, 단순히 실행했다는 이유로 문맥 검토를 생략해서는 안 됩니다.

코드·인용·소스 발췌와 한국어 Markdown 다운로드는 원문을 유지합니다. Mermaid는 같은 노드와 연결을 유지하며 생성기가 정한 관계 표시만 번역한 영어 원문을 제공합니다. 검색은 영어 제목과 절 제목을 대상으로 합니다. 영어판의 안내문은 번역이 사람 검토 전이며 원문에 표시된 승인은 번역 승인이 아님을 명시합니다. 카탈로그의 `review_status`를 수정해도 사람 승인으로 승격하지 않습니다.

현재 번역에는 별도의 사람 승인 장부가 없습니다. 따라서 `site.require_approval: true`이면 영어판 게시를 차단합니다. 원문 승인만으로 번역을 승인된 문서처럼 게시하지 않습니다.

페이지 지문에는 생성 시각·검토 상태·화면 문구도 포함됩니다. 이런 값이 바뀌어도 카탈로그를 검토하고 갱신해야 합니다. 기존 CLI와 `impact.json` schema 1은 바뀌지 않습니다. 다음 단계로 [반복 실행 계약](#반복-실행-계약)에 따라 사이트를 검증하세요.

## Mermaid 구성

시나리오 문서는 주요 확인 지점, 호출 관계도, 추적 경계, 전체 추적 기록으로 구성합니다. 호출 관계도는 평탄한 facts에서 실행 순서를 추정하지 않습니다. 같은 호출 지점의 가상 후보는 경계 표에 모으며, 예약 대상도 즉시 실행되는 호출과 구분합니다. 전체 기록은 25개씩 펼쳐 볼 수 있고, `hide`로 요약에서 뺀 호출과 같은 이름의 서로 다른 호출 지점도 보존합니다.

시나리오 섹션의 `narration` 기본값은 `facts`입니다. 호출과 경계의 개수 및 탐색 안내를 추출 근거로 구성하며 LLM을 호출하지 않습니다. `sections.yaml`의 해당 섹션에 `narration: llm`을 명시하면 추가 설명을 모델로 생성하고 문단별 입력 근거 검사를 적용합니다. 이 검사도 실행 순서나 소유권에 대한 일반적인 의미 검증은 아닙니다.

`scenarios.yaml`의 `focus`는 요약할 호출을 선택합니다. 생략하면 표시 가능한 호출에서 중복 관계를 제외한 앞의 6개를 고릅니다. 선택자는 대소문자를 구분하며 `names`는 필수 glob 목록, `src`와 `dst`는 선택 glob입니다. 일치하는 호출이나 근거 위치가 없으면 생성을 중단합니다. 설명을 임의로 추가하는 기능이 아니므로 `title`에는 탐색할 지점의 이름을 적습니다.

```yaml
scenarios:
  - id: capture
    from: CameraDevice::capture()
    focus:
      - title: 요청 제출 대상
        names: [submit]
        src: CameraDevice
        dst: RequestManager
```

관계도는 `diagrams.max_nodes` 한도를 적용하며, 초과하면 `focus`를 나누거나 한도를 명시적으로 바꿔야 합니다. 시나리오 facts 또는 표시 설정이 바뀌면 기존 원고의 지문 검사가 사이트 빌드와 증분 이월을 차단하므로 해당 시나리오를 다시 생성해야 합니다.

새 원고는 `generation_method`로 생성 방식을 기록합니다. 소스 발췌 해시에 연결한 설명, 추출 사실로 만든 구조 설명, LLM 설명, 혼합 문서, 결정적 표·목록과 dry-run을 구분합니다. 페이지 상단에는 생성 방식, 하단에는 검증 범위를 표시합니다. 생성 방식을 기록하지 않은 기존 원고는 설정을 보고 추측하지 않고 미기록으로 표시합니다. `export-site`는 메타데이터를 보충하지 않으므로 표시를 갱신하려면 `generate`로 다시 생성하세요.

`generate --from-impact`는 이번에 선택한 섹션에 LLM 설명이 있을 때만 변경 요약에도 모델을 사용합니다. 소스 계약·facts·표·목록으로 구성된 섹션만 갱신하면 `build/change_impact.md`도 영향 보고서로부터 작성하므로 LLM 연결이 필요하지 않습니다. dry-run에서도 이 요약 파일을 작성합니다.

prose 페이지에서 선택한 클래스와 직접 기반 클래스를 facts로부터 도식화합니다. 실제 추출한 상속과 필드 참조를 사용하며 이름만으로 호출 순서를 추측하지 않습니다. 표시할 노드가 한도를 넘으면 빌드가 실패하므로 섹션을 나누거나 명시적으로 한도를 조정하세요. 기존 Mermaid 코드 블록도 렌더링합니다.

자동 클래스 그림은 `diagrams.enabled: true` 또는 섹션의 `diagram.enabled: true`로 켭니다. 기본값은 꺼짐이며, 기존 프로젝트의 넓은 클래스 선택 범위 때문에 문서 생성이 실패하지 않도록 합니다. libcamera 예제는 명시적으로 켜져 있습니다. 그림을 끄거나 선택한 클래스가 없어지면 사이트 재빌드에서 이전 자동 그림과 `.mmd`를 제거합니다. 원고의 이동 링크를 유지하기 위해 해당 절 제목과 안내 문장은 남기며, 직접 작성한 Mermaid 블록은 보존합니다.

```yaml
diagrams:
  enabled: true
  max_nodes: 16
  direction: LR
  strip_namespace: 'libcamera::'
```

각 섹션의 `diagram`에 같은 키를 넣으면 해당 섹션만 재정의합니다. 지원 방향은 LR·TB·RL·BT입니다. 네임스페이스 생략은 표시 이름에만 적용하며 노드 식별에는 전체 이름을 사용합니다.

그림을 누르거나 키보드 Enter/Space를 누르면 확대 창이 열립니다. 요소 이름 검색, 실제 SVG 크기 변경, 화면에 맞춤, 100% 복귀를 지원합니다. Escape로 닫으면 원래 그림과 키보드 초점을 복원합니다. `.mmd` 원문도 내려받을 수 있습니다.

Mermaid는 OMM 템플릿과 같은 `11.12.0` 버전에 고정했고 `securityLevel: strict`로 실행합니다. 지정한 경로를 읽지 못하면 실패 안내와 원문을 표시합니다.

사내망·오프라인에서는 `sdd fetch-mermaid`로 ESM 배포본(본체와 chunk 모듈)을 준비하고, `site.mermaid_dir`를 지정해 사이트 산출물에 동봉합니다. 그러면 CDN 주소가 페이지에 남지 않고 그림이 사이트 자체 파일로 렌더링됩니다. 망이 분리된 환경에서는 `mermaid-<버전>.tgz`를 먼저 반입한 뒤 `--tarball`로 지정하고, 사내 npm 미러가 있으면 `--registry`를 씁니다.

```powershell
uv run sdd --config <설정>/sdd.yaml fetch-mermaid          # <설정 루트>/assets/mermaid 에 준비
uv run sdd --config <설정>/sdd.yaml fetch-mermaid --tarball mermaid-11.12.0.tgz   # 반입한 파일 사용
```

```yaml
site:
  mermaid_dir: assets/mermaid    # 설정 루트 기준. export-site 가 사이트의 assets/mermaid/ 로 복사한다
```

이미 사내 웹 서버에 Mermaid를 호스팅하고 있다면 `site.mermaid` 또는 `--mermaid`로 그 주소(또는 사이트 루트 기준 경로)만 지정해도 됩니다. 우선순위는 `--mermaid` > `site.mermaid` > `site.mermaid_dir` > 공개 CDN입니다.

## OMM 이력 관리 도입 여부

현재는 Git 원본 이력, facts의 `source_commit`, 문서의 생성 메타데이터, `impact`의 기준·대상 커밋으로 분석 입력과 영향을 추적합니다. OMM의 commit 수집도 Git 이력과 검토 체크포인트를 기반으로 하므로 지금 추가하면 이력 상태를 이중으로 관리하게 됩니다.

따라서 이번에는 디자인 규칙만 적용합니다. 향후 여러 저장소의 설계 의도·제약·검토 승인과 체크포인트를 공통 OMM 항목으로 연결해야 할 때 도입을 다시 판단합니다. 커밋 추적 자동화는 `sdd update`(순서 보장·재개·리뷰 관문), 승인 기록은 `sdd accept` 장부가 담당하며, 두 기능 모두 회귀 테스트로 동작을 확인했고, libcamera·사내 저장소에서의 실측은 남아 있습니다.

다음 단계: 게시 문서의 근거와 문장을 검토합니다.


## 근거 링크 표시 검증

모바일 메뉴는 본문 위의 화면 내 패널로 열립니다. 문서 아래에서 열어도 메뉴가 보이는지, 닫기·배경 클릭·Escape 후 본문 위치가 유지되는지 확인합니다. 키보드 초점은 패널 안에서 순환하고 닫으면 메뉴 버튼으로 돌아갑니다. 스크립트가 없으면 기존 문서 내 메뉴를 사용합니다.

발췌를 연 뒤 브라우저의 뒤로 가기 또는 `설명으로 돌아가기`를 사용하면 원래 인용 링크로 초점과 스크롤을 돌립니다. 복귀 후 Tab으로 본문 읽기를 이어 갈 수 있는지 검사합니다. 직접 발췌 주소로 진입한 경우에는 없는 복귀 위치를 만들어내지 않습니다.

`kind: per-package` 페이지에는 클래스·함수 행마다 고유 주소를 붙이고 전역 검색에 코드 요소로 등록합니다. 페이지 내 검색은 이름·경로·설명을 대상으로 하며 패키지·종류 필터와 초기화를 지원합니다. 행과 코드 인용을 삭제하지 않으며 스크립트가 없으면 전체 표를 읽을 수 있습니다. 코드 식별자는 영어판에서도 번역하지 않습니다. 필터로 숨긴 행을 검색 결과로 다시 열면 필터를 초기화하여 해당 행에 초점을 둡니다.

기본 읽기 화면에는 문단별 근거 행·아이콘·버튼을 만들지 않습니다. 검증된 문단 끝 인용과 절의 발췌 목록은 절 끝의 `절 전체 근거 N개`에 모읍니다. 목록에만 있거나 문단에만 있던 고유 근거와 전체 소스 목적지를 모두 유지합니다. 본문 중간의 인용과 일반 링크, 그림 근거는 그대로 둡니다. 한영·모바일·인쇄에 같은 정책을 적용합니다.

H2 본문 절의 H3 이하 소제목·그림과 그 뒤의 설명은 같은 근거 묶음에 포함합니다. 첫 문단 뒤나 소제목 앞에 새 근거 행을 넣지 않고 다음 H2 절 앞에서 한 번 펼쳐 보게 합니다. 본문 절이 없는 문서는 전체 설명 끝에서 모으며 문단별 대응 속성은 그대로 유지합니다.

문장별 원문 구절·근거·해시는 원고의 `generated_design`에 남고 `export-site`가 다시 검사합니다. 원고 Markdown은 감사용 인용을 그대로 포함합니다. HTML에서는 문단의 `data-sdd-evidence` 속성을 HTML 디코딩 후 JSON으로 읽으면 `[파일:줄, 원래 인용 HTML]` 목록을 확인할 수 있습니다. 이 속성에는 조작 요소나 접근성 안내·검색 문구가 없습니다. 검토자는 보존된 원고와 이 대응을 함께 대조합니다. 자동 검사는 사람 승인을 바꾸지 않습니다.

변경 후에는 개요·연동·개발자·시나리오에서 다음을 확인하세요.

`소스 근거` 절에서는 발췌 목록 전체를 `소스 발췌 N개` 한 줄로 접습니다. 목록을 펼친 뒤 개별 원문을 열 수 있고, 본문의 발췌 링크로 이동하면 두 단계가 함께 열립니다. 원고를 재생성하지 않아도 기존 발췌·해시·주소를 보존하여 적용합니다. 스크립트를 끈 상태에서도 목록과 개별 발췌를 키보드로 열 수 있는지 확인하세요.

기존 CLI 감사 영수증을 읽는 사이트 빌드는 과거 실행 파일의 설치 여부를 요구하지 않습니다. 기록된 요청·응답·stdout·실행 인자와 현재 검사 정책은 그대로 대조합니다. 새 CLI 실행은 별도로 설치된 실행 파일을 확인합니다.

1. 기본 화면의 문단 근거 행이 0개이며 빈 행이나 추가 Tab 대상이 없어야 합니다.
2. 절 끝의 `절 전체 근거`를 Enter와 Space로 펼쳐 모든 고유 근거를 확인합니다.
3. 유일한 로컬 발췌의 **발췌** 링크와 고정 커밋의 **전체 소스** 링크를 확인합니다. 발췌가 둘 이상이면 임의로 고르지 않습니다. JavaScript가 없어도 절 접기와 원문 접기를 직접 펼칠 수 있어야 합니다.
4. 390px 모바일·인쇄와 영어판에서도 같은 위치·목적지가 유지되어야 합니다. 검색·그림 확대·이전 앵커와 언어 전환을 함께 확인합니다.

사이트 표시 변경은 Markdown을 재작성할 이유가 아닙니다. 영어판의 HTML 지문은 새로 검토하며, 자동·에이전트 검증을 사람 승인으로 기록하지 않습니다.

## 질문별 그림

### 사내 LLM으로 초안 자동 생성하기

**사내 템플릿의 `config/visuals.yaml`에는 질문만 적습니다. 노드·화살표·근거 해시를 손으로 작성하지 않습니다. 꼭 포함할 실제 함수·상태는 선택적인 required_symbols로 지정할 수 있으며 소스나 그림에 없으면 실패합니다.** 각 질문에 `generation: llm`을 지정하면 `generate`, `run`, `update`가 기존 `agent` 연결을 사용해 그림 JSON 초안을 요청합니다. 기본 `agent.kind: cli`는 Hermes를 실행하며 OpenCode·Claude Code로 바꿀 수 있습니다. 모델·제공자·인증은 선택한 CLI에서 관리합니다. [CLI 선택 안내](../inhouse/cli-agents.md)를 따릅니다. 실제 HAL과 모델에서 별도 검증하기 전에는 사내 적용 완료로 판단하지 않습니다.

```yaml
schema: 1
sections:
  overview:
    - id: session-states
      topic: lifecycle
      kind: state
      title: 세션 상태 전이
      question: 실제 코드에 있는 시작·정지 상태와 허용 전이는 무엇입니까?
      generation: llm
```

`topic`은 현재 섹션의 `design_topics` ID이며 그 주제에 실제 소스 발췌가 있어야 합니다. 직접 작성한 그림과 LLM 질문을 같은 파일에 함께 둘 수 있습니다. 자동 질문에는 `nodes`, `edges`나 해시를 미리 넣을 수 없습니다. 초기 사내 템플릿의 빈 소스 범위와 필수 질문부터 실제 HAL에 맞게 채우세요. `dry-run`은 LLM 그림을 만들지 않으며 게시 가능한 결과로 통과하지 않습니다.

LLM은 노드의 소스 심볼과 레이블, 연결, 원문 구절 ID를 JSON으로 제안합니다. 생성기가 구절을 실제 발췌에 연결하고 해시를 부여합니다. 노드 심볼이 구절에 없거나 화살표 근거에 양 끝의 심볼이 없으면 거절합니다. 조건은 발췌의 `if`에서 복사한 식만 허용하며 c0:true·c0:false 같은 조건 ID로 방향을 선택합니다. `if` 식 복사는 C++ 의미 분석이 아닙니다. 이 검사는 구절 일치·심볼 동시 출현을 확인하며 방향·인과·소유권 해석 전체의 정확성을 보증하지 않습니다. 의미 검토와 기존 승인 관문은 계속 필요합니다.

레이블에 비교식을 함께 썼다면 인용한 원문의 조건과 공백을 제외하고 일치해야 합니다. 원문에 없는 반대 식이나 이전 조건은 거절합니다. 모델 출력에 올바른 조건이 함께 적혔다는 이유만으로 불필요하게 실패시키지 않습니다. Doxygen 반환값 설명은 상태별 구절로 나눠 전달하며 원문의 연속된 구절을 그대로 보관합니다.

모든 선택된 그림의 초안·검사가 끝나기 전에는 원고를 교체하지 않습니다. 실패한 호출과 응답은 기존 `build/prompts/calls` 영수증에 남고 직전 정상 원고·사이트는 보존합니다. 모델에 근거 해시, Mermaid나 승인을 작성하게 하지 않습니다. 사내 호환 게이트웨이에 Ollama 전용 구조화 출력 기능이 없어도 JSON 파싱과 같은 검사를 적용합니다.

원고 frontmatter의 `generated_visuals`에 입력 지문, 실제 초안, 근거가 연결된 그림, 작성 모델, 생성 커밋과 본문 해시를 보관합니다. 같은 질문·정책·모델 연결·발췌이면 검증 후 재사용합니다. 소스나 질문이 바뀌면 새 모델 호출이 필요하며 `export-site`는 오래된 그림의 게시를 중단합니다. `generate --from-impact`와 `update`는 선택된 섹션에서 이를 다시 생성합니다. 영향 밖 원고를 이월할 때도 그림 기록을 재검증합니다. 원고와 facts의 커밋이 다른 채로 게시하지 않습니다.

실제 Local Qwen 시험은 `python tools/evaluate_visuals.py --out <새 출력 경로> --runner hermes --with-prose`로 실행합니다. 공개 mini HAL의 실제 함수를 두 Git 커밋으로 만들고 조건 변경, 이전 사이트 보존, 그림 재생성, 영수증·초안 일치를 검사합니다. 반입 ZIP에서도 같은 명령을 실행합니다. 이 공개 예제 시험은 실제 카메라 실행이나 사내 HAL 검증이 아닙니다.

질문의 핵심 용어가 빠지는 알려진 실패는 그림 계획의 선택적 `answer_contract`로 검사할 수 있습니다. 문단과 같은 `basis`, `required_terms`, `reject_patterns`를 사용하되 한국어 노드·화살표 레이블 전체에 적용합니다. 용어가 있다는 사실은 의미 정확성의 판정이 아닙니다. 공개 예제는 Adjusted의 변경 가능성과 호출자 재확인 누락을 검사합니다.

계획별 `max_nodes`로 프로젝트의 `visuals.max_nodes`보다 작은 한도를 지정할 수 있습니다. 예를 들어 반환 상태 세 개와 검증 함수 한 개를 네 노드로 제한하면 같은 상태를 중복해서 늘리는 초안이 통과하지 않습니다. 한도 초과는 자동 축약 없이 실패합니다.

필수 심볼 수가 노드 한도와 같으면 생성기가 `n0`·`n1` 같은 ID를 각 소스 심볼에 연결해 모델에 전달합니다. 모델은 해당 키의 객체에 레이블·구절 ID를 작성하고 화살표를 제안합니다. 원시 응답은 그대로 보관하며 생성기가 심볼을 붙여 검사합니다. 실제 Ollama에서 배열 항목별 제약이 적용되지 않는 문제를 피하는 형식이며, 일반적인 계획은 기존 노드 목록을 사용합니다.

영어 레이블의 별도 최소 용어·오류 검사는 `answer_contract_en`으로 지정합니다. 같은 형식이며 `basis: description`, `implementation`, `measurement`를 지원합니다. 한국어 의무 문장 검사는 영어에 적용하지 않습니다. 두 언어의 가능성·의무 표현이 같은 의미인지도 별도로 대조하세요.

`question`은 독자에게 표시할 질문입니다. 모델에만 전달할 분량·표현 지시는 선택적 `prompt`로 분리하며 원고에 표시하지 않습니다. 이 지시가 바뀌어도 입력 지문이 달라져 재생성해야 합니다.

그림 계획의 선택적 `sources: [근거-id]`로 해당 주제의 발췌 중 그림에 필요한 것만 선택할 수 있습니다. 생략하면 기존처럼 주제의 모든 근거를 제공합니다. 빈 목록·중복·다른 주제의 ID는 실패합니다. 본문의 개별 상태 설명에는 좁은 발췌가 적합해도, 함수와 반환 상태를 연결하는 그림에는 함수 머리와 반환값 설명을 함께 보존한 근거가 필요합니다. 필요한 관계·조건을 잘라내지 않고 무관한 발췌만 제외하세요.

한글 `label`과 영어 `label_en`은 각각 한 줄로 생성합니다. 스키마와 저장 검사가 모두 줄바꿈을 거부하며, 화면 폭에 맞춘 줄바꿈은 생성기의 렌더러가 처리합니다.

그림만 시험하는 문서는 주제에 `narration: facts`를 지정해 질문·소스 원문 보기를 사용할 수 있습니다. 동작 답변을 생성하지 않으며 생성 방식에도 이를 표시합니다. 필수 설계 질문이나 독자 프로필이 있는 사내 문서에서는 이 방식을 사용할 수 없습니다. 실제 Qwen 그림 시험은 이 소스 보기에서 수행하며, 자연어 답변 생성 검증과 구분합니다.

### 근거를 검토해 직접 작성하는 그림

**상태 전이·요청 흐름·소유권·실패 분기는 해당 질문에 답하는 설명 가까이에 배치하세요.** 클래스 상속도만으로 동작을 대신 설명하지 않습니다. 사내 HAL에서는 실제 소스의 발췌와 독자의 질문으로 아래 선언을 새로 작성합니다.

`sdd.yaml`에서 파일과 노드 한도를 지정합니다.

```yaml
visuals:
  file: config/visuals.yaml
  max_nodes: 12
```

그림 파일의 `schema`는 1이며 `sections`는 섹션 ID별 그림 목록입니다. 각 그림은 고유한 `id`, `topic`(현재 `design_topics`의 ID), `kind`(`state`, `flow`, `ownership`, `decision`), `title`, 확인 범위를 설명하는 `question`, `nodes`, `edges`를 가집니다. `kind`는 읽기 목적을 나타내며 네 종류 모두 Mermaid 흐름도로 그립니다. 상태 전이는 상태 노드와 허용 호출 화살표로 표현합니다. Mermaid 원문을 직접 입력하지 않습니다.

노드는 `id`, `label`, `label_en`, `evidence`를 갖습니다. `shape: decision`이면 조건 마름모로 그리며 기본 모양은 상자입니다. 화살표는 `from`, `to`, `label`, `label_en`, `evidence`를 갖습니다. 예를 들어 종료 함수 호출을 표현할 때 다음과 같이 연결합니다.

```yaml
edges:
  - from: running
    to: stopping
    label: stop()
    label_en: stop()
    evidence:
      - source: state/states
        sha256: <검토한 발췌의 SHA-256>
        quote: <이 전이를 직접 뒷받침하는 고유한 원문 구절>
```

`source`는 같은 섹션 안의 `주제 ID/소스 ID`입니다. 노드와 화살표 모두 하나 이상의 근거를 연결합니다. 생성기는 facts의 소스 커밋, 현재 selector, 발췌 해시와 구절의 유일성을 검사합니다. 근거 누락·변경·잘못된 연결·번역 누락·노드 한도 초과는 원고 교체나 배포 전에 실패합니다. 실패 시 기존 원고와 사이트를 보존합니다. 해시를 자동으로 새 값에 맞추지 말고 연결된 해석을 다시 검토하세요. 선언만으로 해석이 맞다는 판정이나 사람 승인을 얻지 못합니다.

그림을 쓰는 페이지는 `kind: prose`, `show_evidence: true`와 연결할 `design_topics`가 필요합니다. 생성과 사이트 빌드에서 같은 코드를 사용해 해당 주제의 첫 문단 뒤에 그림을 배치합니다. 번호 절차나 목록으로 시작하는 절에서는 목록을 나누지 않고 그 앞에 그림을 둡니다. 바로 아래의 `그림 근거와 확인 범위`를 펼치면 요소·전이별 원문으로 이동합니다. 한 그림을 12개 노드 안에서 읽기 어렵다면 질문별로 나누세요. 한도는 늘릴 수 있지만 임의로 일부 노드를 숨기지 않습니다.

사이트를 다시 빌드할 때 생성기가 관리하는 그림 블록만 교체하며 삭제된 선언의 그림과 내려받기 파일도 제거합니다. 각 그림의 Mermaid 원문은 `<페이지>.<그림 ID>.mmd`에 출력합니다. 영어판은 `label_en`으로 표시하되 노드 ID와 연결을 유지합니다. 영어 표시 문구와 원본 HTML 지문은 기존 번역 카탈로그 절차로 검토합니다. 클래스 관계도와 정적 호출도는 계속 지원하며, 추출한 호출 목록만으로 실제 실행 순서·분기·스레드를 추정하지 않습니다.

번역 카탈로그를 준비할 때 그림의 검색·접근성 문구에도 같은 `label_en`을 사용합니다. 이미 있는 영문 라벨을 다시 번역하지 않으며, 같은 한글 라벨에 서로 다른 영문이 선언되어 있으면 충돌을 해결하기 전까지 실패합니다. 이 재사용은 번역 승인 상태를 바꾸지 않습니다.

설명 자체가 바뀌지 않았다면 `export-site`로 그림만 반영할 수 있습니다. Markdown에도 그림을 넣으려면 기존 질문·근거·생성 정책이 같은 답변을 `generate --from-impact`로 재사용합니다. 그림 선언은 별도 manifest 입력으로 기록되며 기존 설명의 인용 검사·사람 승인 상태를 승격하지 않습니다.
## 긴 문서를 분리한 뒤 확인할 것

문서를 나눌 때는 원래 질문과 근거를 함께 옮기고, 독자 프로필의 전체 질문을 유지합니다.
여러 페이지가 한 프로필을 충족해야 한다면 [문서 수명주기](document-lifecycle.md)의
`reader_family` 계약을 사용합니다. `routes[].anchor`는 이동한 제목의 기존 ID를 보존하여
새 페이지로 안내합니다. 생성기에서 정적 링크를 만들며 기존 HTML을 수정하지 않습니다.
분리 후에는 모든 구성원의 원고, 이전 주소의 앵커, 새 문서의 링크·검색과 한영 카탈로그를
검증한 뒤 게시합니다.
