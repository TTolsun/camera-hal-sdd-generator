# 설계 설명과 코드 근거의 연결

설계 설명은 위치 인용만으로 검증되지 않습니다. 생성기는 제한적인 구조 검사와 소스에 연결한 설계 계약을 지원하며, 두 방식 모두 사람의 기술 검토를 대신하지 않습니다. 공통 구현은 `evidence.py`와 `semantic.py`에 있고 libcamera의 이름과 계약은 예제 설정에만 둡니다.

## 생성 설명의 검사

prose 섹션에서 `semantic_review: true`를 지정하면 문단별 인용, 실제 모델 입력에 포함된 인용 위치, 백틱 안의 한정 클래스 이름, 일부 직접 상속·필드 참조 표현을 검사합니다. 기반 클래스가 없는 타입을 상속한다고 서술하는 오류와 잘못된 네임스페이스를 재시도 사유로 전달합니다. 관계 목록도 LLM 입력에 포함하며, 입력 예산 때문에 근거를 생략하면 검토 대상으로 남깁니다.

검사 대상 설명에서는 이전 원고를 모델 입력에 넣지 않습니다. 이전 커밋에서 클래스가 없었다는 설명이 추가 이후에도 반복되는 오염을 방지하기 위한 규칙입니다. facts에 있는 클래스를 없다고 서술하는 일부 표현도 검출합니다. 기반 클래스의 별칭은 클래스 엔티티가 없더라도 추출 관계에 있으면 유효한 이름으로 인정합니다.

이 검사는 한국어 표현 일부와 추출된 구조를 비교하는 보수적인 검사입니다. 모든 자연어 관계 표현, 간접 상속, 소유권·수명·동시성 주장의 진위를 판정하는 일반 의미 검증기가 아닙니다. 근거 위치가 맞아도 설명이 틀릴 수 있습니다. 원고의 `semantic_review: human-review-required`와 보고서의 `human_review: pending`은 이를 구분합니다.

설명 문단에는 근거 인용을 요구합니다. 다만 모든 문장이 "확인되지 않았다"는 서술인 문단은 예외입니다. 인용할 위치가 없는 문단에 인용을 요구하면 관계 없는 위치가 붙고, 그 인용은 근거가 아니라 검사를 통과하기 위한 장식이 됩니다. 사실을 하나라도 주장하는 문단에는 그대로 인용을 요구합니다.

문장 형태 검사에는 코드 표기 규칙이 있습니다. facts에 있는 클래스 이름이 본문에서 백틱 없이 나오면 반려합니다. 소형 모델이 이름을 평문으로 적으면 독자가 코드 식별자와 일반 명사를 구분하기 어렵고, 이름이 줄어든 것도 눈에 띄지 않습니다.

`build/content-review.json`에는 실행 중 생성한 절의 최종 설명, 자동 검사 상태, 실패 사유와 생략된 근거를 기록합니다. 각 모델 호출의 원래 출력은 기존 `build/prompts`에 남습니다. 증분 실행에서 이 보고서는 이번에 생성한 절만 다루며, 이전 원고의 승인 장부는 아닙니다.

## 주제별 소스 근거

`design_topics`는 책임·상태·요청·소유권·종료·동시성과 같은 질문을 개별 절로 생성합니다. `sources`의 시작·종료 앵커로 facts의 `source_commit`에 해당하는 Git 객체를 읽습니다. 현재 체크아웃의 수정 파일은 읽지 않습니다. 시작 앵커가 유일하지 않거나 파일·종료 앵커가 없으면 해당 질문을 확인 필요로 남깁니다.

```yaml
design_topics:
  - id: shutdown
    title: 종료 계약
    question: 종료 시 대기 요청은 언제 반환됩니까?
    sources:
      - id: stop
        file: src/device.cpp
        start: "고유한 종료 계약 주석의 시작"
        end: "해당 구현 다음의 고유한 표식"
        sha256: "실제 발췌를 검토한 뒤 기록한 SHA-256"
    statements:
      - text: "코드와 대조하여 작성한 종료 계약 설명입니다."
        evidence: [stop]
```

`statements`가 없으면 주제별 발췌를 LLM에 전달합니다. 있으면 작성된 설명을 그대로 출력하며 각 설명의 근거를 자동 인용합니다. 이 경우 모든 연결된 발췌에 SHA-256이 필요합니다. 발췌가 변경되면 예전 설명을 표시하지 않고 재검토 과제를 표시합니다. 해시를 자동으로 새 값으로 바꾸지 않습니다. 코드 변경의 의미를 확인하고 설명과 지문을 함께 갱신해야 합니다.

해시 일치는 **설명을 연결해 둔 근거가 그대로라는 뜻**입니다. 처음 작성한 설명의 정확성이나 실제 실행, 발췌 밖 코드의 의미 불변까지 증명하지 않습니다. 근거 범위를 너무 좁히면 변경을 놓칠 수 있습니다. 소스 주석과 구현이 어긋나는 경우에는 구현의 분기와 조건을 직접 대조하고 차이를 설명에 남겨야 합니다.

발췌는 `facts.json`의 `evidence`에 커밋·경로·시작과 종료 줄·본문·해시·상태로 저장합니다. `extract`와 `generate`가 설정에 맞춰 수집하므로 Git 원본을 읽을 수 있어야 합니다. 사내 소스의 발췌와 그 설명도 사내 파생 데이터이며 공개 예제 저장소에 배포하지 않습니다.

## 필수 설계 항목 검사

`design_requirements`는 문서가 답해야 할 질문을 별도로 선언합니다. 각 `statements`의 `covers`는 답변하는 항목 ID를 연결합니다. 이 모드는 소스 발췌 해시가 고정된 설명을 요구하므로 LLM의 자유 서술을 필수 답변으로 인정하지 않습니다. 기존 LLM 모드는 필수 항목을 설정하지 않은 섹션에서 계속 사용할 수 있습니다.

```yaml
design_requirements:
  - id: lifetime
    question: 정지할 때 대기 요청은 어떻게 반환됩니까?
show_evidence: true
design_topics:
  - id: shutdown
    title: 종료 계약
    question: 대기 요청의 취소와 완료 순서는 무엇입니까?
    sources:
      - id: stop
        file: src/device.cpp
        start: "고유한 시작 앵커"
        end: "고유한 종료 앵커"
        sha256: "검토한 발췌의 실제 SHA-256"
    statements:
      - text: "소스와 대조하여 작성한 취소·완료 동작을 여기에 적습니다."
        evidence: [stop]
        covers: [lifetime]
      - text: "드라이버의 실제 완료 시점은 기기에서 확인해야 합니다."
        kind: limitation
        evidence: [stop]
        covers: [lifetime]
```

필수 질문은 프로젝트 담당자가 정합니다. 질문 목록 자체가 시스템 설계 전체를 빠짐없이 대표하는지는 자동으로 판정하지 않습니다. 책임·상태·입출력·소유권·오류·종료·동시성 중 해당 문서에 필요한 질문을 정의하고 코드와 대조한 설명을 추가해야 합니다. libcamera 클래스명과 답변은 예제 설정에만 있습니다.

생성 전에 선택된 모든 섹션을 검사합니다. 답변 누락, 빈 문장, 연결되지 않은 항목, 중복 ID, 근거 누락·변경이나 발췌 본문과 해시의 불일치가 있으면 원고를 덮어쓰기 전에 실패합니다. `kind: limitation`은 실행 확인 항목으로 표시하며, 이 문장만 있는 필수 질문은 `limited`로 보고하고 실패합니다. `build/design-review.json`에는 질문별 `documented`·`limited`·`missing` 상태, 연결된 주제와 실패 이유를 기록합니다. 이 보고서는 해당 실행에서 선택된 섹션의 검사 결과입니다.

`show_evidence: true`이면 설명 바로 아래에서 원본 발췌·시작 위치·종료 줄·해시를 펼쳐 볼 수 있습니다. 요약과 원문을 대조하는 기능이며 원문의 코드나 주석을 모델로 다시 쓰지 않습니다. 사이트 빌드와 증분 이월도 필수 항목을 검사합니다. 필수 질문이나 답변 설정의 변경은 기존 근거 지문을 무효화합니다.

`documented`는 **설정된 질문에 답변과 변경되지 않은 소스 근거가 연결되어 있다는 뜻**입니다. 작성자의 해석을 자동으로 증명하거나 실행 결과를 승인하지 않습니다. 사람 승인 상태는 계속 `pending`이며 기존 승인 장부와 게시 정책을 따릅니다.

## 증분 생성

검사 대상 페이지에는 선택 클래스·함수·관계·주제 설정·소스 근거의 지문을 저장합니다. 메뉴 분류(`group`), 확인 목록(`routes`), 다음 문서 링크(`next`), 재생성 대상 glob(`watch`)은 지문에 넣지 않습니다. 설명에 실리는 내용이 아니라 페이지 배치와 영향 분석에만 쓰이므로, 이것 때문에 근거가 고정된 문서를 다시 만들면 게시된 문장이 이유 없이 바뀝니다. 영향 밖 원고라도 지문이 달라지거나 이전 지문이 없으면 이월하지 않습니다. 줄 번호가 같아도 상속 관계나 근거 본문이 달라졌다면 재생성이 필요합니다. 사이트의 커밋 일치 조건은 그대로 유지합니다.

사이트를 게시하기 직전에도 원고의 지문과 현재 입력을 비교합니다. 소스 커밋이 같더라도 질문·근거 설정을 바꾸면 재생성해야 하며, 검사 옵션을 제거해 이전 지문 검사를 우회할 수 없습니다. 출력 파일명을 생략한 기본 페이지에도 같은 검사를 적용합니다. 패키지 요약·의존 관계와 읽기 순서에 사용한 시나리오도 지문 입력에 포함합니다.

현재 per-package 페이지에서 `semantic_review`를 활성화하면 영향 패키지만의 재사용을 중지하고 해당 페이지를 다시 생성합니다. 패키지별 근거 지문이 없는데 인용 위치만으로 기존 설명을 재사용하지 않기 위한 제한입니다.

## libcamera 예제

카메라 문서의 여섯 주제는 원본의 API 계약과 구현을 대조한 설명을 발췌 해시에 연결합니다. `stop()`의 실행 중이 아닌 분기는 0을 반환하고, 파이프라인 호출은 `ConnectionTypeBlocking`이라는 점을 명시합니다. fence는 성공 시 Request가 아니라 버퍼로 이동합니다. 실제 콜백 스레드와 하드웨어 종료는 추가 검증 대상으로 남깁니다.

별도 `ipu3-lsc` 페이지는 LSC 구현, IPU3 처리 상태와 세션 설정, 관련 자유 함수를 선택합니다. A에서 Lsc가 추출되지 않고 B에서 추가되는 차이를 표와 관계 그림에 반영합니다. 익명 구조체와 엔티티가 추출되지 않은 파일은 범위 검토 보고서에 계속 남습니다.

이 페이지는 공통 옵션 `narration: facts`를 사용합니다. 선택한 클래스의 직접 기반 클래스와 추출 관계를 문장으로 직접 만들며 LLM을 호출하지 않습니다. 클래스 구조를 자유롭게 의역하면서 관계를 잘못 연결하는 문제를 방지합니다. 실행 순서와 소유권은 이 모드에서 추정하지 않으며, 함수 목록도 HAL 진입점으로 단정하지 않고 관련 자유 함수로 표시합니다.

보존한 빌드·facts를 사용한 재검증은 다음과 같이 실행합니다. 새 출력 디렉터리가 필요하며 원본 검증 결과를 덮어쓰지 않습니다.

```powershell
.venv/Scripts/python.exe examples/libcamera/validate_design.py `
  --baseline build/revision-validation/20260921 `
  --source build/publication/libcamera-sdd `
  --out build/revision-validation/new-design-run
```

이 실행은 새 빌드나 구조 재추출을 하지 않습니다. 동일한 A/B facts에 새 소스 근거를 수집하고, A 생성 → 엄격 범위 검사 → 남은 항목을 기록한 B 증분 생성 → 원래 오류 원고 재검사 → 사이트 반복 빌드를 수행합니다. 검토용 사이트를 만들며 공개 배포와 사내 HAL 검증은 수행하지 않습니다.
