# 응답과 원고를 재사용할 때 확인하는 경계

**재사용 경로를 고를 때는 무엇이 같아야 하는지 먼저 확인하세요.** 같은 요청의 응답을 다시 읽는 작업, 현재 근거로 옛 응답을 다시 검사하는 작업, 기존 원고의 답변을 이월하는 작업은 조건이 서로 다릅니다. 어떤 경로도 사람의 승인을 자동으로 기록하지 않습니다.

| 기능 | 재사용하는 대상 | 같아야 하는 입력과 확인 사항 | 판단을 담당하는 코드 |
| --- | --- | --- | --- |
| `cli_checkpoint` | 같은 소스 버전에서 검증한 CLI 항목 | `review.cli_checkpoint: true`로 사용합니다. 명시적 모델·실제 CLI 인자·질문·근거·프롬프트·집필/검증 정책과 원본 호출 영수증을 대조합니다. 모든 항목이 통과하기 전에는 기존 원고를 교체하지 않습니다. | `cli_checkpoint.py`가 원자적 보존과 영수증 무결성을, 생성 소비자가 현재 항목 검증과 정확한 grounding 판정을 다시 확인합니다. 신규 호출과 구분해 `checkpoint_units`에 남깁니다. |
| `answer_cache` | 같은 소스 버전에서 검증한 Ollama 응답 | 명시적으로 허용한 직접 API 비교 시험에서만 사용합니다. 커밋·질문·발췌·정책·모델 설정·모델 가중치 digest가 캐시 키에 포함됩니다. 읽은 응답은 현재 생성 검사를 다시 거칩니다. | `answer_cache.py`와 생성 소비자가 캐시 적합성과 재검증을 담당합니다. |
| `design_reuse` | 기존 원고에 보존한 주제별 답변 | 원고 본문 해시와 주제별 입력 지문을 확인합니다. 선택한 질문·근거·정책이 같아야 하며 현재 facts로 답변을 다시 검사합니다. | `design_reuse.py`가 답변과 작성자 기록을 보존합니다. 구조 표와 그림은 현재 facts에서 다시 구성합니다. |
| `design_replay` | 실제 호출 기록에 남은 응답 원문 | 수리 시험에서 요청·응답 해시와 모델·설정을 확인합니다. 생성 응답은 질문과 근거의 문맥을 대조하고 현재 검사 규칙을 다시 적용합니다. 검토 응답은 전체 요청이 같은 경우에만 재생합니다. | `design_replay.py`가 문맥 비교·완료 상태·후보 선택을 담당합니다. |
| `response-bundle` | 현재 요청 해시에 대응하는 응답 파일 | 형식 버전·모델·요청 해시와 응답 문자열을 확인합니다. 파일 교환만으로 모델이 실제 실행되었는지 판단하지 않습니다. | `response_bundle.py`가 파일 교환 형식을 검사하며 `llm.Agent`가 명시적으로 선택한 전송만 연결합니다. `repair_reader.py`는 별도로 원래 HTTP 호출 기록과 설정을 검증하고, 같은 요청에 서로 다른 응답이 있으면 수입을 거부합니다. |

## 호출 기록에서 공통으로 확인하는 범위

`design_trials.py`는 기존 `answer_cache`와 `design_replay`를 생성 실행에 연결하는 어댑터입니다. 비교 시험의 캐시 키·digest 조회·저장은 `answer_cache`, 영수증·완료 상태·후보 순서는 `design_replay`에 남습니다. 재생 후보의 현재 응답 검사가 실패하면 후보를 건너뛰며 새 호출의 재시도 예산을 소비하지 않습니다. 실제 CLI 오류는 그대로 전파하고 저장 응답으로 자동 대체하지 않습니다.

`design_compat.py`에는 기존의 정확한 과거 HTTP 정책 해시 쌍만 있습니다. 전체 답변에 명시적인 HTTP 작성자가 있어야 별칭을 허용하며, 누락·혼합·부분 작성자 맵과 CLI 작성자는 현재 해시가 필요합니다. 파일 이동으로 grounding 정책 소스를 수정하거나 허용 목록을 넓히지 않았습니다. 이 경계 이동은 #140의 무효화 정책 개선을 구현하지 않습니다.

운영 CLI 체크포인트의 `execution` 식별자는 `cli_checkpoint.execution_identity`가 기존 runner·model·command·args·실제 인자 필드를 그대로 조립합니다. 생성 실행 계층은 이 값을 전달하며 `cli_agent`의 인자 형식이나 `cli_schema`의 네이티브 schema를 해석하지 않습니다. 이 책임 이동은 저장 키·검증 정책·재시도·호환 허용 범위를 바꾸지 않습니다. CLI나 모델을 바꿨을 때의 기존 무효화 규칙도 유지합니다.

검증 정책의 AST 지문은 Python 버전에 따라 달라질 수 있고, 파일 바이트 지문은 체크아웃의 줄바꿈에도 영향을 받습니다. [동일 코드의 Python 3.12·3.14 대조](../inhouse/records/issue150-151-e117-candidate-audit.md#재개-후-정책-차이의-원인-분리와-한영-감사-기록-대조)처럼 코드·환경 차이를 나누어 확인하고, 원고를 생성·재검증·게시한 Python 버전과 정책 지문을 함께 기록하세요. 지문 차이만으로 의미 규칙 변경을 단정하거나 기록된 정책을 수동으로 고치지 않습니다. #141의 전후 보존 근거는 같은 런타임에서 비교한 결과이며, 다른 런타임의 지문을 자동으로 허용하는 예외를 추가하지 않습니다.

`call_records.py`는 한 호출의 `.receipt.json`, `.request.json`, `.response.txt`를 함께 읽습니다. 요청 JSON은 키를 정렬한 UTF-8 표현으로 해시를 계산하고, 응답은 저장된 UTF-8 바이트를 그대로 해시합니다. 응답의 개행이나 공백을 정리하지 않으며, 파일이 빠졌거나 해시가 다르면 실패합니다. 보관 디렉터리 밖의 경로와 심볼릭 링크를 통한 입력도 거부합니다.

공통 로더는 `transport`, `http_call`, `cli_call`, 모델, 설정, 완료 사유와 답변의 의미를 판정하지 않습니다. 이 조건들은 기록을 사용하는 검증기와 재생기가 판단합니다. 해시가 맞는 CLI 기록을 HTTP 기록으로 바꾸거나, `response-bundle` 기록을 새 모델 호출로 계산하지 않습니다.

요청이 같아도 여러 응답이 남을 수 있습니다. 공통 로더는 기록을 모두 보존합니다. 수리용 응답 수입의 충돌 거부와 문맥 재생기의 후보 정렬은 각 소비자에 남겨 둡니다.

## 시험 설정과 운영 입력의 분리

`trial_workspace.py`는 새 출력 경로가 운영 소스·원고·facts·입력 자산이나 이전 시험과 겹치지 않는지 확인합니다. 프로젝트 루트 아래의 새 `build/` 시험 디렉터리는 사용할 수 있습니다. 경로의 심볼릭 링크는 `resolve()`로 링크 정보가 사라지기 전에 검사합니다.

시험 설정은 `Config`를 깊은 복사로 만들고 출력 디렉터리만 새 위치로 옮깁니다. 섹션·시나리오·프롬프트·템플릿·집필 규칙·용어집은 원래 설정에서 계산한 경로를 유지합니다. 섹션 파일을 시험 디렉터리에 복사한 경우에는 그 복사본을 명시적으로 지정합니다. `sdd.yaml` 스냅샷에는 실제 CLI runner·모델·인자와 검사 설정을 기록하므로 다시 읽을 때도 같은 입력과 출력을 가리킵니다.

공통 함수는 이전 원고를 복사하거나, 다른 커밋의 시험을 재개하거나, 실행기를 바꾸지 않습니다. 사내 CLI 재현에서는 선택한 CLI의 실제 실행 결과와 미완료 단계를 별도로 확인합니다. 공개 libcamera 시험의 결과를 사내 HAL 검증 완료로 표시하지 않습니다.

다음으로 [설계 근거 검사](design-evidence.md)에서 재사용한 답변이 현재 근거와 연결되는 조건을 확인하세요.

## CLI 중간 실패에서 재개하기

실패 원인을 해결한 뒤 동일 설정과 소스에서 `sdd generate`를 다시 실행하세요. 검증된 앞선 항목은 원본 request/response/receipt와 CLI stdout을 함께 대조한 후 재사용합니다. 실패 항목은 새 CLI 호출로 처리하며, 손상된 체크포인트는 오류로 보고합니다. 프롬프트·질문·근거·커밋·모델/인자·집필 규칙이 다르면 새 생성 호출이 필요합니다. CLI가 기본 모델에 의존하면 체크포인트를 만들지 않습니다.

검증 코드만 바뀌면 원본 답변을 현재 결정적 검사로 다시 검증합니다. grounding 정책이 바뀌면 같은 답변을 새 실제 CLI 대조 호출로 재검토합니다. 새 정책에서 거절된 항목은 예전 통과 판정을 유지하지 않고 해당 항목만 다시 생성합니다. 이 재검증은 `checkpoint-revalidated`로 신규 생성·완전 재사용과 구분합니다. 전역 집필 규칙 변경은 모든 영향 항목의 신규 생성을 요구하며, 정책 해시를 고정하거나 호환 목록을 확대하지 않습니다.

`build/generation-runs/*.json`에는 신규 호출의 성공/실패와 시간, 문서별 항목의 신규 생성·체크포인트 재사용·원고 재사용·실패·미시작 상태를 따로 기록합니다. 실패한 호출과 재시도 시간도 포함합니다. 프로세스가 강제로 중단되면 마지막 `running` 항목을 완료로 계산하지 마세요. 원고의 문장이 매번 같다는 보장은 없으며 검증된 같은 원고의 사이트 반복 빌드 동일성과 구분합니다.

`review.max_calls`, `max_seconds`는 실행 전체, `document_max_calls`, `document_max_seconds`는 한 설계 문서의 상한입니다. 생략하거나 0이면 해당 상한을 적용하지 않습니다. 실패한 전송도 호출로 세며 예산 소진은 일반 답변 수정 재시도로 흡수하지 않습니다. 같은 설정을 동시에 실행하지 마세요. 공개 예제의 기본 상한은 운영 권장값을 뜻하지 않으며 실제 소요량에 맞춰 설정합니다.
