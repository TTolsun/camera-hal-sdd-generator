# 같은 근거를 작업과 판단에 연결하기

같은 기술 근거를 읽는 사람이 다음 구현 작업 또는 검증 범위의 판단으로 이어가도록 구성합니다.

`site.reader_paths`는 기존 Vendor/Developer 분류에 추가하는 진입점입니다. Vendor를 임원의 다른 이름으로 쓰거나 사내 직책·승인 권한을 추정하지 않습니다. 공개 libcamera는 검증용 사례이며 사내 HAL의 적용 실적이 아닙니다.

## 설정과 근거 소유권

공개 설정은 [reader-paths.yaml](../../examples/libcamera/reader-paths.yaml), 입력이 없으면 게시를 막는 사내 양식은 [사내 설정](../../examples/inhouse-template/config/reader-paths.yaml)에 있습니다.

```yaml
site:
  reader_paths: reader-paths.yaml
```

`schema: 1` 설정은 `ready`, `scope`, `limitations`, `required_inputs`, `claims`, `roles`를 갖습니다. `ready`가 `true`가 아니면 필요한 입력을 표시하고 게시를 중단합니다. 빈 사내 자료로 승인 가능한 보고서를 만들지 않습니다.

각 주장에는 표시할 `title`도 필요합니다. 현재 역할별 설정의 사람 승인을 기록하는 CLI는 없으므로 `site.require_approval: true`와 함께 사용하면 게시를 중단합니다. 기존 원고의 승인을 새 역할별 구성의 승인으로 승격하지 않습니다. 검토 환경에서 확인한 뒤 승인 기록 연동을 별도로 준비해야 합니다.

사실 설명은 기존 원고의 `generated_design.answers`가 소유합니다. `kind: fact`는 `sources: [{section, topic, part}]`로 분할 답변 하나를 선택하고 그 답변의 모든 문장을 생성 시 그대로 표시합니다. 사실의 대체 원고를 설정의 `text`에 쓸 수 없습니다. 조건·예외를 포함한 본문, 소스 발췌, 커밋과 검토 상태는 원래 상세 페이지에서 관리합니다.

가설(`hypothesis`), 미측정 효과(`unmeasured`), 결정 요청(`decision_request`)은 `text`, `condition`, `sources`, `needed_inputs`가 필수입니다. 결정 요청에는 `options`도 필요합니다. 이들의 링크는 판단의 배경이며 효과 측정값이 아닙니다. 형식 검사는 문장의 의미를 승인하지 않습니다.

## 먼저 고정할 질문과 출력 위치

| 진입점 | 필수 질문 | 출력 |
|---|---|---|
| 파트원(`work`) | 재현 조건, 조사 위치, 구현 책임, 수정 후 확인 | `reader-work.html#question-<aspect>` |
| 기술 의사결정자(`decision`) | 문제, 가치, 남은 위험, 선택지, 다음 결정 | `reader-decision.html#question-<aspect>` |

`work`의 `aspect`는 `reproduction`, `investigation`, `responsibility`, `verification`입니다. `decision`은 `problem`, `value`, `risk`, `options`, `decision`입니다. 질문 문구와 표시 순서는 설정에서 정하고 `claims`의 ID로 공통 답변을 참조합니다. 같은 페이지에서 답변을 다시 쓰는 질문은 첫 답변으로 연결합니다.

두 진입점은 사실을 하나 이상 공유하고 네 종류의 상태를 전체에서 다룹니다. 질문·근거·분할 답변 누락, 소스 커밋 불일치, 원고와 충돌하는 출력 위치는 게시를 중단합니다. 설정·생성 코드·원고·facts는 기존 manifest에 기록합니다. 기존 링크와 CLI, `impact.json` schema 1은 유지합니다.

질문마다 주장에 연결된 공통 상세 항목을 중복 없이 바로 연결합니다. 선택적인 `sources: [{section, topic}]`를 지정하면 해당 과업의 상세 항목을 먼저 표시하고 주장의 근거 링크도 유지합니다. `heading`에 기존 하위 제목을 지정하면 실제 렌더링된 제목을 확인해 그 위치로 연결합니다. 같은 주제 밖의 제목·코드 블록 속 제목·없는 제목·여러 번 등장하는 제목은 받지 않습니다. 질문 바로 아래에서 검증된 항목으로 이동하며, 같은 주장으로 되돌아가는 링크보다 먼저 표시합니다. 명시한 빈 목록이나 없는 항목은 이전 사이트를 보존한 채 게시를 중단합니다. 임의 URL이나 대체 설명은 받지 않습니다.

사실의 적용 조건·한계는 인용문보다 먼저 표시합니다. 정지의 오류 완료 계약은 애플리케이션 콜백이 모두 실행·반환했다는 보장으로 읽지 않도록 구분하며, 연결 방식·수신 객체 스레드·관찰 범위는 기존 상세 설명에서 확인합니다. 실제 장애 조사 착수와 문서의 근거 탐색 평가 착수는 다른 결정으로 이름을 붙입니다.

사실에는 선택적인 `details: [{section, topic, heading}]`로 읽기 조건의 상세 위치를 연결할 수 있습니다. 이 링크도 조건 뒤·인용문 앞에 표시하며 질문의 직접 링크에 포함합니다. `sources`의 원래 분할 답변 선택을 바꾸거나 사실 원고를 추가하는 필드는 아닙니다.

## 비작성자 평가의 사전 계획

평가 대상은 공개 libcamera의 “제출은 성공했지만 완료가 오지 않는 상황”입니다. 결과를 보기 전에 다음 과제를 고정합니다. 비교 기준은 기존 Vendor/Developer 진입점입니다. 속도나 ROI 개선률은 측정하지 않습니다. 사이트 전체의 설계 설명, 모든 기기의 실행과 사내 도입은 평가 범위에 포함하지 않습니다.

| 역할 | 문서만 읽고 답할 과제 | 성공 조건 |
|---|---|---|
| 파트원 | 처음 기록할 조건, 조사할 코드·값·분기, 수정할 구현의 책임·수명, 수정 후 확인을 설명합니다. | 제출과 완료를 혼동하지 않고 근거와 남은 확인 사항을 찾습니다. |
| 기술 의사결정자 | 문제, 확인된 기술적 성질, 가설·미측정 효과, 선택지·보류 조건, 추가 입력·다음 결정을 설명합니다. | 공개 사례를 사내 성과나 도입 승인으로 오해하지 않고 불확실성과 배경 근거를 찾습니다. |

평가자에게는 과제와 대상 사이트만 제공합니다. 설정·작성 대화·정답표는 주지 않습니다. 평가 전후 build ID가 다르면 같은 배포본에서 다시 평가합니다. 익명 역할 ID, 방문 URL·앵커, 실제 답변, 미발견 항목, 오해, 주관적 관련성(1–5점과 사유)을 기록합니다. 원본 공개 허락이 없으면 익명 집계만 공개합니다.

각 역할에서 실제 비작성자 한 명 이상이 필요합니다. 에이전트의 대리 역할 평가는 별도로 기록하며 사람 합격이나 실제 임원 공감 검증으로 승격하지 않습니다. 참여자가 없으면 사람 평가를 미완료로 남기고 구현·자동 검사·공개 반영을 진행합니다. 참여자에게 임의로 연락하거나 사내 조직을 추정하지 않습니다.

## 시각화와 적용 경계

역할별 질문과 판단 상태는 짧은 목록으로 표현하므로 진입점에서 기술 흐름을 다시 그리지 않습니다. 요청·버퍼·정지의 여러 단계와 소유권은 연결된 질문별 그림에서 확인합니다. 각 항목에서 기존 상세 그림으로 충분한지, 짧은 선택지·입력 목록이라 생략할 수 있는지 검토 기록에 남깁니다. 페이지 전체에 그림이 있다는 사실로 다른 항목을 통과시키지 않습니다.

다음 단계: [독자 품질 기준](reader-quality.md)에 따라 같은 배포본에서 과제를 수행합니다.
