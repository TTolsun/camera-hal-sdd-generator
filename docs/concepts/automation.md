# sdd automate가 동작하는 방식

**설정과 실행 순서는 [문서 갱신 시스템](../inhouse/03-update-system.md#c-예약-갱신과-게시)에 있습니다.** 이 문서는 실패했을 때 무엇이 재개되는지, Hermes와 누락 보완이 무엇을 바꾸고 무엇을 바꾸지 않는지를 설명합니다.

## 단계와 재개

`sdd automate`는 시작할 때 HAL 커밋 하나를 고정하고, 그 커밋의 게시가 끝나기 전에는 더 새로운 커밋으로 넘어가지 않습니다.

| 실패한 단계 | 다음 실행의 동작 |
|---|---|
| 추출·생성·검토 | `update-state.json`의 기준에서 재개하며 관문을 유지합니다. |
| 사이트 검증 | 게시 작업본을 유지하고 빌드를 재시도합니다. |
| 커밋·push | 검증한 산출물과 문서 커밋을 재사용합니다. |
| 배포·URL 확인 | 그 단계만 재시도합니다. 마지막 게시 성공 커밋은 전진하지 않습니다. |
| 변경 없음 | 빈 커밋을 만들지 않고, 산출물이 같으면 배포도 생략합니다. |

- 진행 상태는 `build/automation-state.json`에 남습니다.
- 미완료 게시 중에 게시 설정이나 `publish.remote`의 실제 주소가 바뀌면 재개하지 않고 멈춥니다. 시간 설정만 바꾸는 것은 허용합니다.
- 같은 설정의 중복 실행은 OS 잠금으로 거절합니다. 프로세스가 끝나면 잠금이 풀리므로 lock 파일을 지우지 않습니다.
- 확인 명령은 Git push나 HTTP 200만으로 성공 처리하지 않습니다. 실제 URL의 manifest와 모든 산출물 해시가 로컬 사이트와 같을 때만 0을 돌려줘야 합니다. 내장 `sdd verify-publication`이 이 계약을 따릅니다.

## Hermes 재검토가 바꾸는 것

Hermes는 근거 발췌의 해시가 바뀐 `design_topics`의 기존 설명을 다시 검토해 새 문장을 제안합니다.

1. 주제마다 질문, 기존 설명, 변경 전후 발췌를 보냅니다. 입력 한도를 넘으면 잘라 보내지 않고 실패합니다.
2. 필수 질문·근거 검사를 통과한 제안만 `sections.yaml`에 원자적으로 반영합니다. 해시는 실행기가 계산합니다.
3. 기다리는 동안 사용자가 설정을 고쳤으면 제안을 반영하지 않습니다.

Hermes가 하지 않는 것: 앵커·범위·질문 완화, 승인 정책 변경, 해시만 교체, `sdd accept` 호출. 기본 도구 집합은 `todo`로 제한해 파일 수정·터미널·네트워크 도구를 막습니다. 원본·프롬프트·응답은 `build/hermes/<HAL-SHA>/`에 남습니다.

## 커밋이 없는 날의 누락 보완

`automation.idle_review.enabled: true`이면 실행 시작 시 처리할 커밋이 없는 날에만 기존 문서의 누락을 한 항목 점검합니다. `sdd improve`로 한 번만 실행할 수도 있습니다.

1. 기존 섹션의 질문·설명과 고정 커밋의 소스 창 하나를 Hermes에 보냅니다.
2. 기존 prose 섹션에는 근거가 연결된 질문·설명을, per-scenario 섹션에는 실제 진입점을 더할 수 있습니다. 새 최상위 문서는 만들지 않습니다.
3. 별도 작업 디렉터리에서 근거·원고·사이트를 검증하고 통과한 제안만 반영합니다.

근거 부족·잘못된 JSON·승인 관문 실패는 `deferred`로 남기고 원본을 유지합니다. 같은 소스 창은 같은 커밋·`revision`에서 다시 점검하지 않습니다. 보류 원인을 고친 뒤 `revision`을 올리면 새로 점검합니다. 기록은 `build/idle-review-state.json`과 `build/idle-review/<실행 ID>/`에 있습니다.

## 자동화가 보증하지 않는 것

자동 검사, LLM 판정, Hermes 재검토는 모두 사람의 승인이 아닙니다. `site.require_approval: true`이면 승인 없는 원고는 게시되지 않습니다. 설명의 의미 정확성은 사람이 확인해야 합니다.
