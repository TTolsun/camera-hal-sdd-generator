# 사내 Claude로 문서 자동화 시스템 구축하기

**사내에 이 저장소와 HAL 소스를 준비한 뒤, 아래 지시문을 Claude에 전달하세요. 첫 목표는 실제 HAL의 한 경로를 문서화하고 코드 변경에 따른 갱신까지 검증하는 것입니다.**

이 가이드는 사내 환경에서 수행할 구축 절차입니다. 공개 libcamera에서 확인한 결과를 바탕으로 작성했으며, 사내 HAL 적용을 완료한 기록은 아닙니다. clone만으로 완성된 SDD가 생성되지는 않습니다. 실제 빌드 연결과 프로젝트별 설계 질문·설명·근거 설정이 필요합니다.

## 1. Claude에 전달할 지시문

아래 지시문을 복사하고, 알고 있는 소스 경로와 제품 빌드 구성을 함께 전달하세요. 환경에서 찾을 수 있는 정보는 Claude가 먼저 조사하고, 확인할 수 없는 필수 입력만 질문하도록 합니다.

```text
이 저장소를 기반으로 사내 Camera HAL의 설계 문서 자동화 시스템을 구축해줘.
docs/inhouse-agent-bootstrap.md를 구축 기준으로 사용해줘.

먼저 AGENTS.md, README.md, DESIGN.md, style/README.md,
docs/inhouse-adoption.md, docs/document-site.md,
docs/design-evidence.md를 읽어줘.

실제 HAL 소스 경로, 대상 제품과 빌드 변형, compile_commands.json,
생성 헤더와 분석 기준 커밋을 조사해줘. 환경에서 찾을 수 없는
필수 정보만 질문하고, 답변과 무관하게 진행할 수 있는 작업은 계속해줘.

1. 사내 HAL용 설정과 출력 위치를 별도로 만들고 실제 빌드의 사실 추출을 연결해줘.
   libcamera의 클래스명, 경로, 빌드·게시 방식이 같다고 가정하지 마.
2. 요청 제출·완료·flush 중 한 경로부터 실제 진입점을 확인해줘.
   책임, 상태, 입출력, 소유권, 스레드 경계, 오류와 종료 계약을
   소스와 대조하여 설계 질문·설명·근거로 작성해줘.
3. design_requirements와 design_topics를 구성하고, 각 설명에
   covers와 evidence를 연결해줘. 확인하지 못한 실행 동작은 명시해줘.
   근거 해시가 바뀌면 해시만 교체하지 말고 연결된 설명을 다시 검토해줘.
4. 생성된 Markdown과 HTML을 직접 고치지 말고 생성기와 프로젝트 설정을 수정해줘.
   필요한 공통 기능이 부족하면 생성기를 보완하고 관련 검증을 수행해줘.
5. 실제 코드 변경 전후의 두 커밋으로 영향 분석·문서 갱신과
   근거 변경 시 재검토 차단을 확인한 뒤, 사내 CI의 반복 실행에 연결해줘.

소스·facts·설계 설정·문서·프롬프트·로그는 사내 환경에만 보관해줘.
사용할 LLM과 정적 자산은 사내에서 허용한 경로로 설정해줘.
Claude가 작업을 수행하는 것과 생성기가 LLM을 호출하는 것은 구분해줘.

자동 검사 통과를 사람의 승인으로 기록하지 마.
사내 게시 위치와 운영 승인 정책을 확인하여 배포 단계를 구성해줘.
설정이나 권한이 준비되지 않았다면 검증된 산출물과 구체적인 미완료 항목을 남겨줘.

완료할 때 실제 설정 경로, 재실행 명령, 기준 커밋, 검증 결과,
실패 후 재개 방법과 미검증 범위를 문서로 남겨줘.
한 경로의 초기 구축 완료와 전체 HAL의 운영 적용 완료를 구분해서 보고해줘.
```

## 2. 먼저 확인할 입력과 저장 위치

| 입력 | 확인할 내용 |
|---|---|
| 소스와 기준 커밋 | 분석할 저장소, 고정 SHA와 첫 문서화 경로를 정합니다. |
| 실제 빌드 입력 | 제품·빌드 변형별 compile DB, include 경로, 매크로와 생성 헤더를 확보합니다. |
| 생성 방식 | 소스 계약·facts 기반 생성과 LLM 초안 중 필요한 방식을 선택합니다. LLM을 쓸 때만 허용된 엔드포인트·모델·인증 방법을 확인합니다. |
| 사내 열람 환경 | 코드 인용 URL, Mermaid 자산, 문서 서버 또는 사내 아티팩트 저장소를 정합니다. |
| 반복 운영 환경 | 실행할 CI·호스트, 변경 감지 방식, 검토 담당자와 게시 정책을 확인합니다. |

예를 들어 생성기 옆에 별도 사내 프로젝트 디렉터리를 둘 수 있습니다. 아래 이름은 배치 예시이며 필수 경로가 아닙니다.

```text
workspace/
  camera-hal-sdd-generator/    # 공통 생성기
  hal-camera-analysis/        # 분석·갱신 전용 HAL 체크아웃
  hal-sdd-project/            # 사내 설정과 산출물
    sdd.yaml
    config/
      sections.yaml
      scenarios.yaml
    build/
    sdd/
```

`sdd.yaml`의 상대 경로는 해당 설정 파일 기준입니다. `source.root`·`source.compile_commands`·출력 경로와 `paths.config`·`paths.prompts`·`paths.templates`·`paths.style`을 실제 배치에 맞춥니다. 공통 프롬프트와 템플릿을 생성기 저장소에서 참조할 수 있습니다. 설정 상세는 [사내 적용 절차](inhouse-adoption.md#2-바꿀-설정)를 따릅니다.

사내 클래스명과 소스 발췌에 연결한 설명이 들어간 설정도 사내 파생 데이터입니다. 공개 저장소의 예제 디렉터리에 추가하거나 공개 upstream으로 push하지 않습니다. `.gitignore`는 반출 방지 장치가 아니므로 사내 저장소와 출력 위치를 명시적으로 정합니다.

## 3. 한 경로에서 처음부터 끝까지 검증하기

### 빌드와 추출을 연결합니다

1. 실제 제품 빌드에서 compile DB와 생성 헤더를 준비합니다. 예제 경로나 추측한 include 경로로 통과시키지 않습니다.
2. `doctor`로 환경을 확인하고 필요하면 `compdb --normalize`로 별도 정규화본을 만듭니다.
3. `extract`를 실행하여 파싱 오류·빈 입력·진입점 누락을 해결합니다. 클래스 수와 파일 범위가 의도한 제품 구성을 반영하는지도 확인합니다.

생성기 루트에서 별도 설정을 지정하는 예시입니다.

```bash
uv sync --extra dev
uv run sdd --config ../hal-sdd-project/sdd.yaml doctor
uv run sdd --config ../hal-sdd-project/sdd.yaml extract
```

### 설계 설명을 구성합니다

1. 요청 제출·완료·flush 중 실제로 추적할 한 경로의 함수 시그니처를 소스에서 확인합니다.
2. 해당 경로를 이해하는 데 필요한 질문을 `design_requirements`에 정의합니다. 함수 목록만으로 수명이나 종료 계약을 설명했다고 판단하지 않습니다.
3. `design_topics`에 소스 발췌와 대조한 설명을 작성하고 `covers`·`evidence`를 연결합니다. 발췌의 SHA-256은 검토한 본문에 고정합니다.
4. 가상 호출 후보, 함수 포인터, 큐와 콜백의 경계를 구분합니다. 확인하지 못한 실행 사항은 `kind: limitation`으로 남기고, 이 문장만으로 필수 질문의 답변을 대체하지 않습니다.
5. 문서를 생성하여 설명·그림·근거 링크와 펼칠 수 있는 원문을 확인합니다.

```bash
uv run sdd --config ../hal-sdd-project/sdd.yaml generate
```

Claude는 초기 설명을 작성하고 코드와 대조하는 구축 담당 역할을 수행합니다. 생성기의 `agent.kind`는 별도 모델 호출 설정이며 현재 `ollama`, `openai-compatible`, `dry-run`을 지원합니다. 사내 Claude가 저장소에서 작업한다고 해서 생성기가 자동으로 그 세션을 모델 엔드포인트로 사용하는 것은 아닙니다. 소스 계약과 facts 기반 문서는 생성할 때 LLM 호출이 필요하지 않습니다. LLM 초안을 사용할 때는 지원되는 사내 연결 방식을 별도로 구성합니다.

처음에는 `site.enabled: false`로 문서 생성과 사이트 빌드를 분리할 수 있습니다. 운영 설정에 `site.require_approval: true`를 둔 경우, 미승인 원고의 `export-site`가 차단되는 것이 정상입니다. 검토용 미리보기가 필요하면 게시 위치와 분리된 출력·설정을 사용하고 사람 검토 전 상태를 유지합니다. 운영 검사를 없애서 생성 성공으로 보고하지 않습니다.

### 코드 변경을 반영하는지 확인합니다

1. 기준 커밋의 facts와 원고를 별도로 보존합니다.
2. 실제 관련 변경이 있는 후속 커밋에서 빌드 입력과 facts를 갱신합니다. 해당 경로에 적합한 커밋이 없으면 격리된 검증 브랜치에서 변경 사례를 만들고 운영 소스와 구분합니다.
3. 이전 facts를 지정하여 영향 분석을 실행하고 문서 범위 누락을 확인합니다.
4. 근거가 달라진 설명은 다시 대조하여 갱신합니다. 재검토하지 않은 옛 설명이 새 커밋으로 조용히 이월되지 않는지 확인합니다.
5. 갱신한 원고를 생성하고 사이트의 링크·해시·반복 빌드 결과를 확인합니다. 실패 경로에서는 기존 사이트가 보존되어야 합니다.

```bash
uv run sdd --config ../hal-sdd-project/sdd.yaml impact --base <이전-SHA> --base-facts <보존한-facts.json> --fail-on-coverage-gap
uv run sdd --config ../hal-sdd-project/sdd.yaml generate --from-impact
uv run sdd --config ../hal-sdd-project/sdd.yaml export-site
uv run sdd --config ../hal-sdd-project/sdd.yaml verify-site
```

`design_requirements`의 검사 결과는 설정 루트의 `build/design-review.json`에 기록됩니다. `documented`는 질문에 답변과 변경되지 않은 소스 근거가 연결되었다는 뜻입니다. 설명의 의미나 실기기 동작에 대한 승인은 아닙니다. 자세한 규칙은 [설계 근거 검사](design-evidence.md)를 따릅니다.

## 4. 사내 CI와 게시 단계 연결하기

초기 검증 후 사내에서 사용하는 CI나 실행 서비스에 다음 단계를 연결합니다. 특정 CI 제품이나 GitHub Pages를 필수로 사용하지 않습니다.

| 단계 | 구성할 동작 |
|---|---|
| 변경 감지 | 사내 저장소의 이벤트 또는 주기 작업으로 대상 ref를 확인합니다. |
| 증분 갱신 | `sdd update --to <ref>`를 실행합니다. 빌드 입력 재생성이 필요하면 `update.compdb_cmd`에 명령 인자 목록을 설정합니다. |
| 실패·재검토 처리 | 종료 코드와 `update-state.json`·영향 보고서·설계 검사 결과를 보관하고 담당자가 확인할 수 있게 합니다. 실패한 커밋을 완료 처리하지 않습니다. |
| 검토와 사이트 검증 | 실제 검토에 따라 승인 장부를 기록하고 `export-site`와 `verify-site`를 실행합니다. 자동 검사 통과만으로 승인자를 대신하지 않습니다. |
| 게시 | `sdd automate`로 Git 반영과 환경별 배포·확인 명령을 연결합니다. [예약 게시 절차](scheduled-publication.md)를 따릅니다. |

`update`는 커밋마다 소스를 체크아웃하므로 개발자가 수정 중인 작업 폴더와 분리합니다. 같은 소스·설정·출력 경로를 사용하는 작업은 CI에서 동시 실행되지 않도록 설정합니다. 기준 facts, `build/update-state.json`, 원고와 승인 장부는 재실행에 필요한 상태이므로 실행 간에 보존합니다.

근거가 바뀐 설계 설명은 현재 생성기가 스스로 해석하여 승인하지 않습니다. 재검토 과정을 사람이나 사내 에이전트 작업으로 연결할 수 있지만, 해시만 자동 교체하여 검사를 통과시키는 작업으로 만들면 안 됩니다. 실행 실패와 검토 대기를 구분하고, 해결 후 같은 명령으로 재개하는 절차를 남깁니다.

## 5. 완료 기준과 인계할 결과

첫 적용의 완료 기준은 다음과 같습니다. 모든 HAL 경로를 다뤘다는 선언과 구분합니다.

| 완료 항목 | 남길 증거 |
|---|---|
| 실제 제품 구성에서 추출했습니다. | 기준 SHA, 빌드 구성, compile DB 위치와 추출 결과를 기록합니다. |
| 한 경로의 설계를 설명했습니다. | 필수 질문별 답변·소스 근거·미검증 사항과 생성된 문서를 남깁니다. |
| 코드 변경을 처리했습니다. | 전후 SHA, 영향 보고서, 갱신 또는 재검토 차단 결과를 남깁니다. |
| 반복 실행을 검증했습니다. | 사이트 링크·해시 검사, 같은 입력의 반복 빌드, 실패 후 재개 결과를 기록합니다. |
| 운영자가 다시 실행할 수 있습니다. | 설정 경로, 정확한 명령, CI 정의, 상태 보존 위치, 게시·복구 절차와 남은 작업을 사내 문서로 남깁니다. |

빌드 입력·권한·게시 대상이 없어 끝내지 못한 단계는 구체적인 미완료 항목으로 보고합니다. 로컬 미리보기만 만들었다면 사내 배포가 끝났다고 표현하지 않습니다. 첫 경로의 검증을 마친 뒤 같은 기준으로 요청 제출·완료·flush와 나머지 HAL 경로를 확장합니다.

다음 단계: [사내 적용 절차의 필요한 입력](inhouse-adoption.md#1-필요한-입력)을 실제 환경과 대조합니다.
