Official cam and actual DMA-BUF verification results

This is a virtual test configuration. It must not be used as a support or performance claim for an actual product.

On the WSL2 test kernel 6.18.33.2-microsoft-standard-WSL2-issue211, with udmabuf built in, we ran the unmodified official cam, based on source 293d751a814e0d4c34e85ad457ccd9d5eefd1a61, as a root child process. We applied the (0) 400x300-NV12/SMPTE170M setting to virtual camera Virtual2. Three independent processes each completed 3 frames and ended with exit code 0. Cancelled callbacks were 0 in all three processes, and the unprivileged run failed with errno 13.

The DMA-BUF access records come from a separate probe, dmabuf-probe-2, not from the official cam. The probe recorded, at allocate, backing_fd 4, dmabuf_fd 5, and size 4096. After mmap, it logged sync-start (flags 3), cpu-access of 4096 bytes, sync-end (flags 7), munmap, close-dmabuf, close-backing, and close-provider, all with result 0. The records do not contain the names SYNC_START and SYNC_END; the event names are sync-start and sync-end.

The three frames confirmed in the callback and subsequent processing

This is a virtual test configuration. It must not be used as a support or performance claim for an actual product.

CameraSession::requestComplete returns without doing anything if the request status is RequestCancelled. Any other completed request defers the processRequest call to the event loop via EventLoop::instance()->callLater so that the camera manager thread is not blocked. If the capture limit has been reached, processRequest returns immediately; otherwise, processRequest prints frame information and then increments captureCount_. The observation point is inside the processRequest function, immediately before captureCount_ is incremented.

In the measurement data, for each of the three independent processes (pid 434, 449, 464), the callback-entry and frame-processed events are paired by the same request address and sequence (0, 1, 2), so three frames are counted once per process. The Request status enum is declared in the order RequestPending, RequestComplete, RequestCancelled, and no numeric values are specified, so the actual status 1 corresponds to the second item, RequestComplete. The TIDs of the callbacks threads are 437, 452, 467, and the TIDs of the main_tid and processed threads are 434, 449, 464. The buffer_sequence values 0, 1, 2 with successful buffer status (buffer_status 0) match the successful_buffer_sequences values 0, 1, 2.

Execution check item: The 0 cancellations (cancelled_callbacks 0) are this observed value; since the cancellation branch was not dynamically executed, the observed count of 0 is not a forced result. Because the callback-return instruction was not observed, this measurement is not verification of the cancellation path, return instruction, or performance. There is an observation limitation that GDB breakpoints affect timing, and the result applies only to source 293d751a814e0d4c34e85ad457ccd9d5eefd1a61, the WSL2 custom UDMABUF kernel, and the Virtual2 400x300 NV12 configuration; physical DMA, physical camera, other operating applications, and internal HAL are not verified. This configuration is a simulation-based virtual trial configuration and is not an actual product.
