# 앱이 요청한 USB 뷰파인더 크기를 어디까지 추적할 수 있나

기준 소스는 libcamera `adfa719f8ed67d18fd8a0739fc088a1f8b9e7252`다. [기준 공개판](https://github.com/TTolsun/libcamera-sdd/tree/ec95369614b2a80631e53c1e5447132ce481fa06/docs)의 빌드 ID는 `bd487ad37969d729667eceb2c24c8b86c285145d0c764c0a1f4288b8c9ec2c29`다.

공식 앱 가이드에서 뷰파인더 한 개를 만들고 크기를 640×480으로 바꾼 뒤 검증 결과를 읽는 사례를 선택했다. 가이드의 320×240은 조정이 가능한 한 예다. 장치 구현은 고정된 소스의 UVC 핸들러를 사용한다. 공식 핸들러 가이드의 Vivid는 별도의 교육용 구현이다. [앱의 구성 검증](https://docs.libcamera.org/master/guides/application-developer.html#change-and-validate-the-configuration) · [핸들러의 구성 적용](https://docs.libcamera.org/master/guides/pipeline-handler.html#configuring-a-device)

## 독자에게 준 과제

ForDeveloper에서 시작한다. USB 카메라에 640×480을 요청했을 때 앱이 다시 읽을 값과 장치가 적용하려는 값을 찾아 설명한다. 요청값과 다른 경우에도 계속할 수 있는 시점과 오류로 돌아오는 시점을 구별한다. 실제 보드에서 확인할 결과를 적는다. 독자에게는 고정 사이트와 그 안의 코드 발췌만 제공한다.

수정 전 독자는 `for-developer.html#configure`에서 공통 검증과 핸들러의 반환값을 찾고 기능·지원 범위에서 앱이 조정된 값을 확인하는 절을 찾았다. 진단 자료가 UVC 검증 함수를 후보로 언급했지만, 확인한 한국어 페이지 34개에서는 UVC가 검증한 크기를 장치에 넘기는 지점과 드라이버가 다른 값을 반환했을 때의 결과를 연결할 수 없었다. 공개된 가상 카메라의 400×300 관측값은 이 USB 카메라의 결과로 해석하지 않았다.

## 수정 후 같은 과제에서 확인한 점

생성 설정에 공식 앱 가이드와 UVC·공통 구현의 소스 창 10개를 연결하고, ForDeveloper의 공통 구성 절 다음에 이 사례를 배치했다. 새 자동 독자는 같은 질문만 받고 목차에서 해당 절로 이동했다. 독자는 외부 저장소를 열지 않고 그림 아래의 내부 코드 발췌에서 다음 세 가지를 설명했다.

- 앱은 검증 뒤 남은 스트림의 크기와 픽셀 포맷을 확인하고 조정된 값을 수용하거나 거절할 수 있다.
- 접근 검사 뒤 공통 재검증을 통과하려면 결과가 `Valid`여야 한다. UVC는 검증된 크기와 대응하는 FourCC를 장치에 전달한다. 적용 호출의 오류는 그대로 반환하고, 호출이 성공했어도 반환 크기나 FourCC가 검증값과 다르면 `-EINVAL`을 반환한다.
- 성공하면 앱은 연결된 스트림의 활성 구성을 읽는다. 특정 보드의 지원값과 실제 적용 결과를 알려면 장치에서 따로 확인해야 한다.

그림 설명의 줄 번호는 외부 전체 소스를 가리킨다. 독자는 같은 그림 아래 ‘그림 근거와 확인 범위’에서 내부 코드 발췌로 이동했다. 이 시험은 자동 독자 한 명의 수정 전 결과와 다른 자동 독자 한 명의 수정 후 결과를 기록한다.

## 원고 작성과 독립 검토

격리된 Codex CLI에서 `gpt-6-luna` high로 새 원고를 생성했다. 최종 시험은 같은 소스 창을 사용하되, 공통 접근 검사와 재검증 순서, 장치 오류와 반환값 불일치, 앱과 UVC 내부의 관찰 위치를 집필 질문에 명시했다. 시험 그림의 첫 노드는 앱의 검증 호출만 표시했다. 새 원고의 SHA-256은 `58473de0aa3ea7b67a97d2b205961981d7fd711b3c15d62d921744c180c9ce8b`이며 자동 검사는 통과했다. 별도 Terra High 검토는 보완으로 판정했다. 공식 앱 예제가 실제로 수행하는 동작과 앱 작성자가 내려야 할 결정의 구분, stride·프레임 크기·색 공간이 검증 단계에서 온 값이라는 설명이 남았다.

정식 공개 원고는 공개 프로필의 Terra High로 생성했다. SHA-256은 `3c61c3556093a5ffc315eb2c150fbf940f4e5fe72ef45dbb79d814b003bbab69`다. 독립 Terra High 소스 대조는 통과했고 한영 일관성 검사에서 미해결 지적은 없었다. 사람 독해 시험과 보드 측정은 수행하지 않았다.

## 후속 시험에서 공개 집필 입력과 Luna 입력을 일치시켰을 때

기준은 [앞선 공개판](https://github.com/TTolsun/libcamera-sdd/tree/a774f3d838a74ee53e174e4ec508e71207734fe1/docs)이다. 이 빌드의 ID는 `05106a238aa2f1ce61ff2d1a0f1175793be5d34a9454cb499c8d39def3fd4b40`이고 libcamera 소스 커밋은 같다. 독자에게 ForDeveloper의 뷰파인더 절 본문과 그림에서 다음 두 질문의 답을 찾아 달라고 했다.

1. 가이드의 예제 코드는 어떤 동작을 하고, 조정된 구성을 받아들일지는 누가 결정하는가?
2. 활성 구성의 stride, frameSize, 색 공간은 어디에서 오며 장치 적용 후 어떤 값을 다시 대조하는가?

수정 전 독자는 앱이 조정된 값을 수용하거나 거절할 수 있고 UVC가 적용 뒤 크기와 FourCC를 비교한다는 설명을 찾았다. “호출해야 합니다”라는 지침에서 예제 코드에 실제 분기가 있는지는 확정할 수 없었다. 세 필드의 이름이나 값을 채우는 시점도 본문과 그림에서 찾지 못했다.

생성 설정을 가이드 예제와 호출자의 판단, 장치 적용, 활성 구성 값의 출처라는 세 질문으로 나눴다. 예제에서 `validate()`를 호출해 검증 후 구성을 출력하고 이어서 `configure()`를 호출하는 코드까지 발췌했다. 그림 설명과 한영 대조 계약에도 호출자의 수용 결정과 각 필드의 출처를 반영했다.

새 Luna 시험은 공개 예제의 섹션·그림·검토 계약 파일이 같은지 바이트와 파싱 결과로 대조했다. 원고 작성 모델은 Codex CLI의 `gpt-6-luna` high였다. 새 출력 디렉터리에서 130.01초에 생성하고, 집필·근거 대조의 완료 영수증 8개를 확인했다. 원고 SHA-256은 `5cc0bee7aa39d7d13f48b7860241e5dfc1e18a123f363877ede7c91df1d84fef`다. 자동 검사와 독립 Codex CLI Terra High의 네 항목(두 보완점, 기본 처리 경로, 그림)이 모두 통과했다.

- 예제는 `validate()`의 반환값을 사용하지 않고 검증된 구성을 `toString()`으로 출력한다. 호출자는 `Adjusted`이면 스트림 제거와 남은 스트림의 매개변수 변화를 포함해 구성 전체를 살핀 다음 수용 여부를 정한다.
- UVC는 `tryFormat` 결과의 첫 평면에서 `bpl`과 `size`를 읽어 `stride`와 `frameSize`를 채운다. 색 공간이 달라졌으면 구성에 반영한다. 성공한 `setFormat` 호출 뒤 대조하는 것은 검증된 크기와 FourCC다. UVC는 이때 앞의 세 필드를 다시 비교하거나 덮어쓰지 않는다. 앱이 성공 후 읽는 값은 공통 코드가 활성 스트림에 복사한 구성이다.

중간 원고에서 “요청값”의 비교 기준이 모호했고, “장치에서 적용한 값을 확인”한다는 서두가 실측으로 읽힐 수 있어 생성 입력을 고치고 다시 작성했다. 사람 승인과 특정 보드의 지원 여부·적용값은 이 시험의 판정에 포함하지 않았다.
