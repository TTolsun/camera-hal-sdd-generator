# libcamera 설계 문서

**카메라 API부터 Pipeline Handler와 IPA까지, 코드 구조와 근거를 함께 읽는 문서입니다.**

이 문서는 공개 libcamera 소스를 분석해 만든 검토용 설계 문서입니다. libcamera 공식 문서의 탐색 구조와 OMM의 읽기 중심 디자인을 적용했습니다.

## 읽는 순서

연동 중 오류를 찾고 있다면 **요청 처리와 문제 진단**부터 읽으세요. 내부 구현을 수정한다면 시스템 개요에서 시작하여 해당 파이프라인과 알고리즘의 근거를 확인하세요.

| 하려는 작업 | 먼저 읽을 문서 | 확인할 결과 |
|---|---|---|
| 요청과 버퍼를 안전하게 재사용합니다. | [요청 처리와 문제 진단](request-lifecycle.md) | 자원별 유지 기간과 재사용 조건을 확인합니다. |
| 제출 성공 뒤 완료가 오지 않는 원인을 찾습니다. | [요청 처리와 문제 진단](request-lifecycle.md) | 제출 실패, 준비 대기, 장치 처리, 완료 통지를 구분합니다. |
| 파이프라인의 완료·정지 코드를 수정합니다. | [Pipeline Handler](pipeline-handler.md) | 제출 순서 반환과 정지 중 대기 요청 처리 계약을 확인합니다. |
| IPU3 LSC의 제어값이나 갱신 조건을 수정합니다. | [IPU3 LSC의 설정과 프레임 처리](ipu3-lsc-flow.md) | 조건별 파라미터 갱신과 별도로 필요한 실행 검증을 확인합니다. |

1. **시스템 개요**에서 카메라 탐색·요청 생성·완료의 책임과 캡처 세션의 상태를 확인한 뒤 관련 패키지를 찾으세요.
2. **핵심 시나리오**에서 요청 제출·완료와 캡처 종료·취소에 관련된 주요 호출과 정적 추적의 경계를 확인하세요.
3. **요청 처리와 문제 진단**에서 제출부터 완료·재사용·정지를 연결해서 읽으세요. **카메라와 요청 모델**에서 소유권과 상태 전이를, **Pipeline Handler**에서 요청 큐·완료·정지 계약을, **IPA 관리와 구현 진입점**에서 모듈 선택·실행 경계·입출력·오류 처리를 확인하세요.
4. **IPU3 LSC** 두 문서는 한 알고리즘을 끝까지 따라가는 예입니다.

각 페이지 끝의 "다음 단계" 링크가 이 순서를 그대로 잇습니다.

클래스 표의 "책임" 칸은 소스의 문서 주석에서 가져옵니다. libcamera는 클래스 설명을 구현 파일에 따로 적기도 하므로, 선언에 붙은 주석과 구현 파일의 문서 주석을 함께 읽습니다.

각 페이지에는 추출한 클래스, 구조 설명, 관계 그림과 코드 근거가 있습니다. 관계 그림을 누르면 확대하거나 클래스 이름을 검색할 수 있습니다. 소스 링크는 분석에 사용한 커밋의 파일과 줄로 연결됩니다.

설계 계약 문서는 질문별 설명 위치를 안내하고, 설명 아래에서 연결된 소스 발췌 원문을 펼쳐 볼 수 있습니다. 실행 확인 항목은 코드에서 설명한 동작과 구분하여 읽으세요.

왼쪽 메뉴에서 목차에 딸린 하위 문서는 접었다 펼 수 있습니다. 읽고 있는 가지만 펴 둡니다.

시나리오의 주요 확인 지점과 관계도는 설정에서 선택한 호출 근거로 만듭니다. 가상 호출 후보와 예약 대상은 추적 경계 표에서 확인할 수 있습니다. 관계도는 실행 순서를 뜻하지 않습니다. 로깅과 접근자 호출을 포함한 전체 추적 기록은 페이지 안에서 구간별로 펼쳐 볼 수 있습니다.

## 검토 상태 읽기

사람이 승인하지 않은 생성 문서는 **사람 검토 전**으로 표시합니다. `ok`는 해당 생성 방식에 적용된 자동 검사를 통과했다는 뜻이며, 설명의 정확성이 승인되었다는 뜻은 아닙니다. `needs-review`는 자동 검사에서 확인할 문제가 남아 있다는 뜻입니다.

현재 검사 결과와 승인 상태는 아래 문서 목록에서 확인하세요. 각 페이지에는 추출 사실로 만든 설명, 소스 발췌에 연결한 설계 설명, LLM 설명 등 생성 방식과 검증 범위를 표시합니다. 발췌 해시 일치나 자동 검사 통과가 사람의 내용 검토를 대신하지 않습니다. 클래스 관계 그림도 실행 순서나 실기기 동작을 보증하지 않습니다.

같은 근거로 4B·9B 모델을 비교했지만 두 모델 모두 소유권·종료·실행 경계 설명에 오류나 누락이 남았습니다. [비교 기록](https://github.com/TTolsun/camera-hal-sdd-generator/blob/main/docs/model-comparison.md)에 원문과 판정 근거를 보존했습니다. 비교 원고는 이 사이트의 설계 설명으로 채택하지 않았습니다.

## 분석과 배포 범위

분석 기준 커밋은 각 문서에 표시합니다. WSL2에서 IPU3·RKISP1·UVC와 GStreamer를 포함해 빌드하고 추출한 결과를 사용합니다. 개요·카메라·Pipeline·IPA·LSC 처리 설명은 예제 설정에 작성된 계약을 소스 발췌와 대조하여 생성합니다. 핵심 시나리오에는 `Camera::stop()`의 종료·취소 경로도 포함합니다. 시나리오는 libclang으로 추출한 호출 관계와 경계를 표시하며, 실기기 촬영과 실행 검증은 후속 작업입니다.

[camera-hal-sdd-generator](https://github.com/TTolsun/camera-hal-sdd-generator)는 분석·생성·검증·화면 구성 기술을 관리합니다. [libcamera-sdd](https://github.com/TTolsun/libcamera-sdd)는 원본 소스 이력과 완성 문서의 배포를 담당합니다. 공개 환경에는 정기 예약을 두지 않습니다. 생성기 저장소에서 작업할 때 공식 upstream 확인·동기화와 문서 갱신·배포를 함께 수행하고, 새 커밋이 없으면 기존 카테고리의 누락을 점검합니다. 정기 예약과 시간 변경 기능은 사내 운영을 위한 공통 실행기에서 제공합니다.

원래 라이브러리의 사용법은 [libcamera 공식 문서](https://docs.libcamera.org/master/)에서 확인할 수 있습니다.
